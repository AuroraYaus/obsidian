# T5.5 译码硬件验证思维：从 golden model 到 bit-exact 回归
## 本节学习目标

译码硬件不是“仿真跑过一个例子”就算可靠。一个真实译码器会遇到不同传输块长度、码块数量、软信息幅度、冗余版本、早停条件、复位、反压、错误注入和边界输入。验证的任务是系统性地证明：在这些条件下，硬件行为和参考模型一致，错误能被观察到，问题能被定位。

本节讲 golden model、bit-exact 对比、约束随机、边界案例、覆盖率、回归和波形调试，并说明循环冗余校验通过/失败如何成为译码结果的可观察证据。

- 解释 golden model 和设计实现之间的关系。
- 区分 bit-exact、数值容差和协议级 pass/fail。
- 为一个码块译码器列出最小验证计划，并能说明传输块级结果怎样由多个 CB（码块，Code Block）结果汇总而来。
- 说明为什么 CRC（循环冗余校验，Cyclic Redundancy Check）pass/fail 是重要观察点，但不能替代内部一致性检查。
- 设计边界案例覆盖定点饱和、最大迭代、输入反压和错误路径。
- 说明回归测试为什么要记录随机种子、配置、输入向量和输出证据。

## 前置知识检查

| 前置项 | 本节需要达到的程度 |
|:---|:---|
| 定点软信息 | 知道对数似然比在硬件里通常被量化。 |
| CRC | 知道 CRC pass/fail 可用于判断候选译码结果是否可接受。 |
| FSM | 知道译码器有 load/decode/check/output 等状态。 |
| Python | 能理解 Python 参考模型可生成期望结果。 |
| 硬件描述 | 知道寄存器传输级是硬件实现描述层级。 |

如果只记住一句话：验证不是证明“某次看起来对”，而是建立可重复、可定位、可覆盖的证据链。

## 资料与协议边界

本节是工程验证基础课。3GPP 规范提供协议行为的权威来源，例如 CRC 多项式、分段规则、编码结构、速率匹配和冗余版本；验证方法本身，例如覆盖率模型、随机约束、波形调试和回归框架，不是 3GPP 规定。

| 协议背景 | 本地证据 |
| :--- | :--- |
| LTE TS 36.212 Rel-19 `36212-j30` | `3GPP_Rel19/processed/TS_36.212_36212-j30` |
| NR TS 38.212 Rel-19 `38212-j30` | `3GPP_Rel19/processed/TS_38.212_38212-j30` |
| 硬件验证方法 | 不适用 |

协议边界：如果一个测试宣称“协议一致”，必须能追溯到 TS 编号、章节、表格或公式；如果一个测试只检查握手、饱和或 FSM，则应标注为实现验证，不伪装成协议要求。

## golden model 的角色

golden model 是参考模型。它不一定快，也不一定适合硬件实现，但它必须清晰、可审计、可复现。译码项目里常见的 golden model 分三层：

| 层级 | 作用 | 例子 |
|:---|:---|:---|
| 浮点 golden | 验证算法方向 | Python/MATLAB Turbo（Turbo 码，Turbo Code）Log-MAP、LDPC（低密度奇偶校验码，Low-Density Parity-Check Code）Min-Sum、Polar（极化码，Polar Code）SCL（连续消除列表译码，Successive Cancellation List）。 |
| 定点 golden | 验证量化和饱和 | C/Python bit-exact 定点模型。 |
| 协议 golden | 验证比特级流程 | TS 36.212/38.212 分段、CRC、rate matching。 |

RTL（寄存器传输级，Register Transfer Level）应该先对齐定点 golden，再通过协议 golden 进入链路级验证。若直接用 CRC pass/fail 验 RTL，问题会很难定位：CRC fail 只能说明最终结果不对，不能告诉你是 LLR（对数似然比，Log-Likelihood Ratio）符号、地址、饱和、状态机还是 CRC 本身错了。

## 验证的基本理论

验证这个词容易被误解成“跑一下程序”。工程上更准确的定义是：给定一个设计目标、一个可观察接口和一组输入条件，收集足够证据说明设计行为满足目标。这里有三个关键词。

| 关键词 | 含义 | 译码器中的例子 |
|:---|:---|:---|
| 设计目标 | 设计应该实现什么行为 | 对每个 CB 输出正确硬判决和 CRC 状态。 |
| 可观察接口 | 测试能看到什么 | 输入 LLR、输出比特、状态、计数器、波形。 |
| 输入条件 | 测试覆盖哪些场景 | 长度、软信息幅度、迭代次数、反压、复位。 |

验证不能证明“所有可能世界都正确”，但可以用系统化证据降低漏错风险。对译码硬件来说，风险主要来自四类不一致：

1. 数学不一致：算法公式、近似方法或定点缩放与参考模型不同。
2. 协议不一致：CRC、多码块拼接、速率匹配、冗余版本或 filler bit 的顺序错。
3. 时序不一致：valid/ready、复位、反压和状态机在某些周期组合下丢数据。
4. 存储不一致：bank 地址、循环缓存、读写同址或初始化状态与预期不同。

因此，一个好的验证计划必须同时覆盖“值是否正确”和“值在什么时间、什么顺序、什么状态下出现”。只看最终输出值，容易漏掉握手重复、状态越界和内部存储污染；只看波形状态，又不能证明数学结果正确。

## 数值例子：错误定位的证据链

设一个小型译码器测试向量包含 4 个输入 LLR，golden model 的输出硬判决为：

$$
\mathbf{b}_{\mathrm{golden}}=[0,1,0,0]
\tag{1}
$$

RTL 输出为：

$$
\mathbf{b}_{\mathrm{rtl}}=[0,1,1,0]
\tag{2}
$$

最终比较发现 index 2 不一致。验证报告不能只写“fail”，而应继续构造证据链：

| 证据层 | 检查内容 | 可能结论 |
|:---|:---|:---|
| 输入层 | 第 2 个 LLR 是否进入 RTL | 若输入已错，问题在 testbench 或接口。 |
| 地址层 | 第 2 个 LLR 是否写入正确 bank 和地址 | 若地址错，问题在写地址生成。 |
| 运算层 | 第 2 个位置的内部消息是否与定点 golden 一致 | 若消息错，问题在算术或饱和。 |
| 控制层 | 该位置是否经历正确迭代次数 | 若提前停止，问题在早停或 CRC 控制。 |
| 输出层 | 输出顺序是否被重排 | 若内部正确但输出错，问题在读地址或拼接。 |

这个例子说明 bit-exact mismatch 是起点，不是终点。真正的验证价值在于把错误缩小到一个周期、一个地址、一条控制路径或一个算术单元。

## bit-exact、容差和 pass/fail

bit-exact 表示每一位输出都和参考模型一致。对于定点译码器，bit-exact 很重要，因为硬件保存的是固定位宽整数。

| 检查类型 | 适用对象 | 通过标准 |
|:---|:---|:---|
| bit-exact | 定点整数、硬判决比特、CRC 余数 | 每一位完全一致。 |
| 数值容差 | 浮点概率、LLR、块错误率曲线 | 误差在阈值内。 |
| pass/fail | CRC、协议验收、错误路径 | 状态和结果符合预期。 |

不能把三者混用。浮点 LLR 可以用容差；定点 RTL 输出通常要 bit-exact；最终 TB（传输块，Transport Block）是否接受要看 CRC pass/fail 和协议状态。

## 手算例子：最小 bit-exact 对比

假设 golden model 给出 4 个定点 LLR：

$$
\mathbf{g}=[3,-1,0,7]
\tag{3}
$$

RTL 输出：

$$
\mathbf{r}=[3,-1,0,6]
\tag{4}
$$

逐项比较：

| index | golden | RTL | 是否一致 |
|---:|---:|---:|:---:|
| 0 | 3 | 3 | 是 |
| 1 | -1 | -1 | 是 |
| 2 | 0 | 0 | 是 |
| 3 | 7 | 6 | 否 |

即使最终 CRC 可能偶然通过，这个 bit-exact 对比仍然失败。验证不能因为最终 pass 就忽略内部差异，尤其在早期单元测试阶段。

## 最小验证计划

一个 CB 译码器的最小验证计划至少包括：

| 类别 | 用例 | 观察点 |
|:---|:---|:---|
| 接口 | valid/ready backpressure | 不丢输入，不重复输出。 |
| 定点 | 最大/最小 LLR、饱和加法 | 不回绕，符号正确。 |
| 地址 | 解速率匹配、交织/解交织 | 输出顺序与 golden 一致。 |
| 算法 | 固定小向量 | 中间消息或最终硬判决 bit-exact。 |
| CRC | pass/fail 两条路径 | 通过时输出，失败时保留或报错。 |
| 状态机 | reset、timeout、max iteration | 状态转移可解释。 |
| 回归 | 多随机种子 | 失败可复现。 |

## 约束随机与边界案例

约束随机不是“随便乱测”。它是在合法范围内随机选择参数，并确保覆盖关键组合。

| 参数 | 合法约束 | 必测边界 |
|:---|:---|:---|
| CB 长度 | 来自协议或教学范围 | 最小、最大、非对齐长度。 |
| LLR 幅度 | 定点范围内 | 最小值、最大值、0、饱和附近。 |
| 迭代次数 | 1 到最大迭代 | 1 次早停、跑满最大。 |
| backpressure | ready 随机拉低 | 长时间拉低、边界周期拉低。 |
| CRC 结果 | pass/fail | pass 输出、fail retry、fail error。 |

边界案例比随机中间值更容易抓 bug。比如补码最小值、循环缓存回绕点、最后一个 LLR、最后一个 CB、CRC fail 的最后一次迭代，都是高风险点。

## 覆盖率

覆盖率回答的问题是：测试到底碰到了哪些情况。

| 覆盖类型 | 例子 | 价值 |
|:---|:---|:---|
| 代码覆盖 | 哪些 RTL 行和分支执行过 | 发现完全没跑到的逻辑。 |
| 功能覆盖 | 是否测过 CRC pass/fail、max iteration、backpressure | 对齐验证计划。 |
| 状态覆盖 | FSM 每个状态是否进入过 | 防止 error 或 retry 路径未测。 |
| 交叉覆盖 | 长度边界 × CRC fail × backpressure | 捕捉组合场景。 |

覆盖率高不等于没有 bug，但覆盖率低一定说明证据不足。

## 波形调试

波形调试用于回答“错误从哪一拍开始出现”。译码器推荐至少观察：

| 信号 | 目的 |
|:---|:---|
| `state` | 状态机是否按预期转移。 |
| `desc_valid/ready` | descriptor 是否锁存。 |
| `llr_valid/ready/data` | 输入是否丢失或重复。 |
| `addr`/`bank` | 地址和 bank 冲突是否正确处理。 |
| `iter_count` | 是否早停或跑满最大。 |
| `crc_start/done/pass` | CRC 控制是否单次启动并正确采样。 |
| `out_valid/ready` | 输出反压是否保持数据。 |

调试时不要只看最终 `crc_pass=0`。应从 golden mismatch 的第一个 index 或第一个错误周期向前追踪，找到最早分歧点。

## Python 对比片段

```python
def compare_vectors(golden: list[int], dut: list[int]) -> tuple[bool, int | None]:
    """Return pass flag and first mismatch index. Time: O(N), Space: O(1)."""
    if len(golden) != len(dut):
        return False, min(len(golden), len(dut))
    for index, (g, d) in enumerate(zip(golden, dut)):
        if g != d:
            return False, index
    return True, None


ok, index = compare_vectors([3, -1, 0, 7], [3, -1, 0, 6])
assert ok is False
assert index == 3
ok, index = compare_vectors([1, 2, 3], [1, 2, 3])
assert ok is True
assert index is None
print("T5.5_BIT_EXACT_COMPARE_OK")
```

## 浮点仿真方案

| 仿真项 | 方法 | 通过条件 |
|:---|:---|:---|
| 浮点 golden | 固定随机种子生成 LLR | 输出可复现。 |
| 定点转换 | 浮点 LLR 量化 | 与 [[T5.1_fixed_point_numbers_for_LLR|T5.1]] 定点规则一致。 |
| RTL 对比 | dump RTL 输出向量 | bit-exact 或定位首个 mismatch。 |
| 曲线验证 | 多 SNR（信噪比，Signal-to-Noise Ratio）点回归并统计 BLER（块错误率，Block Error Rate） | 曲线单调性和阈值符合预期。 |

浮点仿真提供算法基线，不能替代定点和 RTL 对比。

## 定点化策略

定点验证要把格式写成测试参数：

| 参数 | 必须记录 |
|:---|:---|
| LLR 位宽 | 输入 soft information 的总位宽。 |
| 小数位 | Q 格式缩放。 |
| 舍入方式 | 截断、四舍五入或其他。 |
| 饱和阈值 | 最大/最小整数值。 |
| 内部消息位宽 | 迭代消息或路径度量位宽。 |

如果 golden model 和 RTL 的舍入方式不同，后面所有 bit-exact 对比都会失败。

## 硬件实现映射

| 验证对象 | RTL/专用集成电路关注点 | 证据 |
|:---|:---|:---|
| 接口 | valid/ready、reset、backpressure | 波形和断言。 |
| 存储 | bank 冲突、读写同址、初始化 | 地址 dump 和覆盖率。 |
| 数据通路 | 定点饱和、符号扩展、路径度量 | bit-exact 比较。 |
| 控制 | FSM、早停、错误路径 | 状态覆盖和断言。 |
| 性能 | cycles、stall、iterations | 计数器和回归报告。 |

ASIC（专用集成电路，Application-Specific Integrated Circuit）阶段还要补充门级仿真、时序约束、功耗和面积，但这些属于后续综合与验证模块。

## 验证方法

| 步骤 | 动作 | 产物 |
|:---|:---|:---|
| 1 | 固定测试配置和随机种子 | test manifest。 |
| 2 | 运行 golden model | golden 输出和中间 dump。 |
| 3 | 运行 RTL 仿真 | DUT（被测设备，Device Under Test）输出、波形、日志。 |
| 4 | 执行 bit-exact 对比 | pass/fail 和首个 mismatch。 |
| 5 | 收集覆盖率 | 覆盖率报告。 |
| 6 | 归档证据 | 配置、命令、版本、结果。 |

## 常见错误

| 错误 | 后果 | 修正 |
|:---|:---|:---|
| 只看 CRC pass | 内部错误可能被偶然掩盖。 | 单元阶段必须 bit-exact。 |
| 不记录随机种子 | 失败无法复现。 | 每次回归写入 seed 和配置。 |
| golden model 未版本化 | 参考结果变化无法追踪。 | 记录 git hash 或文件校验。 |
| 只测正常长度 | 边界 bug 漏掉。 | 最小、最大、回绕、非对齐都要测。 |
| 覆盖率只看代码行 | 功能场景未必覆盖。 | 建立功能覆盖点和交叉覆盖。 |

## 工程思考题

1. 为什么 CRC pass 不能替代 bit-exact 对比？
2. golden model 为什么可以慢，但必须清晰可审计？
3. 约束随机和完全随机有什么区别？
4. 波形调试时为什么要找首个 mismatch？
5. 回归报告至少要记录哪些信息？

## 工程思考题参考答案

1. CRC pass 只说明最终候选通过错误检测，不能证明内部每一步和参考模型一致，也可能存在误通过风险。
2. golden model 是证据基准，慢可以接受；如果逻辑不清晰或不可审计，RTL 对齐就没有可信目标。
3. 约束随机在合法参数范围内随机，并强制覆盖关键边界；完全随机可能生成无效输入或漏掉重要组合。
4. 首个 mismatch 最接近根因，越往后错误会扩散，定位成本更高。
5. 配置、随机种子、输入向量、golden 版本、RTL 版本、命令、输出、覆盖率和失败日志。

## 自测题

1. bit-exact 的含义是什么？
2. 哪些对象适合用数值容差而不是 bit-exact？
3. 功能覆盖和代码覆盖有什么区别？
4. CRC fail 的波形调试应观察哪些信号？
5. 为什么边界案例通常比普通随机样本更容易发现 bug？

## 自测题参考答案

1. 每一位输出都和参考模型一致。
2. 浮点 LLR、概率值、BLER 曲线等存在数值误差的对象。
3. 代码覆盖看哪些代码执行过；功能覆盖看验证计划中的场景是否发生过。
4. `state`、LLR 输入、地址、迭代计数、CRC start/done/pass、输出握手等。
5. 边界案例触发溢出、回绕、最后一项、最大迭代、反压等高风险逻辑，普通随机样本不一定碰到。
