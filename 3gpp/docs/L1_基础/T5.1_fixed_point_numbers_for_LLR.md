# T5.1 LLR 处理中的定点数：从浮点可靠度到硬件可保存的有符号数
## 本节学习目标

译码器前端通常先在浮点仿真里使用对数似然比。LLR（对数似然比，Log-Likelihood Ratio）是一个带符号的可靠度数字：本课程约定 LLR 为正表示更像比特 `0`，为负表示更像比特 `1`，绝对值越大表示越可靠。软件仿真可以用 `float` 或 `double` 保存 LLR，但硬件译码器不能无限制地保存实数。寄存器传输级和专用集成电路实现需要把 LLR 变成固定位宽的二进制数。

本节讲 **有符号定点数（signed fixed-point number）**。它不是 LTE 或 NR 协议规定的空口格式，而是接收机实现为了存储、计算和传递软信息所采用的工程表示。

- 解释为什么硬件译码器不能直接保存无限精度浮点 LLR。
- 说清二进制补码、符号位、整数位、小数位和 Q 格式的含义。
- 手算一个 LLR 从浮点到定点整数编码、再从定点整数解码回实数的过程。
- 区分裁剪、量化、舍入和饱和。
- 解释定点位宽过小会怎样影响 Turbo（Turbo 码，Turbo Code）、低密度奇偶校验码和 Polar（极化码，Polar Code）译码。
- 用 Python 做位级检查，确认正数、负数、边界值和饱和值都符合预期。

## 前置知识检查

| 前置项 | 本节需要达到的程度 |
|:---|:---|
| LLR | 知道正负号表示倾向，绝对值表示可靠度。 |
| 二进制整数 | 能看懂 `0b0110` 表示二进制数。 |
| 量化 | 知道连续值需要映射到离散整数。 |
| 裁剪 | 知道过大或过小的值会被限制到某个范围内。 |
| Python | 能读懂列表、函数和 `assert`。 |

如果只记住一句话：定点 LLR 是“把连续可靠度按固定步长量化成有限范围内的有符号整数”，硬件真正保存的是整数码字，不是数学上的实数。

## 资料与协议边界

本节是实现基础课，不是 3GPP 协议精读课。3GPP 规范会规定调制映射、信道编码、速率匹配、冗余版本、循环冗余校验和接收流程相关输入输出，但通常不会规定某个接收机内部必须用 5 bit、6 bit 还是 8 bit 保存 LLR。

协议和本节的关系如下：

| 层次 | 是否由 3GPP 直接规定 | 本节处理方式 |
|:---|:---|:---|
| 调制映射和编码结构 | 是，需查 TS 36.211/36.212/38.211/38.212 | 本节不复现协议表格，只说明 LLR 来自软解调和解速率匹配之后。 |
| LLR 位宽、Q 格式、饱和阈值 | 否，属于接收机实现 | 本节作为工程基础详细讲解。 |
| CRC（循环冗余校验，Cyclic Redundancy Check）pass/fail | 协议规定 CRC 计算和附加，硬件实现负责检查 | 本节只把 CRC 作为定点误差最终影响译码成败的观察点。 |
| RTL（寄存器传输级，Register Transfer Level）/ASIC（专用集成电路，Application-Specific Integrated Circuit）存储结构 | 否，属于实现 | 本节说明位宽、符号扩展和饱和加法对硬件的影响。 |

因此，本节不会把定点格式写成 3GPP 强制要求。后续 LTE Turbo、NR LDPC（低密度奇偶校验码，Low-Density Parity-Check Code）、NR Polar 的协议章节会分别说明 LLR 的来源、排列顺序和软缓存位置；本节只解决“这些 LLR 在硬件中怎样表示和验证”。

## 浮点数与定点数的差别

浮点数像科学计数法：同样 32 bit 可以表达很大范围和很多小数，但加法、比较和截断逻辑复杂。定点数更像带小数点的整数：小数点位置预先固定，硬件只保存一个整数码字。

例如约定步长为 $0.25$，那么实数值和整数码字的关系是：

| 实数 LLR | 定点整数 | 解释 |
|---:|---:|:---|
| $+1.00$ | $+4$ | 因为 $1.00/0.25=4$。 |
| $+0.25$ | $+1$ | 一个最小步长。 |
| $0.00$ | $0$ | 中性软信息。 |
| $-0.50$ | $-2$ | 因为 $-0.50/0.25=-2$。 |

硬件保存的不是 `+1.00` 这个十进制小数，而是整数 `4` 的二进制补码。需要参与运算时，硬件按整数加减；需要解释为 LLR 时，再乘回步长。

## 二进制补码：负数的比特表示

有符号定点数通常使用二进制补码（two's complement）。补码的好处是：加法器不需要为正数和负数设计两套逻辑，同一个二进制加法器就能处理加减。

以 4 bit 有符号整数为例，最高位是符号位。可表示范围是：

$$
-2^{4-1}\le q \le 2^{4-1}-1
\tag{1}
$$

也就是：

$$
-8\le q \le 7
\tag{2}
$$

4 bit 补码的部分取值如下：

| 二进制码 | 解释成无符号 | 解释成补码有符号 |
|:---:|---:|---:|
| `0000` | 0 | 0 |
| `0001` | 1 | 1 |
| `0111` | 7 | 7 |
| `1000` | 8 | -8 |
| `1110` | 14 | -2 |
| `1111` | 15 | -1 |

判断负数的方法是看最高位。若最高位为 `1`，它表示负数；真实数值可以用：

$$
q=u-2^W
\tag{3}
$$

其中 $W$ 是位宽，$u$ 是把同一串比特当无符号数得到的值。例如 `1110` 在 4 bit 中无符号值是 14，所以补码值是：

$$
q=14-2^4=-2
\tag{4}
$$

## Q 格式：整数位与小数位的分配

Q 格式用来说明定点数的小数点位置。本课程采用 `Qm.n` 的教学约定：

- `m` 表示包括符号位在内的整数侧位数。
- `n` 表示小数位数。
- 总位宽 $W=m+n$。
- 缩放因子为 $2^n$。

如果使用 `Q4.2`，总位宽是 6 bit，其中 4 bit 在整数侧，2 bit 在小数侧。硬件保存整数 $q$，解释成实数 $x$ 时：

$$
x=\frac{q}{2^n}
\tag{5}
$$

反过来，浮点 LLR $x$ 量化为整数：

$$
q=\mathrm{round}(x\cdot 2^n)
\tag{6}
$$

`Q4.2` 的步长是：

$$
\Delta=2^{-2}=0.25
\tag{7}
$$

6 bit 补码整数范围为：

$$
-2^{5}\le q \le 2^5-1
\tag{8}
$$

即：

$$
-32\le q \le 31
\tag{9}
$$

换成实数范围：

$$
-8.00\le x \le 7.75
\tag{10}
$$

注意这个范围不是对称的：补码负端多一个值。这是很多饱和逻辑和测试向量容易漏掉的边界。

## 手算例子：LLR 的 Q4.2 编码与解码

假设 LLR 为：

$$
x=-1.75
\tag{11}
$$

使用 `Q4.2`，缩放因子是 $2^2=4$：

$$
q=\mathrm{round}(-1.75\times4)=-7
\tag{12}
$$

6 bit 补码中，$-7$ 的编码可以这样算。先用 $2^6=64$ 加上负数：

$$
u=64-7=57
\tag{13}
$$

57 的 6 bit 二进制是：

```text
111001
```

所以 `Q4.2` 编码为 `111001`。解码时最高位为 `1`，先还原补码整数：

$$
q=57-64=-7
\tag{14}
$$

再除以 4：

$$
x=-7/4=-1.75
\tag{15}
$$

这个例子没有量化误差，因为 $-1.75$ 正好落在 $0.25$ 的网格上。

## 量化误差、舍入和截断

如果 LLR 是：

$$
x=1.37
\tag{16}
$$

使用 `Q4.2`：

$$
x\cdot4=5.48
\tag{17}
$$

整数码字必须是整数。常见策略有三种：

| 策略 | 结果 | 误差特点 |
|:---|---:|:---|
| 向零截断 | $q=5$，解码为 $1.25$ | 简单，但有系统性偏差。 |
| 四舍五入 | $q=5$，解码为 $1.25$ | 平均误差较小。 |
| 向最近偶数舍入 | 视半值规则而定 | 常用于减少统计偏差。 |

若 $x=1.38$，则 $x\cdot4=5.52$，四舍五入得到：

$$
q=6,\quad \hat{x}=6/4=1.5
\tag{18}
$$

量化误差为：

$$
e_q=\hat{x}-x=1.5-1.38=0.12
\tag{19}
$$

量化误差不可避免。工程目标不是消除它，而是在块错误率、面积、功耗和时钟之间找到合适折中。

## 裁剪与饱和

裁剪（clipping）和饱和（saturation）经常一起出现，但含义略有不同：

| 名称 | 发生位置 | 含义 |
|:---|:---|:---|
| 裁剪 | 量化前或接口边界 | 把过大的浮点值限制到允许范围。 |
| 饱和 | 整数运算之后 | 加减结果超过定点范围时固定到最大/最小值。 |

以 `Q4.2` 为例，最大实数是 $7.75$。如果输入：

$$
x=10.0
\tag{20}
$$

不能编码成 6 bit 补码范围内的有效 LLR。裁剪后：

$$
x_{\mathrm{clip}}=7.75
\tag{21}
$$

整数码字为：

$$
q=31
\tag{22}
$$

如果软合并时两个整数 LLR 相加：

$$
q_{\mathrm{old}}=25,\quad q_{\mathrm{new}}=12
\tag{23}
$$

普通整数和是：

$$
q_{\mathrm{sum}}=37
\tag{24}
$$

但 6 bit 补码最大值是 31，所以饱和输出为：

$$
q_{\mathrm{sat}}=31
\tag{25}
$$

如果不做饱和，6 bit 截断会把 37 变成二进制低 6 bit `100101`，解释成补码反而是 $-27$。这会把“非常可靠的 0”变成“非常可靠的 1”，属于灾难性错误。

## Python 位级检查

下面的代码验证 `Q4.2` 的编码、解码和饱和加法。它不是完整译码器，只检查定点表示本身。

```python
def q_range(width: int) -> tuple[int, int]:
    """Return signed two's-complement integer range. Time: O(1), Space: O(1)."""
    return -(1 << (width - 1)), (1 << (width - 1)) - 1


def saturate_int(value: int, width: int) -> int:
    """Saturate an integer to signed width. Time: O(1), Space: O(1)."""
    lo, hi = q_range(width)
    return min(max(value, lo), hi)


def encode_q(x: float, width: int, frac: int) -> int:
    """Encode float to signed fixed-point integer with rounding. Time: O(1), Space: O(1)."""
    return saturate_int(round(x * (1 << frac)), width)


def to_twos_bits(q: int, width: int) -> str:
    """Return two's-complement bit string. Time: O(1), Space: O(1)."""
    if q < 0:
        q = (1 << width) + q
    return format(q, f"0{width}b")


def from_twos_bits(bits: str) -> int:
    """Decode two's-complement bit string. Time: O(1), Space: O(1)."""
    width = len(bits)
    value = int(bits, 2)
    if bits[0] == "1":
        value -= 1 << width
    return value


def decode_q(q: int, frac: int) -> float:
    """Decode signed fixed-point integer to float. Time: O(1), Space: O(1)."""
    return q / float(1 << frac)


width = 6
frac = 2
q = encode_q(-1.75, width, frac)
bits = to_twos_bits(q, width)
assert q == -7
assert bits == "111001"
assert from_twos_bits(bits) == -7
assert decode_q(q, frac) == -1.75
assert encode_q(10.0, width, frac) == 31
assert saturate_int(25 + 12, width) == 31
print("T5.1_FIXED_POINT_Q42_OK")
```

## 浮点仿真方案

| 仿真项 | 输入 | 检查项 | 通过标准 |
|:---|:---|:---|:---|
| 编码/解码往返 | `[-1.75, -0.5, 0, 0.25, 7.75]` | 定点整数和解码实数 | 网格点无误差。 |
| 量化误差 | 随机 LLR | `decode(encode(x))-x` | 误差绝对值不超过半个步长，裁剪区除外。 |
| 饱和加法 | 接近边界的正负整数 | 输出是否固定在上下限 | 不发生补码回绕。 |
| 符号一致性 | 正负 LLR | 硬判决方向 | 正数仍判 `0`，负数仍判 `1`。 |

建议先仅测试定点工具函数，再把它接入软解调、HARQ（混合自动重传请求，Hybrid Automatic Repeat Request）合并和译码器输入。这样出错时能区分“定点格式错”和“译码算法错”。

## 定点化策略

定点策略不是单个参数，而是一组接口约定：

| 决策项 | 常见选择 | 工程影响 |
|:---|:---|:---|
| 输入 LLR 位宽 | 5-8 bit 常见 | 位宽越大，soft buffer 面积越大。 |
| 小数位 | 1-3 bit 常见 | 小数位越多，弱 LLR 分辨率越好，但整数范围变小。 |
| 裁剪阈值 | 对称或按补码范围 | 影响高可靠 LLR 是否过早饱和。 |
| 舍入方式 | 截断、四舍五入、随机舍入 | 影响统计偏差和可复现性。 |
| 内部消息位宽 | 通常大于输入 LLR | 迭代译码中消息相加更容易溢出。 |

一个实用原则是：接口位宽先满足存储和带宽，内部累加位宽再满足迭代和软合并。不要把所有节点都强行使用同一个位宽，否则很容易在校验节点、路径度量或外信息累加处饱和。

## RTL/ASIC 映射

定点 LLR 在硬件中会落到几个具体模块：

| 模块 | 关键逻辑 | 风险 |
|:---|:---|:---|
| Quantizer | 浮点或高精度输入转定点整数 | 舍入和裁剪不一致导致 bit-exact 失败。 |
| Soft buffer | 静态随机存取存储器保存定点 LLR | 位宽直接决定面积和带宽。 |
| Saturating adder | HARQ 合并和迭代消息相加 | 回绕会造成符号翻转。 |
| Sign extension | 不同位宽之间转换 | 符号位扩展错误会把负数变正数。 |
| Histogram counter | 统计饱和次数和幅度分布 | 没有观测点时性能退化难定位。 |

SystemVerilog 风格接口片段如下：

```systemverilog
// @Purpose: Signed fixed-point LLR saturating add.
// @Clock: comb path inside decoder datapath.
// @Reset: no state.
// @Width: IN_W includes sign bit; OUT_W includes sign bit.
module llr_sat_add #(
  parameter int IN_W  = 6,
  parameter int OUT_W = 6
) (
  input  logic signed [IN_W-1:0]  a_i,
  input  logic signed [IN_W-1:0]  b_i,
  output logic signed [OUT_W-1:0] y_o
);
  localparam logic signed [OUT_W-1:0] MAX_Q = {1'b0, {(OUT_W-1){1'b1}}};
  localparam logic signed [OUT_W-1:0] MIN_Q = {1'b1, {(OUT_W-1){1'b0}}};

  logic signed [OUT_W:0] sum_ext;

  always_comb begin
    sum_ext = $signed(a_i) + $signed(b_i);
    if (sum_ext > $signed(MAX_Q)) begin
      y_o = MAX_Q;
    end else if (sum_ext < $signed(MIN_Q)) begin
      y_o = MIN_Q;
    end else begin
      y_o = sum_ext[OUT_W-1:0];
    end
  end
endmodule
```

这段代码表达结构，不作为综合签核代码。真实 RTL 还要检查参数合法性、时序路径、lint、综合工具对 signed 比较的解释和测试平台覆盖。

## 验证方法

| 层级 | 用例 | 预期 |
|:---|:---|:---|
| 单元测试 | 所有边界码字：最小值、最大值、-1、0、+1 | 编码/解码一致。 |
| 单元测试 | 正溢出和负溢出加法 | 输出饱和值，不回绕。 |
| 随机测试 | 随机浮点 LLR 量化 | 误差在半步长内或被正确裁剪。 |
| 集成测试 | 接入 HARQ soft combining | 多次合并后饱和计数可解释。 |
| 链路测试 | 浮点 vs 定点 BLER（块错误率，Block Error Rate）曲线 | 定点损失在设计阈值内。 |

验收时不能只看某个样本输出正确。至少要覆盖全部边界码字，因为补码边界往往是硬件错误最集中的地方。

## 常见错误

| 错误 | 后果 | 修正 |
|:---|:---|:---|
| 把补码当无符号数解释 | 负 LLR 变成大正数。 | 所有接口标注 signed，测试最高位为 1 的样本。 |
| 加法后直接截断 | 溢出回绕，符号可能翻转。 | 使用饱和加法。 |
| 小数位没有写入接口文档 | 不同模块对同一整数解释不同。 | descriptor 或设计规格中固定 Q 格式。 |
| 浮点模型和 RTL 舍入规则不同 | bit-exact 对比失败。 | Python/C/RTL 使用同一舍入定义。 |
| 只测正常范围 | 边界饱和 bug 漏掉。 | 专门测最大、最小和超范围输入。 |

## 工程思考题

1. 为什么 6 bit 补码的整数范围是 `[-32,31]`，不是 `[-31,31]`？
2. `Q4.2` 中整数码字 `-7` 表示的实数是多少？
3. 为什么定点加法不能简单保留低 6 bit？
4. LLR 位宽变大一定会提升最终 BLER 吗？
5. 为什么定点格式不属于 3GPP 空口协议强制内容？

## 工程思考题参考答案

1. 补码最高位权重为 $-2^{W-1}$，正端最大值为 $2^{W-1}-1$，因此负端多一个值。
2. `Q4.2` 的缩放因子是 4，所以 $-7/4=-1.75$。
3. 保留低位会发生回绕，例如超过最大正数后可能变成负数，直接反转 LLR 方向。
4. 不一定。位宽过大增加面积和带宽，性能还受算法、迭代次数、信道估计和速率匹配影响；超过某个点收益会变小。
5. 3GPP 规定空口处理规则和比特级协议关系，接收机内部 LLR 位宽是厂商实现选择，只要最终行为满足协议互操作和性能要求即可。

## 自测题参考答案

1. `1111` 作为 4 bit 补码表示 $15-16=-1$。
2. `Q4.2` 有 2 个小数位，步长是 $2^{-2}=0.25$。
3. $6/4=1.5$。
4. 最大正整数是 31，最小负整数是 -32。
5. 输出应饱和为 31，而不是回绕成负数。
6. 因为不同位宽之间传递负数时必须复制符号位；若零扩展，负 LLR 会被解释成大正数，直接改变硬判决方向。
