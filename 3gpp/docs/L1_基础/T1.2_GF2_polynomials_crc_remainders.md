# T1.2 GF(2) 多项式与循环冗余校验余数：整除规则与错误检测
## 本节学习目标

上一节已经讲过：GF(2) 是只含 `0` 和 `1` 的二元有限域，加法就是异或，减法和加法一样。本节在这个基础上解决一个更具体的问题：一串比特怎样变成一个可以计算余数的多项式，为什么这个余数能用来做错误检测。


- 把一个比特串翻译成 GF(2) 多项式。
- 解释生成多项式是什么，它为什么决定循环冗余校验规则。
- 手算一个小型循环冗余校验：补零、长除法、取余数、附加余数、接收端检查。
- 说清“校验通过”和“数据绝对正确”不是一回事。
- 用一段短 Python 代码复核手算结果。

**CRC（循环冗余校验，Cyclic Redundancy Check）** 从本节开始成为主角。标题里已经出现过它的缩写；从这里开始，后文会直接使用 CRC。

| 名称 | 先这样理解 |
|:---|:---|
| 循环冗余校验 | 一种错误检测方法。 |
| CRC | 循环冗余校验的英文缩写，后文会反复使用。 |
| 本节核心 | 发送端加一小段校验比特，接收端用同一条规则重新检查。 |

如果检查失败，说明错误被发现了；如果检查通过，只能说明这条规则没有发现错误。

## 前置知识检查

如果下面几个问题还不熟，建议先回到 [[T1.1_GF2_binary_arithmetic_for_decoders|T1.1]]：

| 问题 | 需要达到的程度 |
|:---|:---|
| GF(2) 里 `1 + 1` 等于多少？ | 等于 `0`，因为 GF(2) 加法只保留奇偶性。 |
| GF(2) 里减法和加法是什么关系？ | 它们相同，所以“减掉”可以用异或实现。 |
| 比特串 `1011` 怎么写成多项式？ | $D^3 + D + 1$。 |
| 多项式除法的第一步是什么？ | 最高项对齐，然后逐位异或。 |

本节不会假设你学过抽象代数或通信协议。只需遵循一个原则：CRC 长除法里的每次“相减”，实际都是对齐后的异或（XOR, exclusive OR）。

## 奇偶校验的检测局限

先从上一节的奇偶校验说起。假设发送方发送：

```text
1 0 1
```

这串里有两个 `1`，是偶数。若仅用偶校验，可附加一个 `0`：

```text
1 0 1 0
```

接收端数一数 `1` 的个数，仍然是偶数，就认为奇偶校验通过。

但问题来了：如果传输中两个比特同时翻转，比如第一个 `1` 变成 `0`，第二个 `0` 变成 `1`：

```text
0 1 1 0
```

现在仍然有两个 `1`。奇偶性没有变，简单奇偶校验发现不了这个错误。

这说明只数 `1` 的个数还不够。还需校验规则能感知“这些 `1` 在什么位置”。GF(2) 多项式正好能做到这一点：每个位置对应一个 $D$ 的幂，位置不同，项也不同。

## CRC 的核心想法

CRC 的核心不是背多项式表，而是下面这句话：

> 发送端选择一个固定的生成多项式，把消息除以它，得到余数；再把余数附加到消息后面，使完整比特串能被同一个生成多项式整除。

这里有两个新词。

生成多项式就是 CRC 的规则。它像普通除法里的“除数”，但它不是随便选的。不同生成多项式会产生不同长度的余数，也会影响能检测哪些错误模式。

余数就是发送端附加的校验比特。接收端拿到完整比特串后，用同一个生成多项式再除一次。如果余数为 `0`，说明这串比特满足这条 CRC 规则；如果余数不为 `0`，说明错误被这条规则检测到了。

暂勿直接查阅协议中的 CRC24、CRC16 或 CRC11。本节用一个很小的教学多项式把机制算清楚。真实协议多项式会更长，但计算原则不变。

## 比特串到多项式的映射

把比特串写成多项式的规则是：从左到右，最高位对应最高次幂；某一位是 `1`，就保留对应项；某一位是 `0`，就没有这一项。

例如：

```text
1101
```

四个比特对应 $D^3, D^2, D^1, D^0$，所以：

$$
1101 \quad \leftrightarrow \quad D^3 + D^2 + 1
\tag{1}
$$

再看生成多项式：

```text
1011
```

它对应：

$$
g(D)=D^3 + D + 1
\tag{2}
$$

这里的 $g(D)$ 读作“生成多项式”。最高次数是 3，所以 CRC 余数最多有 3 个比特。后面会看到，发送端要先给消息末尾预留 3 个位置。

很多教材会把变量写成 $x$，例如 $g(x)$。本课程用 $D$，是为了和 3GPP（第三代合作伙伴计划，3rd Generation Partnership Project）协议里常见的写法保持一致。只需知道 $D$ 和 $x$ 在这里都只是“位置标记”。

## 发送端补零与余数位置预留

CRC 余数需要放在消息后面。生成多项式最高次数为 3，余数就需要 3 个比特位置。发送端先把消息后面补 3 个 `0`，这是在给余数预留位置。

消息是：

```text
1101
```

补 3 个 `0` 后变成：

```text
1101000
```

多项式写法是把消息乘以 $D^3$：

$$
(D^3 + D^2 + 1)D^3 = D^6 + D^5 + D^3
\tag{3}
$$

注意，补零后的 `1101000` 不是最终发送结果。它只是用来计算余数的临时工作串。

## 手算 CRC 长除法

现在用生成多项式 `1011` 去除补零后的工作串 `1101000`。

CRC 长除法只有两个动作：

- 当前最高位是 `1`：把生成多项式对齐到这里，然后逐位异或。
- 当前最高位是 `0`：跳过，继续看下一位。

逐步计算如下。

**第 1 步：从最左边开始。**

当前前四位是 `1101`，最高位是 `1`，所以和 `1011` 异或：

```text
1101000
1011
----
0110000
```

异或后最左边变成 `0`，工作串是：

```text
0110000
```

**第 2 步：跳过最左边的 0，在下一位对齐。**

从第 2 个位置开始看到 `1100`，继续和 `1011` 异或：

```text
0110000
 1011
 ----
0011100
```

工作串变成：

```text
0011100
```

**第 3 步：再跳过前两个 0，在第 3 个位置对齐。**

当前位置开始是 `1110`，和 `1011` 异或：

```text
0011100
  1011
  ----
0001010
```

工作串变成：

```text
0001010
```

**第 4 步：再对齐一次。**

当前位置开始是 `1010`，和 `1011` 异或：

```text
0001010
   1011
   ----
0000001
```

现在前面已经没有足够长度继续除，最后 3 个比特就是余数：

```text
001
```

所以本例的 CRC 余数是：

$$
R = 001
\tag{4}
$$

发送端最终发送“消息 + 余数”：

```text
1101 001
```

也就是：

$$
C = 1101001
\tag{5}
$$

## 接收端零余数检查

发送端附加的不是任意 3 个比特，而是刚刚算出来的余数。它的作用是让完整码字 `1101001` 能被同一个生成多项式 `1011` 整除。

接收端用 `1011` 再除一次：

```text
1101001 / 1011
```

得到的余数应该是：

```text
000
```

用公式写就是：

$$
C(D) \bmod g(D) = 0
\tag{6}
$$

### 附加余数后可整除性的证明

上面是动手算出来的结果。这里从代数角度证明它不是巧合，而是 GF(2) 多项式的必然性质。

发送端做 CRC 长除法时，补零后的消息除以生成多项式会得到一个商和一个余数：

$$
D^r M(D) = Q(D)\, g(D) + R(D)
\tag{6a}
$$

其中 $Q(D)$ 是商，$R(D)$ 是余数（次数低于 $g(D)$ 的次数 $r$）。发送端接着把余数 $R(D)$ 附到消息后面，构成完整码字：

$$
C(D) = D^r M(D) + R(D)
\tag{6b}
$$

把式 (6a) 代入式 (6b)：

$$
\begin{aligned}
C(D) &= \bigl[Q(D)\, g(D) + R(D)\bigr] + R(D)  \\
     &= Q(D)\, g(D) + \bigl[R(D) + R(D)\bigr]
\end{aligned}
\tag{6c}
$$

关键一步在 GF(2) 里：任意多项式加上它自己等于零，因为相同比特异或结果就是 0。

$$
R(D) + R(D) = 0
\tag{6d}
$$

所以：

$$
C(D) = Q(D)\, g(D)
\tag{6e}
$$

换言之，$C(D)$ 刚好是 $g(D)$ 的整数倍。因此接收端用同一个 $g(D)$ 去除时，余数必然为 0。这个结论不依赖具体消息内容，只要发送端严格按"补零 → 除法取余 → 附加余数"的步骤构造码字，$C(D)$ 就能被 $g(D)$ 整除。

用本节的具体数字带入验证：

- $M(D) = D^3 + D^2 + 1$（消息 `1101`）
- $g(D) = D^3 + D + 1$（生成多项式 `1011`，$r = 3$）
- 补零后：$D^3 M(D) = D^6 + D^5 + D^3$（`1101000`）
- 长除法得到：$Q(D) = D^3 + D^2 + D$，$R(D) = 1$（余数 `001`）
- 码字：$C(D) = D^6 + D^5 + D^3 + 1$（`1101001`）
- 验证：$(D^3 + D^2 + D)(D^3 + D + 1) = D^6 + D^5 + D^3 + 1 = C(D)$ ✓

如果把这里的 $+$ 全部换成 XOR，就是硬件里实际执行的逻辑：**余数附加到消息后面，接收端再除一次，余数必定归零**。

如果传输中有一个比特翻转，例如收到：

```text
1111001
```

再用 `1011` 去除，余数会变成非零值。非零余数的意思是：这串比特不满足原来的生成多项式约束，所以错误被检测到了。

但要特别注意：CRC 通过不等于绝对无错。它只能说明“在这条生成多项式规则下，没有检测到错误”。如果某种错误模式刚好也是生成多项式的倍数，CRC 也可能漏检。

## 例题：完整发送端和接收端过程

**题目：** 消息 `1101`，生成多项式 `1011`。求 CRC 余数、发送码字，并检查接收端余数。

**解：**

1. 生成多项式 `1011` 最高次数为 3，所以先补 3 个 `0`：

```text
1101 -> 1101000
```

2. 用 `1011` 除 `1101000`，得到余数：

```text
001
```

3. 发送码字为：

```text
1101 001
```

4. 接收端用同一个 `1011` 除 `1101001`，余数为：

```text
000
```

所以，如果接收端收到的就是 `1101001`，这条 CRC 检查通过。

## 生成多项式、余数与错误模式

CRC 的生成多项式不是一个装饰性名字，而是整条错误检测规则本身。给定同一条消息，换一个生成多项式，余数通常会变；给定同一个接收码字，换一个生成多项式，检查结果也可能变。

可以把接收端 CRC 检查看成下面这条关系：

$$
r(D)=C(D)\bmod g(D)
\tag{7}
$$

这个公式回答的问题是：接收端拿到的完整码字多项式 $C(D)$，除以生成多项式 $g(D)$ 后的余数 $r(D)$ 是什么。若 $r(D)=0$，CRC 检查通过；若 $r(D)\ne 0$，CRC 检查失败。

发送端构造码字时会让：

$$
C(D)=D^rM(D)+P(D)
\tag{8}
$$

这里 $M(D)$ 是消息多项式，$r$ 是生成多项式最高次数，$P(D)$ 是要附加的 CRC 余数。前面的“补零”就是乘以 $D^r$，给 $P(D)$ 留出 $r$ 个低次位置。补零不是因为消息真的多了几个 `0`，而是为了计算稍后要填进去的余数位置。

如果传输中有比特翻转，接收端看到的是：

$$
\hat{C}(D)=C(D)+E(D)
\tag{9}
$$

$E(D)$ 是错误模式：哪些位置翻转，就在哪些幂次上有 `1`。接收端重新计算：

$$
\hat{C}(D)\bmod g(D)
=
\left(C(D)+E(D)\right)\bmod g(D)
\tag{10}
$$

因为发送端构造的 $C(D)$ 本来能被 $g(D)$ 整除，所以检测是否失败，本质上取决于：

$$
E(D)\bmod g(D)
\tag{11}
$$

这一步说明了 CRC 的能力边界：如果错误模式 $E(D)$ 不是 $g(D)$ 的倍数，余数就非零，错误会被检测到；如果某个错误模式刚好是 $g(D)$ 的倍数，CRC 会漏检。真实协议选择 CRC 多项式时，会考虑常见错误模式、长度和检测能力；本节不展开多项式设计理论，但必须知道“CRC 通过不等于绝对无错”的数学原因就在这里。

从接收端工程角度看，CRC 余数还有三个容易出错的接口点：

| 接口点 | 错误表现 | 诊断方式 |
|:---|:---|:---|
| 消息位顺序 | 同一比特串在软件和硬件中余数不同。 | 用短消息 golden vector 比较逐步余数。 |
| 余数附加顺序 | 发送端构造的码字在接收端不过检。 | 同时打印 message、remainder、codeword。 |
| filler 或 padding 处理 | 分段后某些边界块总失败。 | 分离“协议填充位”和“CRC 计算输入位”。 |

后续 [[T3.1_LTE_NR_CRC_families|T3.1]] 会把这些接口点放回 TB（传输块，Transport Block）CRC、码块CRC 和控制信息 CRC；[[T3.2_transport_code_block_filler_bits|T3.2]]-[[T3.5_NR_Polar_segmentation_crc|T3.5]] 会继续讨论 filler bit 和分段对 CRC 输入范围的影响。

## Python 校验片段

下面这段代码用列表表示比特串，例如 `[1, 1, 0, 1]` 表示 `1101`。可将其粘进 Python 解释器，或放进临时文件运行。

```python
def gf2_div_remainder(dividend: list[int], divisor: list[int]) -> list[int]:
    """Return the GF(2) polynomial division remainder."""
    if not divisor or divisor[0] != 1:
        raise ValueError("divisor must be non-empty and start with 1")

    work = dividend[:]
    r = len(divisor) - 1
    last_start = len(work) - len(divisor)

    for i in range(last_start + 1):
        if work[i] == 1:
            for j, bit in enumerate(divisor):
                work[i + j] ^= bit

    return work[-r:] if r else []


def crc_encode(message: list[int], generator: list[int]) -> list[int]:
    """Append CRC remainder to message."""
    r = len(generator) - 1
    padded = message + [0] * r
    remainder = gf2_div_remainder(padded, generator)
    return message + remainder


def crc_check(codeword: list[int], generator: list[int]) -> bool:
    """Check whether codeword has zero CRC remainder."""
    remainder = gf2_div_remainder(codeword, generator)
    return all(bit == 0 for bit in remainder)


message = [1, 1, 0, 1]
generator = [1, 0, 1, 1]
codeword = crc_encode(message, generator)

print("codeword:", "".join(str(b) for b in codeword))
print("check:", crc_check(codeword, generator))
print("bad check:", crc_check([1, 1, 1, 1, 0, 0, 1], generator))
```

期望输出：

```text
codeword: 1101001
check: True
bad check: False
```

这里的 `bad check` 把第二个比特翻转了，所以 CRC 检查失败。

## 和 3GPP 协议的关系

这一节的 `1011` 是教学用生成多项式，不是 LTE（长期演进，Long Term Evolution）或 NR（新空口，New Radio）的协议多项式。

3GPP 是制定移动通信标准的组织。LTE 是 4G 移动通信技术体系，NR 是 5G 移动通信技术体系。二者的物理层信道编码协议都会规定 CRC 的生成多项式和附加方式。它们和本节小例子的关系是：计算思想相同，但生成多项式更长、使用场景更多、协议条件更复杂。

本地 Rel-19 资料入口如下：

| 系统 | 协议依据 | 本地路径 | 本节采用程度 |
|:---|:---|:---|:---|
| LTE | 技术规范（TS, Technical Specification）36.212 Rel-19 `36212-j30` §5.1.1 CRC calculation | `3GPP_Rel19/processed/TS_36.212_36212-j30/content.md`，`sections.jsonl` | 已核对章节入口；`content.md` 中能看到 `gCRC24A(D)`、`gCRC24B(D)`、`gCRC16(D)`、`gCRC8(D)` 以及“余数为 0”的系统形式描述。 |
| NR | TS 38.212 Rel-19 `38212-j30` §5.1 CRC calculation | `3GPP_Rel19/processed/TS_38.212_38212-j30/content.md`，`sections.jsonl` | 已核对章节入口；`content.md` 中能看到 CRC calculation、generator polynomial 和 remainder equal to 0 的描述，但多项式公式抽取不完整。 |

因此，本节只把 3GPP 作为协议入口，不复现完整 LTE/NR CRC 家族。表中列出的 `gCRC24A(D)`、`gCRC24B(D)`、`gCRC16(D)` 和 `gCRC8(D)` 只记录名称线索，不复现生成多项式表达式；具体多项式以 [[T3.1_LTE_NR_CRC_families|T3.1]] 的本地重建为准。完整协议 CRC 多项式、传输块 CRC、码块 CRC、控制信息 CRC、CRC 掩码和附加规则，会在后续协议精读章节中结合原始 Word、公式可扩展标记语言（XML, Extensible Markup Language）和表格继续核验。

## 常见错误

| 错误 | 为什么错 | 正确做法 |
|:---|:---|:---|
| 把 CRC 长除法当普通十进制除法 | GF(2) 里没有借位，减法就是异或。 | 每次只做“对齐后逐位异或”。 |
| 忘记补零 | 不补零就没有给余数预留位置。 | 生成多项式最高次数为 $r$，就先补 $r$ 个 `0`。 |
| 把教学多项式当成协议多项式 | 本节 `1011` 只为手算方便。 | 协议多项式必须查 TS 36.212/38.212。 |
| 认为 CRC 通过就是绝对无错 | CRC 可能漏检某些错误模式。 | 说“未检测到错误”，不要说“证明无错”。 |
| 余数附加顺序混乱 | 顺序错会导致接收端检查失败。 | 按本节约定把余数按计算结果顺序附加在消息后。 |

## 自测题

先自己算，再看参考答案。

1. 消息 `1010`，生成多项式 `1011`。补零后的工作串是什么？
2. 生成多项式 `1011` 的最高次数是多少？CRC 余数长度是多少？
3. 为什么接收端要用同一个生成多项式检查？
4. CRC 通过能不能说“数据一定正确”？为什么？

## 自测题参考答案

1. `1010000`。因为生成多项式最高次数为 3，要在消息后补 3 个 `0`。
2. 最高次数是 3，CRC 余数长度是 3 bit。
3. 因为发送端就是按这个生成多项式构造余数的。接收端换一个生成多项式，检查规则就变了，通过/失败没有意义。
4. 不能。CRC 通过只表示这条规则没有检测到错误；某些错误模式仍可能让余数为 0。
