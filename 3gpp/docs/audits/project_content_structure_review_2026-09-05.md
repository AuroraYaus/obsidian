先给结论：这个项目已经具备相当成熟的知识库治理框架，规则、记忆、自动审计、术语管理、讲义分层和协议阅读路线都比较完整。当前最大的不足，不是“没有内容”，而是三件事混在了一起：

1. 文档体系已经接近成型；
2. 算法仿真和工程实现仍有大量模板化、计划化内容；
3. README、入口索引、审计台账中的“完成状态”和真实完成度没有完全同步。

因此，项目目前更准确的定位应该是：

> 3GPP LTE/NR 译码与接收机方向的系统化学习与工程设计知识库；文档和验证框架较完整，但真实译码器仿真、定点模型、RTL 和 ASIC 签核尚未完成。

本报告记录 2026-09-05 对项目规则、记忆、目录、讲义、概念笔记、工具、审计台账和工作区状态的只读检视结果。本轮没有修改原有讲义或规则文件。

## 一、检视范围和方法

本次检视读取和比对了以下内容：

- 根目录 `CLAUDE.md`、README 和 `docs/rules/用户全局规则.md`；
- `3gpp/CLAUDE.md`、`3gpp/合规与遵从.md`、`3gpp/项目规则与记忆索引.md`；
- `3gpp/.claude/rules/documentation.md`；
- `3gpp/docs/memory/` 和 `3gpp/docs/audits/lessons/`；
- L0-L3 入口、讲义、概念笔记和主要审计台账；
- `3gpp/sim/`、`3gpp/tools/`、`3gpp/tests/` 的实际文件；
- frontmatter、标题、术语、链接、Mermaid、LaTeX、图像资产和讲义深度审计。

审阅原则是把“机械质量门槛”“教学内容质量”“真实工程证据”分开判断。文本信号统计用于发现结构不一致，不把单一信号直接当成内容缺陷。

## 二、规则和记忆体系评估

### 2.1 已经形成的治理能力

项目规则已经覆盖从写作到工程证据的完整链路：

- 讲义、概念笔记、入口文件有明确的 frontmatter 分类；
- L0-L3 分层和 T/TX 编号体系明确；
- 讲义要求学习目标、前置知识、协议边界、算法、仿真、定点、RTL/ASIC、验证、常见错误、练习和参考文献；
- 概念首现必须包含中文定义、英文术语和 wikilink；
- 正文不得记录代码调试过程或中间运行结果；
- NumPy 示例必须先本地运行并通过断言；
- Mermaid、SVG 和图片资产具有语法、几何、渲染和台账要求；
- 新增或修改内容需要同步入口、术语、资产、计数、README 和记忆；
- 用户纠错必须沉淀为规则、工具或经验教训；
- 记忆在项目内部和会话镜像中双份维护。

这说明项目不再只是普通 Obsidian 笔记，而是一个带有质量门禁、证据追踪和持续改进机制的知识库工程。

### 2.2 规则体系本身的不足

规则数量较多、历史记录较长，部分规则和当前资产状态之间已经出现时间差。主要表现为：

- 旧台账仍保留历史数量和旧编号；
- 审计工具会把规则自身的示例识别为违规内容；
- 同一语义存在多个等价标题，自动审计难以判断；
- “每篇讲义必须有 NumPy、图、小结、协议证据表”等要求，在工具和正文中的定义还不完全一致；
- “500 行”这一指标容易被误解为硬性篇幅要求，而规则实际又禁止用习题或重复内容凑行数。

后续应把规范拆为三层：硬性阻断规则、建议性质量指标、需要人工复核的风险触发器。

## 四、讲义格式总体评估

### 4.1 格式基线的优点

156 篇讲义整体已经形成比较稳定的共同骨架：

- 统一 frontmatter；
- 明确学习目标；
- 前置知识检查；
- 资料与协议边界；
- 表格化表达；
- 参考文献；
- 算法、协议、工程和验证之间有较强关联。

主要覆盖情况如下：

| 格式或内容信号 | 覆盖情况 | 评价 |
|---|---:|---|
| 统一 frontmatter | 156/156 | 很好 |
| 学习目标 | 156/156 | 很好 |
| 前置知识 | 156/156 | 很好 |
| 资料与协议边界 | 156/156 | 很好 |
| 参考文献 | 156/156 | 很好 |
| 表格 | 156/156 | 很好 |
| 显式协议 TS 引用 | 153/156 | 基本完整 |
| NumPy 或代码信号 | 约 120/156 | 存在明显缺口 |
| 教学图信号 | 约 140/156 | 约 16 篇需人工确认 |
| 500 行以上 | 约 88/156 | 长度差异较大 |
| 显式“协议证据表”标题 | 约 76/156 | 标题命名不统一 |
| 显式“伪代码”标题 | 约 57/156 | 算法段落不易统一定位 |

| 小结/验收/收束段 | 约 96/156 | 缺口较明显 |

以上数字是文本信号统计。某篇讲义即使没有命中关键词，也可能通过“数值走读”“执行与证据记录”或 ASCII 图表达了相应内容；但统计仍然能够有效暴露规范落地不一致的问题。

### 4.2 讲义格式的系统性问题

#### A. 收束段缺失

L2 中约 42 篇没有可识别的 `## 小结`、`## 本节验收` 或等价收束标题，主要集中在：

- T6 LTE Turbo；
- T7 LTE 接收侧；
- T8 NR LDPC；
- T9 NR LDPC 接收侧；
- T10 NR Polar；
- T11 对比系列。

L3 中约 18 篇缺少明确收束段，重点是：

- T17.2-T17.5；
- T18.2-T18.6；
- T19.1-T19.6；
- T20.1-T20.6。

工程讲义常常有“验收表”和“证据记录”，但这不能完全替代教学收束。学习者仍需要知道本节掌握了什么、哪些结论已被验证、哪些只是设计假设、下一步应该读什么。

建议统一采用：

```markdown
## 小结

## 本节验收

## 下一步
```

#### B. 教学图覆盖不完整

约 16 篇讲义没有检测到 Mermaid、SVG、PNG、PlantUML 等教学图信号。

重点文件包括：

- L1：T1.1-T1.6、T5.5、TX4；
- L2：T7.4、T7.6、T8.0、T9.0、T9.8、T16.3、T16.4；
- L3：T23.2。

需要逐篇确认是否使用了 ASCII 图或表格。如果没有等价图示，应补充能够解释数据流、状态转移、译码迭代或工程证据关系的教学图，并完成资产登记和渲染验证。

#### C. 500 行指标落实不均

约 68 篇讲义少于 500 行，短篇集中在 L1 的早期基础系列、L2 的 T6-T11 基础讲义、L2 的部分 T14-T16，以及 L3 的 T22/T23。

500 行不应被当成机械补字数的目标。建议把它作为人工深度复查触发器，重点检查：

- 是否有足够的数值实例；
- 是否覆盖边界条件和失败模式；
- 是否存在可运行验证；
- 是否有精确协议锚点；
- 是否能连接到真实实现和验收指标。

#### D. NumPy 验证覆盖不足

约 36 篇讲义没有明显 NumPy 或可运行代码信号。缺口集中在：

- L1 T2.0、T2.7、T2.8、T2.10-T2.12、T2.17-T2.19；
- L2 T6.1-T6.8、T7.2、T7.5、T8.7、T9.0、T9.7、T9.8、T10.9、T11.4-T11.5；
- L3 T17.2-T17.5、T18.2-T18.6、T19.1-T19.5、T20.1。

其中一部分是计划、架构或工程管理型讲义，使用伪代码和验收命令是合理的；但项目入口不应笼统宣称所有讲义都含有可运行 NumPy 验证。更合理的分层是：

1. 理论讲义：公式、手算和反例即可；
2. 算法讲义：必须有最小可运行参考模型；
3. 工程讲义：必须有可执行接口、性能或验收脚本。

#### E. 协议证据表标题不统一

几乎所有讲义都有协议边界、协议资料或协议表格，但只有约一半明确使用“协议证据表”标题。

建议统一标题，或者在审计工具中定义可接受的等价标题集合，避免“内容存在但工具判定缺失”。

#### F. 伪代码、例题和小结命名不统一

不同讲义使用“算法流程”“处理步骤”“数值走读”“案例分析”“执行与证据记录”等不同名称。内容并非一定缺失，但读者和工具都难以快速判断结构是否完整。

建议统一最小结构：

```markdown
## 算法流程

## 伪代码

## 数值例题或案例走读

## 常见错误

## 小结
```

## 五、重点讲义和系列问题

### 5.1 T2.6 术语首现

术语首次使用审计唯一发现的问题位于：

`3gpp/docs/L1_基础/T2.6_from_resource_grid_to_decoder_LLR.md:64`

工具报告：

```text
PUSCH: 真首现 L64 = CHECK(中文紧跟)
```

```text
PUSCH（物理上行共享信道，Physical Uplink Shared Channel）
```

### 5.2 T23.1-T23.3 协议边界不足

以下文件缺少显式协议 TS 引用：

- `T23.1_synthesis_backend_physical.md`；

- `T23.3_sw_hw_co_design.md`。

这些主题可以引用 IEEE、EDA 文档或项目工程规范，但仍应明确区分：

- 3GPP 直接规定的内容；
- 通用 ASIC 方法学；
- 项目内部的设计决策；
- 尚未验证的工程假设。

### 5.3 T22/T23 工程讲义深度

T22/T23 多数讲义约 260-310 行。问题不在于篇幅本身，而在于工程主题需要更多可复现证据：

- 面积、功耗和时序目标；
- 误差预算；
- 工具链执行命令；
- 失败案例；
- 证据文件格式；
- 结果如何回填到项目台账。

| 维度 | 当前判断 |

## 十、审计工具和测试体系的不足

### 10.1 链接审计误报

`audit_link_integrity.py` 会把 memory 文件中用于讲解错误链接的示例，例如 `[[wikilink]]`、`[[...]]` 和 `[[..]]`，识别成真实死链。

建议采用以下任一方案：

- 工具忽略代码块和示例块；
- memory 中的示例统一改写为不触发解析的形式；

### 10.2 圈号字符审计自指误报

### 10.3 测试命令工作目录不友好

```bash
PYTHONPATH=3gpp python3 -m unittest discover -s 3gpp/tests -v
```

或提供包装脚本、测试配置和 CI 固定入口。
