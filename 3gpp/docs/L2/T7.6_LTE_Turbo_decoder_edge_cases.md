# T7.6 LTE Turbo 译码边界案例
## 本节学习目标

本节把 LTE Turbo接收链路中最容易出错的边界案例整理成一套可执行的诊断方法。这里的“边界案例”不是冷门案例，而是协议规则切换、缓存地址切换、码块顺序切换或数值语义切换的位置。真实工程中，很多 Turbo 译码失败并不是因为译码算法完全错误，而是因为某个边界语义被混淆：填充位（filler bit）、子块交织补位 `<NULL>`、打孔位置、重复位置、软缓存位置和码块重组顺序都可能表现为“这里没有收到一个正常业务比特”，但它们在协议和接收端实现中的处理完全不同。


- 区分小块、分段 filler、子块交织 `<NULL>`、打孔位置和重复位置的协议位置。
- 解释最大码块数、软缓存限制、冗余版本（Redundancy Version, RV）序列不匹配、对数似然比符号不匹配、循环冗余校验误通过风险和译码超时。
- 对照 TS 36.212 的分段、Turbo 编码和速率匹配规则建立接收端诊断证据链。
- 设计包含 descriptor、地址、mask、软缓存和 CRC 的最小 dump 包。
- 判断某个问题属于协议比特规则、接收端反操作、数值定点策略还是硬件控制策略。

本节后文使用以下工程缩写：传输块、码块、混合自动重传请求、调制与编码方案、寄存器传输级和专用集成电路。这些缩写在 LTE Turbo 译码调试中会反复出现。

## 前置知识检查

| 前置项 | 本节需要达到的程度 |
|:---|:---|
| 传输块/码块 | 知道 TB 可以按协议分割成 CB，多个 CB 最后必须按编号重组回一个 TB。 |
| Turbo 速率匹配 | 知道三个 Turbo 编码输出流经过子块交织、比特收集、循环缓存选择和发送长度截取。 |
| HARQ | 知道 HARQ 会把重传软信息与旧软信息合并。 |
| LLR | 知道 LLR 的符号表示更相信 0 还是 1，幅度表示置信度。 |
| CRC | 知道 CRC 只能做错误检测，不能保证所有错误都被发现。 |
| 定点实现 | 知道硬件保存的是有限位宽数值，累加需要饱和，地址和 mask 需要可观测。 |

协议前因后果可以按接收侧反推：发射端必须把任意长度 TB 变成 Turbo 编码器支持的 CB，再把编码输出按无线资源容量截取成 $E$ 个发送比特；接收端拿到的是解调后的软比特，不是完整编码码字，因此必须恢复码块边界、恢复循环缓存位置、合并 HARQ 重传、译码每个 CB、检查 CB CRC、按协议顺序重组 TB，再检查 TB CRC。边界错误通常发生在这些反操作的接口处。

## 边界案例的工程动机

边界案例之所以高风险，有三个原因。

第一，协议里有多个“空洞”。分段 filler 是为了凑出合法码块长度；子块交织 `<NULL>` 是为了凑出交织矩阵形状；打孔或未发送位置是当前传输没有观测到某个编码位。这三者都可能在代码中被表示成“没有真实接收值”，但它们的生命周期不同：filler 在 CB 开头、参与编码和 CB CRC 计算时按 0 处理、最终重组 TB 时删除；`<NULL>` 是子块交织内部的补位，速率匹配读出时跳过，不应该进入循环缓存有效内容；打孔位置是实际编码位，只是本次没有发送，接收端应保留位置并给未知软信息。

第二，HARQ 让错误延迟暴露。初传 RV0 的地址错误可能只表现为性能略差；重传 RV2 到来后，如果接收端把 LLR 写入错误循环缓存位置，软合并反而会增加错误置信度。此时只看最终 TB CRC fail 无法定位，需要同时看 `rvidx`、$k_0$、$E$、$N_{cb}$ 和软缓存 before/after。

第三，Turbo 译码是迭代算法。LLR 符号反转、饱和过早、尾比特错误或外信息缩放不当，可能都表现为迭代次数跑满、CB CRC fail 和块错误率异常。诊断必须先排除协议地址和符号约定，再讨论译码器内部算法。

## 协议规则到接收端对象模型

建议把接收端每个 CB 的上下文保存成 descriptor，而不是把所有控制量散落在日志里。一个最小 descriptor 至少包含：

| 字段 | 含义 | 协议或实现来源 | 诊断用途 |
|:---|:---|:---|:---|
| `tb_id` | TB 唯一标识或测试向量标识 | 实现策略 | 关联 TB CRC、CB dump 和 HARQ 日志。 |
| `harq_id` | HARQ 进程编号 | 调度/MAC 控制 | 防止软缓存串进程。 |
| `r` | CB 编号 | TS 36.212 §5.1.2 | 重组时必须按 $r=0,1,\ldots,C-1$ 顺序。 |
| `C` | CB 总数 | TS 36.212 §5.1.2 | 检查最大码块数、CB CRC 个数和重组完成条件。 |
| `K_r` | 第 $r$ 个 CB 长度 | TS 36.212 §5.1.2 和 Table 5.1.3-3 | 校验 Turbo 交织器参数和解码输出长度。 |
| `F` | 第 0 个 CB 前置 filler 数量 | TS 36.212 §5.1.2 | 只允许在 CB0 开头删除。 |
| `K_w` | 循环缓存生成前的收集长度 | TS 36.212 §5.1.4.1 | 定位循环缓存地址范围。 |
| `Ncb` | 第 $r$ 个 CB 可用软缓存长度 | TS 36.212 §5.1.4.1.2 | 判断软缓存限制是否导致截断。 |
| `E` | 本次传输为该 CB 分配的速率匹配输出长度 | TS 36.212 §5.1.4.1.2 | 检查解速率匹配输入数量。 |
| `rvidx` | 本次传输使用的 RV 编号 | TS 36.212 §5.1.4.1.2 | 计算循环缓存读取起点 $k_0$。 |
| `k0` | 循环缓存起点 | TS 36.212 §5.1.4.1.2 | 诊断 RV 序列和地址映射。 |
| `null_mask` | 子块交织 `<NULL>` 位置 | 协议规则加实现记录 | 确认 `<NULL>` 被跳过。 |
| `unknown_mask` | 打孔或未发送编码位位置 | 接收端反匹配策略 | 区分无观测和低可靠度。 |
| `soft_before`/`soft_after` | 软合并前后 LLR 摘要 | 实现策略 | 检查重复和重传是否累加、饱和。 |
| `cb_crc`/`tb_crc` | CB/TB CRC 判决 | TS 36.212 §5.1.1/§5.1.2 | 建立失败定位层级。 |

这个对象模型的关键是把“比特值”和“语义来源”分开。数值 0 可以表示一个真实硬比特 0，也可以表示未知 LLR 的中性值；如果没有 mask，后续调试无法区分。

## 三类空洞的严格区分

| 空洞类型 | 产生阶段 | 是否代表业务位 | 是否占据 Turbo 译码码字位置 | 是否在 TB 重组时删除 | 正确接收端语义 |
|:---|:---|:---:|:---:|:---:|:---|
| 分段 filler | 码块分段，TS 36.212 §5.1.2 | 否 | 是。它在 CB0 开头补足合法 $K$。 | 是。只删除 CB0 开头 $F$ 位。 | 编码和 CRC 计算中按协议规则处理，最终不能进入 TB payload。 |
| 子块交织 `<NULL>` | 子块交织矩阵补位，TS 36.212 §5.1.4.1.1 | 否 | 否。它不是有效编码位。 | 否。它不应出现在译码输出。 | 生成循环缓存和读出时跳过。 |
| 打孔/未发送位置 | 循环缓存选择和有限发送长度，TS 36.212 §5.1.4.1.2 | 是编码位位置 | 是。该位置属于码字，只是本次没有观测。 | 否。 | 保留位置，输入未知软信息，等待其他 RV 或保持中性 LLR。 |

这张表直接约束四个典型失败模式：不能把打孔位置当 0，不能把 `<NULL>` 当业务位，不能把分段 filler 留到 TB 中，也不能按译码完成顺序拼接 CB。

## 边界案例总表

| 案例 | 触发条件 | 典型症状 | 必查字段 | 定位步骤 | 修复方向 |
|:---|:---|:---|:---|:---|:---|
| 小块 | $B<40$ 或接近最小 Turbo 交织器长度 | 单 CB CRC fail，输出长度比预期多，早停异常 | `B`、`C`、`K_r`、`F`、CB0 输入 | 对照 §5.1.2 确认 filler 是否加在 CB0 开头；检查 Turbo 编码器输入是否把 filler 按协议置 0 | 用 descriptor 驱动 filler 插入和删除，不在译码器内部猜测长度。 |
| 分段 filler | $F>0$，尤其多 CB 且 CB0 需要 filler | TB CRC fail，CB CRC 可能 pass，TB payload 前端偏移 | `F`、`r`、CB0 decoded bits、TB reassembly offset | 只检查 CB0 前 $F$ 位；确认 CB CRC 输入和 TB 重组输入不是同一语义 | CB CRC 前按协议处理 filler，TB 重组时删除 CB0 前 $F$ 位。 |
| 子块交织 `<NULL>` | $D$ 不能整除交织矩阵列数，矩阵前端需要补位 | 解速率匹配后 LLR 数量不对，循环缓存地址偏移 | `null_mask`、矩阵行列数、列置换索引、$K_w$ | 从子块交织矩阵读出序列开始比对；统计 `<NULL>` 被跳过数量 | `<NULL>` 只作为矩阵补位 mask，不进入有效循环缓存。 |
| 打孔位置 | $E<N_{cb}$ 或本次 RV 没覆盖全部循环缓存区域 | 高码率性能异常，未知位置被译码器强置信度误导 | `unknown_mask`、$E$、$N_{cb}$、$k_0$、LLR 初值 | 检查未收到位置是否被填成强正或强负 LLR | 未发送位置用中性 LLR 或实现约定 unknown，并保留 mask。 |
| 重复位置 | $E$ 大于可选有效区域或循环读取回绕 | 可靠度异常偏大或偏小，饱和计数异常 | 地址命中计数、`sat_count`、soft before/after | 统计同一循环缓存位置被写入次数；比对累加和饱和 | 重复位置做软合并，不覆盖；定点实现使用饱和加法。 |
| 最大码块数 | TB 较大导致 $C>1$，或实现数组上限小于协议/配置需要 | 只译部分 CB，重组缺块，最后一个 CB 溢出 | `B`、`C`、`max_cb_supported`、CB descriptor 数组 | 用 §5.1.2 重新计算 $C$；检查 descriptor 分配和 scoreboard 完成条件 | 按配置上限显式报错或扩展数组，禁止静默截断。 |
| 软缓存限制 | $N_{cb}<K_w$，用户设备（User Equipment, UE）软缓存能力受限 | 重传合并效果弱，某些位置永远无观测 | $N_{soft}$、$N_{IR}$、$N_{cb}$、$K_w$、HARQ ID | 确认接收端和发射端使用同一软缓存限制；检查地址是否 modulo $N_{cb}$ | 软缓存 key 包含 HARQ/CB，地址空间以 $N_{cb}$ 为准，超出部分不能误认为协议位缺失。 |
| RV 序列不匹配 | 重传的 `rvidx` 与调度或缓存记录不一致 | 重传后 BLER 不降反升，LLR 合并方向混乱 | `rvidx`、$k_0$、$E$、soft before/after、HARQ attempt | 对每次传输计算起点，比较写入位置和前一次覆盖区域 | RV 作为地址生成输入，不能只写日志；检测非法 RV 序列并清缓存或 fail。 |
| LLR 符号不匹配 | 解调器和译码器对正 LLR 的含义相反 | 高信噪比（Signal-to-Noise Ratio, SNR）下仍大量 CRC fail | 已知二进制相移键控向量、硬判结果 | 用固定比特向量直接分类正 LLR 表示 0 还是 1 | 在接口文档和 bit-exact 测试中固定符号约定。 |
| CRC 误通过风险 | 错误比特模式碰巧产生相同 CRC 余数 | 少量错误 TB 被当成 pass，后续协议层异常 | seed、CRC input、first mismatch、CB CRC、TB CRC | 保存 pass 样本的摘要；对比 golden payload 而不是只看 CRC | 用回归统计和跨层一致性降低风险，不能宣称 CRC 绝对无误。 |
| 超时 | 最大迭代次数跑满、硬件周期预算耗尽或 HARQ deadline 到达 | CB 未完成、ACK/NACK 延迟、吞吐下降 | `iter_count`、`max_iter`、cycle count、timeout flag | 区分数值不收敛、地址错误和资源调度不足 | timeout 是失败状态，必须保留现场并阻止错误 TB 交付。 |

## 接收端诊断状态机

| 阶段 | 检查问题 | 失败时优先保留的证据 |
|:---|:---|:---|
| 1. 控制面锁存 | TB size、MCS、HARQ ID、RV、CB 数是否与调度一致 | 调度摘要、descriptor、HARQ attempt 计数 |
| 2. 分段反推 | $C$、$K_r$、$F$、$K_-$、$K_+$ 是否按 §5.1.2 推得 | 分段计算日志、CB0 filler mask、每个 $K_r$ |
| 3. 解速率匹配 | `<NULL>` 是否跳过，循环缓存起点和 $E$ 是否正确 | `null_mask`、$k_0$、$E$、$N_{cb}$、输入 LLR 序列 |
| 4. 软合并 | 同一编码位是否累加，不同 HARQ/CB 是否隔离 | soft before/after、地址命中计数、饱和计数 |
| 5. Turbo 译码 | LLR 符号、迭代次数、尾比特、早停是否正常 | hard decision、extrinsic 摘要、`iter_count`、CB CRC |
| 6. CB 后处理 | CB CRC 是否按 CB 编号关联，CB CRC 位是否删除 | 每个 CB 的 CRC syndrome、decoded length |
| 7. TB 重组 | 是否按 $r$ 顺序拼接，是否删除 CB0 filler | reassembly offset、first mismatch、TB CRC input |
| 8. 交付判决 | timeout、CB CRC fail、TB CRC fail 是否阻止交付 | final status、error code、NACK reason |

状态机的顺序有意从“控制参数”开始，而不是从 Turbo 译码器内部开始。原因是地址和 mask 错误会污染译码器输入，之后再调迭代次数、归一化或饱和值都没有意义。

## 最小诊断 dump 包

定位 LTE Turbo 边界问题时，单个 `CRC_FAIL` 日志没有价值。建议每个失败 TB 至少 dump 下列表格字段；通过 TB 也可以按采样策略保存摘要，用于分析 CRC 误通过风险。

| 类别 | 字段 | 示例 | 说明 |
|:---|:---|:---|:---|
| TB 级 | `tb_id`, `harq_id`, `attempt`, `mcs`, `G`, `Qm`, `NL` | `tb=17, harq=3, attempt=2` | 关联调度、资源和 HARQ 生命周期。 |
| CB 级 | `r`, `C`, `K_r`, `F`, `K_w`, `Ncb`, `E` | `r=0,C=3,K=6144,F=12` | 定位分段、缓存和速率匹配边界。 |
| RV 地址 | `rvidx`, `k0`, `addr_first`, `addr_last`, `wrap_count` | `rv=2,k0=1536,wrap=1` | 确认循环缓存窗口和回绕。 |
| mask | `null_mask_count`, `unknown_mask_count`, `filler_count` | `null=18,unknown=2048,filler=12` | 区分三类空洞。 |
| 软合并 | `soft_before_hash`, `soft_after_hash`, `sat_count`, `repeat_hits` | `sat=32,repeat=128` | 判断覆盖、累加和饱和。 |
| 译码 | `llr_sign_mode`, `iter_count`, `early_stop`, `timeout` | `positive_means_zero,iter=8` | 诊断符号和收敛。 |
| CRC/重组 | `cb_crc`, `tb_crc`, `first_mismatch`, `reassembly_order` | `cb[1]=fail, first=834` | 建立从 CB 到 TB 的失败证据链。 |

其中 `first_mismatch` 应同时给出 TB 级 offset 和 CB 级 `(r,k)` 坐标。只给 TB offset 会让多 CB 问题难以回溯；只给 CB offset 又无法确认最终重组顺序。

## 高 SNR 失败与错误平层定位

高信噪比仍失败时，不要直接把结论写成“Turbo 算法不行”。高 SNR 下噪声不是完全消失，但随机噪声导致的错误应显著减少；如果 BLER 曲线进入平台，或者固定向量在高 SNR 仍稳定失败，优先怀疑确定性实现错误、低重量事件或定点饱和。

定位流程按以下顺序执行：

| 步骤 | 目标 | 必查证据 | 典型结论 |
|:---|:---|:---|:---|
| 1. 固定无噪声或极高 SNR 向量 | 排除 demapper 随机噪声 | 已知发送比特、LLR sign、硬判第一错位 | 若仍失败，先查符号、地址和 CRC 输入。 |
| 2. 单 RV 与多 RV 对比 | 区分 rate recovery 和 HARQ 合并 | `rvidx/k0/E/Ncb`、new/repeated/unknown 统计 | 重传不改善常指向 RV mismatch 或 soft buffer 覆盖错误。 |
| 3. `<NULL>`/punctured 分离 | 排除 mask 语义错 | `null_skip_count`、`unknown_mask_count`、Turbo 输入长度 | 长度相关失败常来自 `<NULL>` 被消费或 unknown 被删除。 |
| 4. 浮点 Log-MAP 对照 | 排除近似和量化 | 浮点后验 LLR、Max-Log LLR 差分、饱和计数 | 浮点过、定点失败时查 clip/scale/saturation。 |
| 5. 迭代轨迹检查 | 区分不收敛和误早停 | 每轮 CRC、LLR 翻转数、外信息幅度 | 翻转不降是振荡，翻转为 0 仍 fail 是稳定错误假设。 |
| 6. 错误平层样本聚类 | 找确定性失败模式 | first mismatch、低重量模式、CB 长度、interleaver 参数 | 相同位置反复失败时，查交织器和边界长度。 |

错误平层样本的 failure bundle 应额外保存这些字段：`snr_db`、`noise_seed`、`rv_history`、`new_cover_count`、`repeat_cover_count`、`unknown_count_after`、`sat_count`、`iter_crc_trace`、`llr_flip_trace`、`first_wrong_bit`、`wrong_weight`、`interleaver_param_id` 和 `null_skip_count`。没有这些字段时，只能说“观察到高 SNR 失败”，不能定位为算法错误或协议错误。

## 详细案例：RV 起点不匹配

RV 的本质不是“第几次重传”的标签，而是循环缓存中不同起点或区域的选择。TS 36.212 §5.1.4.1.2 定义 `rvidx` 和 $k_0$，接收端必须用本次传输的 `rvidx` 把收到的 $E$ 个 LLR 放回对应循环缓存位置。

一个典型错误是：初传按 RV0 写入软缓存，重传到来时日志显示 RV2，但地址生成器仍使用 RV0 的 $k_0$。这样会发生两件事：第一，RV2 原本应补充的校验信息没有写入；第二，RV2 的 LLR 被错误累加到 RV0 覆盖过的位置，形成错误置信度。表面现象是“重传之后性能更差”，根因却是循环缓存写地址错。

最小定位步骤如下：

1. 对同一 `(harq_id,r)` 收集每次 attempt 的 `rvidx`、$E$、$N_{cb}$ 和 $k_0$。
2. 对每次 attempt 生成地址窗口摘要：起点、终点、是否回绕、每个地址的命中次数。
3. 比较 soft before/after：新 RV 应该让一批原 unknown 位置变成有观测，或让重复位置 LLR 增强。
4. 若重传没有减少 unknown count，或大量写入与初传完全相同的窗口，优先检查 RV 锁存和 $k_0$ 计算。

工程修复不能只在日志里记录 `rvidx`，必须让 `rvidx` 进入地址生成器、软缓存 key 和回归向量元数据。若调度层给出非法或不连续 RV 序列，译码器应至少能够产生可审计错误码，而不是把它当普通重传静默合并。

## 详细案例：`<NULL>` 与打孔未知位置混淆

`<NULL>` 和打孔位置都没有真实接收 LLR，但协议语义相反。`<NULL>` 是子块交织矩阵的补位，不是编码位；打孔位置是编码位，只是本次没有发送。

教学例子如下。假设某个子块交织输入长度 $D=10$，矩阵列数为 4，则需要 3 行才能容纳输入，矩阵容量为 12。前面会有 $N_D=12-10=2$ 个 `<NULL>` 补位。经过列置换和按列读出后，读到 `<NULL>` 时应跳过，因此它不会成为循环缓存中的有效编码位。相反，若循环缓存长度 $N_{cb}=20$，本次只发送 $E=8$ 个位置，那么未覆盖的 12 个位置仍然是码字位置，只是缺观测，应进入 `unknown_mask`。

错误实现常把这两类位置都填成 LLR 0。LLR 0 本身代表“没有偏向 0 或 1”，适合表示未知观测；但如果 `<NULL>` 也占一个码字位置，后续所有地址都会偏移。更糟的是，CB CRC 可能只在某些长度下失败，导致问题看起来像随机 BLER 抖动。

诊断时应分别统计：

- `null_skip_count`：从子块交织输出到循环缓存收集阶段跳过了多少 `<NULL>`。
- `unknown_mask_count`：循环缓存中有多少有效编码位当前没有观测。
- `llr_zero_count`：数值为 0 的 LLR 个数。这个计数不能替代前两个语义计数。

修复方向是使用两套 mask：`null_mask` 只在交织和收集阶段生效，`unknown_mask` 进入解速率匹配和软合并阶段。任何把 `<NULL>` 送入 Turbo 译码输入的路径都应被断言拦截。

## 详细案例：分段 filler 留入 TB 重组

TS 36.212 §5.1.2 的分段 filler 解决的是“码块长度必须落在 Turbo 内部交织器支持集合中”的问题。若 $F>0$，filler 加在第 0 个 CB 的开头。协议还规定 CB CRC 计算时 filler 按 0 处理；这容易让实现误以为 filler 是业务 0。

接收端必须把两件事分开：

- CB 译码和 CB CRC 阶段：filler 属于 CB 输入结构的一部分，需要与 $K_0$ 和 CRC 规则对齐。
- TB 重组阶段：filler 不是 TB payload，必须从 CB0 开头删除，不能进入 TB CRC 输入。

一个常见失败流程是：所有 CB CRC 都 pass，但 TB CRC fail；打印 TB payload 时发现开头多出若干 0，后续全部偏移。此时不要先怀疑 Turbo 算法，应检查 `F`、CB0 decoded bits、reassembly offset 和 TB CRC input length。

修复方向是让重组器按 descriptor 工作：

```text
for r in 0..C-1:
    decoded_payload = remove_cb_crc(cb_decoded[r])
    if r == 0:
        decoded_payload = decoded_payload[F:]
    append_to_tb_in_r_order(decoded_payload)
```

这里的 `r_order` 也是边界。多 CB 并行译码时，CB1 可能先完成，但协议重组必须按 CB 编号顺序，不能按完成顺序写 TB buffer。

## 详细案例：最大码块数与软缓存限制

TS 36.212 §5.1.2 给出最大编码块尺寸 $Z=6144$。当 TB 加 CRC 后超过单个 CB 能承载的范围时，协议会引入多个 CB，并可能为每个 CB 加 CB CRC。对接收端来说，最大码块数不是一个可以随意截断的数组长度；它由 TB size、分段规则和实现支持上限共同决定。

边界风险有两类。

第一类是 descriptor 截断。例如实现数组只按常见场景预留 8 个 CB，但某个测试向量推得 $C=13$。如果代码静默只创建前 8 个 descriptor，最后表现为 TB CRC fail 或 timeout，而不是清晰的 `CB_DESCRIPTOR_OVERFLOW`。正确处理是：若实现上限小于当前 $C$，在译码启动前 fail 并记录配置；若目标产品必须支持该场景，则扩展 descriptor、scoreboard、软缓存索引和回归覆盖点。

第二类是软缓存限制。TS 36.212 §5.1.4.1.2 用 $N_{IR}$、$N_{soft}$、$K_{MIMO}$、HARQ 进程数和 $C$ 等量推导每个 CB 的 $N_{cb}$。当 $N_{cb}<K_w$ 时，循环缓存可用于当前 CB 的软信息长度受限。接收端如果仍按 $K_w$ 分配和取模，地址会越界或把无效区域当成未知编码位。正确做法是：所有 RV 起点、写入窗口、unknown mask 和 soft before/after 都以 $N_{cb}$ 为当前地址空间。

最小验证向量应包含：

- 单 CB、小 $F$、无软缓存裁剪。
- 多 CB、$K_-$ 短块在前、$K_+$ 长块在后。
- $N_{cb}=K_w$ 和 $N_{cb}<K_w$ 两组对照。
- 实现支持上限附近的 $C=C_{max}$ 和 $C=C_{max}+1$ 负测试。

## 详细案例：LLR 符号约定反转

以 BPSK 为例，常见映射是比特 0 映射到 $+1$，比特 1 映射到 $-1$。若接收采样为 $y$，噪声方差为 $\sigma^2$，并定义

$$
L=\log\frac{P(b=0|y)}{P(b=1|y)}=\frac{2y}{\sigma^2}
\tag{1}
$$

则正 LLR 表示更相信 bit 0，负 LLR 表示更相信 bit 1。若解调器输出采用“正值表示更相信 1”的约定，而 Turbo 译码器按式 (1) 解释，那么信道越好、LLR 幅度越大，错误置信度越强。这个问题在高 SNR 下不会自然缓解，反而更稳定地失败。

诊断不需要完整 LTE 波形，可以用固定 BPSK 小向量直接做接口测试：

| 期望 bit | BPSK 符号 | 接收值 $y$ | 按式 (1) 的 LLR | 硬判 |
|:---:|:---:|:---:|:---:|:---:|
| 0 | $+1$ | $+2$ | $+4$ | 0 |
| 1 | $-1$ | $-1.5$ | $-3$ | 1 |
| 0 | $+1$ | $+0.8$ | $+1.6$ | 0 |
| 1 | $-1$ | $-2.2$ | $-4.4$ | 1 |

若硬判全部相反，先修接口符号，不要调整 Turbo 迭代次数。若只有部分错误，再进入噪声方差缩放、均衡增益、解调近似和定点裁剪排查。

## CRC 误通过与超时处理

CRC 是错误检测码，不是数学上的绝对正确性证明。一个 $L$ bit CRC 在随机错误模型下误通过概率通常可粗略理解为约 $2^{-L}$ 量级，但实际错误模式可能不是独立均匀随机，因此工程上不能只用一句“CRC pass”删除所有证据。尤其在边界案例回归中，建议对 pass 样本也抽样保存 `seed`、descriptor 摘要、first mismatch 对比结果和 CRC input hash。

超时是另一类容易被低估的边界。Turbo 译码器可能因为低 SNR、LLR 符号错、RV 地址错、尾比特错或内部资源拥塞而跑满最大迭代。超时后的 TB 不能交付给上层；即使硬件输出了一串硬判比特，也必须进入失败路径并保留 `timeout`、`iter_count`、`cycle_count` 和当前 CB 编号。把超时结果继续送 TB CRC 会让错误定位变得混乱。

## Python 诊断片段

下面的片段只验证 LLR 符号约定。它不是 LTE Turbo golden model，但适合放在接口回归的第一层，防止最基础的软信息方向错误进入复杂链路。

```python
def classify_llr_sign(llrs: list[float], expected_bits: list[int]) -> str:
    """Classify whether positive LLR means bit 0 or bit 1. Time: O(N), Space: O(1)."""
    hard_positive_zero = [0 if value >= 0 else 1 for value in llrs]
    hard_positive_one = [1 if value >= 0 else 0 for value in llrs]
    err_zero = sum(a != b for a, b in zip(hard_positive_zero, expected_bits))
    err_one = sum(a != b for a, b in zip(hard_positive_one, expected_bits))
    return "positive_means_zero" if err_zero <= err_one else "positive_means_one"


mode = classify_llr_sign([4.0, -3.0, 2.0, -1.0], [0, 1, 0, 1])
assert mode == "positive_means_zero"
print("T7.6_LLR_SIGN_CHECK_OK")
```

更完整的诊断脚本应继续检查：`len(input_llr)==E`、`0<=k0<Ncb`、`unknown_mask_count+observed_count==Ncb`、`null_mask` 不进入循环缓存、CB0 删除 filler 后 TB 长度等于预期。

## 浮点仿真方案

| 测试族 | 输入构造 | 观测字段 | 通过标准 |
|:---|:---|:---|:---|
| 小块与 filler | $B<40$、$F>0$、单 CB 和多 CB 向量 | `F`、CB0 input、TB output length | CB CRC 和 TB CRC 输入长度均正确，filler 不进入 TB。 |
| `<NULL>` 跳过 | 构造非整矩阵行的子块交织输入 | `null_skip_count`、$K_w$、循环缓存有效长度 | `<NULL>` 不进入有效循环缓存。 |
| 打孔与重复 | 人工设置 $E<N_{cb}$ 和回绕读取 | `unknown_mask`、地址命中计数、LLR 合并值 | 未发送位置保持 unknown，重复位置累加。 |
| RV 序列 | RV0/RV2/RV3/RV1 多次传输 | `rvidx`、$k_0$、soft before/after | 新 RV 补充不同区域，相同位置合并且不串 HARQ。 |
| LLR 符号 | 固定 BPSK/正交相移键控比特 | hard decision、CB CRC | 符号分类与接口约定一致。 |
| CRC 误通过 | 大量随机 seed 与 bit-exact golden 对比 | CRC pass 样本、first mismatch | CRC pass 且 payload mismatch 的样本被记录并统计。 |
| 超时 | 低 SNR、错误 RV、错误符号负测试 | `iter_count`、timeout、error code | 超时不交付 TB，失败原因可定位。 |

浮点仿真要把“协议地址正确性”和“译码算法性能”拆开。先用无噪声或高 SNR 向量确认地址、mask、重组完全正确，再扫 SNR 曲线观察 BLER。

## 定点化策略

| 边界 | 定点风险 | 策略 | 必测负例 |
|:---|:---|:---|:---|
| unknown LLR | 数值 0 与真实低可靠度混淆 | 额外保存 unknown mask，不用 LLR 数值承载来源语义 | 把 unknown 当强 0 时应触发回归失败。 |
| 重复合并 | 多次累加溢出或覆盖 | 使用饱和加法，记录 `sat_count` 和命中次数 | 两次相同地址输入后结果必须等于饱和累加值。 |
| RV 地址 | $k_0$ 位宽不足或取模错误 | 地址宽度覆盖 $N_{cb}$ 上限，所有 RV 做边界测试 | $k_0=N_{cb}-1$ 且 $E>1$ 的回绕场景。 |
| filler 删除 | offset 负数、跨 CB 删除 | 删除逻辑只允许作用于 CB0 前 $F$ 位 | 对 CB1 设置伪 filler mask 必须失败。 |
| LLR 符号 | 补码符号扩展错误 | 接口处固定 `positive_means_zero` 或相反约定 | 4 点 BPSK 向量 bit-exact。 |
| timeout | 计数器回绕导致假早停 | `iter_count` 和 cycle counter 采用饱和或足够位宽 | 最大迭代加 1 的边界测试。 |

定点实现中，饱和不是隐藏错误的工具。若 `sat_count` 在某个 RV 或某类块长上突然升高，应作为性能和地址排查线索。

## 硬件映射

RTL 或 ASIC 实现不应只暴露最终 CRC。至少需要下列可观测点：

| 硬件检查点 | 目的 | 推荐断言 |
|:---|:---|:---|
| `cfg_latch_valid` | 确认 TB/CB/HARQ/RV 配置在一次译码期间稳定 | start 后 descriptor 不被异步改写。 |
| `cb_desc_fifo` | 保存 `r,C,K_r,F,K_w,Ncb,E,rvidx,k0` | `r<C`，`E>0`，`Ncb<=Kw` 或等于实现允许范围。 |
| `null_skip_counter` | 统计子块交织补位跳过数量 | `<NULL>` 不写入循环缓存有效 RAM。 |
| `unknown_counter` | 统计未观测编码位 | unknown 位置不会被强置信度初始化。 |
| `soft_merge_sat_counter` | 观测软合并饱和 | 饱和次数超过门限触发 trace。 |
| `rv_addr_trace` | 记录每次 RV 写入窗口 | 同一 HARQ/CB 的不同 RV 地址与 $k_0$ 一致。 |
| `cb_done_scoreboard` | 管理多 CB 完成状态 | TB 重组只在所有 CB 完成且按编号读取后启动。 |
| `timeout_state` | 区分译码 fail 和时序 fail | timeout 后禁止 `tb_valid`。 |

硬件调试的核心是把协议字段变成地址、mask 和状态机的可观测证据。否则仿真看到 `tb_crc_fail`，无法判断是协议反匹配、软合并、Turbo 内核还是重组器的问题。

## 验证方法

| 验证项 | 最小向量 | 通过标准 |
|:---|:---|:---|
| filler 删除 | $F>0$ 的单 CB 和多 CB 向量 | CB0 前 $F$ 位不进入 TB，CB1 之后不被误删。 |
| `<NULL>` 跳过 | 子块交织矩阵需要补位的长度 | `null_skip_count` 等于补位数量，循环缓存无 `<NULL>`。 |
| 打孔 unknown | 人工让 $E<N_{cb}$ | 未覆盖位置保留 unknown mask，不被填成强 0。 |
| 重复合并 | $E$ 覆盖回绕并命中同一地址 | LLR 累加并按定点阈值饱和。 |
| RV 错配 | 同一 TB 故意把 RV2 当 RV0 | 回归必须失败，并在 $k_0$ 或地址窗口层定位。 |
| LLR 符号 | 固定 BPSK 四点向量 | 输出 `T7.6_LLR_SIGN_CHECK_OK`。 |
| 最大 CB 数 | $C$ 接近实现上限 | descriptor 不溢出；超过上限时显式 fail。 |
| 软缓存裁剪 | $N_{cb}<K_w$ | 地址不越界，unknown mask 以 $N_{cb}$ 为范围。 |
| CRC 误通过审计 | 随机 seed 大回归 | pass 样本可追溯，payload mismatch 被统计。 |
| 超时 | 低 SNR 或故意错误配置 | timeout 阻止 TB 交付，保留现场。 |

验证顺序建议先做协议无噪声向量，再做有噪声 BLER。无噪声向量失败时，不要用性能曲线掩盖地址和 mask 错误。

## 常见错误

| 错误 | 后果 | 修正 |
|:---|:---|:---|
| 把打孔位置当 0 | 给译码器强置信度假信息，BLER 异常 | 用 unknown mask 加中性 LLR，保留位置。 |
| 把 `<NULL>` 当业务位 | 循环缓存地址整体偏移 | `<NULL>` 只在子块交织内部存在，读出时跳过。 |
| 把分段 filler 留到 TB 中 | TB payload 前端多位，TB CRC fail | 只删除 CB0 开头 $F$ 位。 |
| 按译码完成顺序拼接 CB | 并行译码时 TB 乱序 | 按 CB 编号 $r$ 重组。 |
| 重复位置覆盖而非合并 | 重传信息损失，可靠度偏低 | 同一编码位位置做饱和累加。 |
| RV 只记录在日志中 | 地址仍使用旧 RV，重传污染软缓存 | `rvidx` 必须进入 $k_0$ 和地址生成。 |
| 软缓存 key 缺少 HARQ ID | 不同进程互相污染 | key 至少包含 HARQ ID、TB/CB 标识和方向。 |
| CRC pass 后删除现场 | 无法分析误通过和边界回归 | 对 pass/fail 都保留摘要和 seed。 |
| 超时后仍交付 | 错误 TB 进入上层 | timeout 必须产生失败状态和 NACK 路径。 |

| 用例 | 场景 | T7.6 诊断价值 |
|:---|:---|:---|
| 基站或终端协议栈联调 | 某些 MCS/RV 组合下重传后 BLER 变差 | 通过 `rvidx`、$k_0$、soft before/after 判断是调度 RV、解速率匹配还是软合并问题。 |

4. RV 不匹配为什么可能让重传性能变差？

7. 为什么 $N_{cb}<K_w$ 时不能继续按 $K_w$ 做循环缓存地址空间？

## 工程思考题参考答案

1. 打孔位置没有观测值。硬 0 等价于告诉译码器“这里非常可靠地是 0”，会把错误信息注入迭代译码；正确语义是保留码字位置并用中性软信息或 unknown mask 表示缺观测。
2. `<NULL>` 属于子块交织矩阵补位，不是有效编码位，读出时应跳过；filler 属于分段阶段 CB0 开头的补位，会进入编码结构和 CRC 语义，但最终不是 TB payload，重组时删除。
3. 高 SNR 会让 LLR 幅度变大。符号正确时这是更强证据；符号反了时就是更强的错误证据，所以提高 SNR 也无法修复。
4. RV 决定循环缓存读取起点。错 RV 会把重传 LLR 写入错误编码位位置，既没有补充原先未发送的校验信息，又可能把错误软信息累加到已观测位置。
5. CRC 长度有限，不同错误比特序列可能产生相同余数。工程上只能通过足够长的 CRC、回归统计、跨层一致性和证据保留降低风险，不能消除到数学上的零。
6. 协议分段和重组按 CB 编号 $r$ 定义。并行译码的完成时间是实现行为，不是协议顺序；按完成顺序拼接会让 TB payload 块间交换。
7. $N_{cb}$ 是当前 CB 的可用软缓存地址空间。若仍按 $K_w$ 寻址，可能读写不存在或不应保存的位置，导致 unknown mask、RV 窗口和软合并全部失真。

## 自测题

1. 子块交织 `<NULL>` 是否进入最终 TB？
2. 分段 filler 是否在重组时删除？
3. 打孔位置是否在重组时删除？
4. 重复位置的 LLR 应覆盖还是合并？
5. 超时后是否可以交付 TB？
6. `first_mismatch` 只记录 TB offset 是否足够？
7. `llr == 0` 是否一定代表打孔或未知？

## 自测题参考答案

1. 不进入。它在子块交织读出阶段被跳过，正常情况下不应进入循环缓存有效内容，更不应进入 TB。
2. 是。只删除第 0 个 CB 开头的 $F$ 个 filler 位，不能删除其他 CB 的比特。
3. 不删除。打孔位置是编码位位置，只是本次没有观测；它影响译码输入，不是 TB 重组阶段的删除项。
4. 合并。同一编码位位置的多次观测应做 LLR 累加，并按定点规则饱和。
5. 不可以。超时是失败状态，应阻止 TB 交付并保留现场。
6. 不足够。应同时记录 TB offset 和 CB 级 `(r,k)` 坐标，才能回溯分段、译码和重组问题。
7. 不一定。LLR 0 只是一个数值，可能来自未知位置，也可能来自真实低可靠度观测；必须结合 mask 判断语义。
