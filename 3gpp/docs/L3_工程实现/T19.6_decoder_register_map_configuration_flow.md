# T19.6 译码器寄存器表与配置流：从协议参数到硬件任务描述符
## 本节学习目标

本节设计 3GPP LTE/NR译码子系统的寄存器表和配置流。这里的“寄存器”不是 3GPP 协议规定的空口字段，而是芯片内部让软件、物理层接收链路和译码硬件达成一致的控制接口。协议给出块长、调制阶数、冗余版本、混合自动重传请求上下文、低密度奇偶校验码基图和Polar构造等语义；硬件寄存器负责把这些语义锁存成一次可执行、可检查、可追踪的译码任务。

本节第一次使用或作为主角的技术缩写如下，后文不再反复展开：

| 名称 | 中文含义 |
|:---|:---|
| 物理层（Physical Layer, PHY） | 解调、反速率匹配和译码所在的最低通信处理层；本节重点是 PHY 把参数交给译码硬件。 |
| 媒体接入控制层 | 管理 HARQ、逻辑信道和调度结果消费的上层；本节只追踪它给译码配置带来的上下文。 |
| 调制与编码方案 | 调度侧选择调制阶数和目标码率的索引。 |
| 无线资源控制（Radio Resource Control, RRC） | 配置小区、能力、HARQ 数量、MCS 表等高层参数的协议层；本节不展开 RRC 消息课程。 |
| 正交相移键控 | 一种每个符号承载 2 个编码比特的调制方式，因此它对应 `Qm=2`。 |
| 调制阶数（Modulation Order, Qm） | 每个调制符号承载多少个编码比特，例如 QPSK 的 `Qm=2`。 |
| 基图（Base Graph, BG） | NR LDPC 的基础稀疏校验矩阵族，后续通过提升大小扩展。 |
| 提升大小（Lifting Size, Zc） | NR LDPC 把基本节图表中一个非零元素扩展成 `Zc x Zc` 循环置换矩阵的尺寸。 |
| 下行控制信息 | 调度 PDSCH/PUSCH 等传输的控制信息，包含 MCS、RV、NDI、HARQ process 等字段。 |
| 循环冗余校验 | 错误检测机制；在寄存器接口中影响 pass/fail、早停和错误码。 |
| 对数似然比 | 译码器输入软信息，寄存器中的 `LLR_WIDTH` 决定它在硬件中的定点宽度。 |
| 传输块 | MAC 交给物理层编码和最终 CRC 验收的数据块，寄存器中用 `TB_EPOCH` 防止新旧数据串扰。 |
| 码块 | TB 分段后的译码工作单元，寄存器中用 `CB_INDEX/CB_COUNT` 标识。 |
| Turbo | LTE 数据业务的信道编码之一，本节用 `TURBO_CFG` 承接它的块长、交织和迭代字段。 |
| 块错误率 | 评价译码失败概率的链路指标，寄存器策略过小或字段错误会让 BLER 变差。 |
| 传输块大小 | 调度和协议过程得到的 TB 比特数，寄存器可保存其派生出的块长、CB 数和 `E` 等字段。 |
| 专用集成电路 | 本节寄存器表、配置锁存和状态接口最终面向 ASIC 实现。 |
| 静态随机存取存储器 | ASIC 内部常用存储器，寄存器可暴露 soft buffer 或 trace 深度能力。 |
| 上行共享信道 | NR/LTE 上行数据传输信道；本节只追踪它给 LDPC/Turbo 任务提供的字段。 |
| 下行共享信道 | NR/LTE 下行数据传输信道；本节只追踪它给 LDPC/Turbo 任务提供的字段。 |
| 上行控制信息 | NR 上行控制比特，可能经 Polar 编码；本节只用于 Polar 配置来源。 |
| 寄存器传输级 | 将寄存器、状态机、译码核和中断逻辑落成硬件的设计层级。 |


- 说明为什么 3GPP 不规定译码器寄存器地址，但寄存器字段必须追溯到协议、调度、MAC/RRC 或实现策略。
- 把算法选择、块长、码率、BG、`Zc`、RV、`Qm`、HARQ ID、列表大小、迭代上限、start/status/error/IRQ 映射到寄存器组。
- 区分协议派生字段、调度派生字段、MAC/RRC 上下文字段、软件策略字段和实现状态字段。
- 设计 `CAPABILITY`、`COMMON_CFG`、`SOFTBUF_CFG`、`TURBO_CFG`、`LDPC_CFG`、`POLAR_CFG`、`CONTROL`、`STATUS`、`ERROR_IRQ`、`TRACE` 十类寄存器。
- 给出配置锁存流程：`IDLE -> WRITE_CFG -> LOCK_DESCRIPTOR -> LEGALITY_CHECK -> START -> BUSY -> DONE/ERROR -> IRQ/CLEAR`。
- 解释为什么 `list_size`、`max_iterations`、timeout、trace mask、IRQ enable 是实现策略，不是 3GPP 强制数值。
- 建立字段来源表、合法性检查、错误码、软件伪代码、RTL/ASIC 映射和验证计划。

如果只记住一句话：寄存器表是把一次协议译码任务变成硬件事务的“边界合同”；协议字段负责给出任务语义，寄存器锁存负责让这个语义在硬件运行期间不可漂移、可追踪、可失败恢复。

## 资料与协议边界

协议前因后果是：接收机先从控制信道、调度和高层配置得到“这次要译哪一类编码、多少比特、哪个 RV、哪个 HARQ 进程、哪些 CBG 被调度”；反速率匹配和 soft buffer 再把 LLR 放成译码器能消费的顺序；寄存器表把这些已解析字段锁存给硬件译码核。若字段来源不清，硬件可能仍能启动，但失败时无法判断是协议解析错、调度上下文错、soft buffer key 错，还是译码算法本身错。

## 寄存器不是协议字段

新手容易把“协议里有 RV 字段”和“硬件必须有一个叫 `RV` 的寄存器”混为一谈。正确分层如下：

| 层 | 负责什么 | 示例 |
|:---|:---|:---|
| 3GPP 协议 | 定义空口字段和处理规则。 | TS 38.214 §5.1.3 说明 PDSCH 从 DCI 读取 MCS 和 RV。 |
| 接收机解析模块 | 把协议字段和配置解析成内部 descriptor。 | `mcs_index -> Qm/R`，`rv bits -> rv`，`TBS procedure -> tb_size_bits`。 |
| 寄存器接口 | 把 descriptor 和实现策略写给硬件并锁存。 | `LDPC_BG`、`LDPC_ZC`、`SOFTBUF_HARQ_ID`、`CONTROL_START`。 |
| 硬件译码核 | 按锁存配置运行，产出 status/error/trace。 | `STATUS_DONE`、`ERROR_FIRST_BAD_FIELD`、`TRACE_DESC_HASH`。 |

因此本节寄存器表的写作原则是：每个字段都要能回答“从哪里来、为什么需要、谁写、谁读、何时锁存、错了会怎样”。如果一个字段不能追溯到协议、调度、MAC/RRC 或实现策略，就不应进入首版寄存器表。

## 字段分类

| 类别 | 来源 | 字段示例 | 处理规则 |
|:---|:---|:---|:---|
| 协议派生算法字段 | TS 36.212/TS 38.212 | Turbo `K/f1/f2`，LDPC `BG/Zc/iLS`，Polar `N/K/E`。 | 上游解析后写入；硬件只做范围检查，不重新跑完整协议表选择。 |
| 调度派生字段 | TS 36.213/TS 38.214、DCI 解析 | `Qm/R/TBS/RV/HARQ ID/NDI/CBGTI/CBGFI`。 | 必须和 soft buffer key、rate recovery 结果一致。 |
| MAC/RRC 上下文字段 | TS 36.321/36.331/38.321/38.331 | HARQ process count、MCS table、CBG 配置、serving cell capability。 | 未精确核验字段保持 `待核验`；写入实现时应由上层配置模块归一化。 |
| 软件策略字段 | driver 或 firmware | `max_iterations/list_size/timeout/trace_mask/irq_enable`。 | 不能写成协议强制值；应有安全上下限。 |
| 实现状态字段 | RTL/ASIC | `busy/done/pass_fail/error_code/latency/desc_hash`。 | 只读或写 1 清除；用于验收和 debug。 |

| `POLAR_CFG` | `POLAR_RNTI_CONTEXT` | RW | 0 | driver | `LOCK_DESCRIPTOR` | DCI CRC/RNTI mask 上下文。 |
| `POLAR_CFG` | `POLAR_MASK_HASH` | RW | 0 | driver | `LOCK_DESCRIPTOR` | frozen/information mask 摘要。 |
| `CONTROL` | `CONTROL_START` | W1P | 0 | driver | `IDLE/LEGALITY_CHECK` | 启动一次任务。 |
| `CONTROL` | `CONTROL_ABORT` | W1P | 0 | driver | `BUSY` | 软件主动中止。 |
| `CONTROL` | `CONTROL_SOFT_RESET` | W1P | 0 | driver | 任意 | 清内部状态，保留 capability。 |
| `STATUS` | `STATUS_BUSY` | RO | 0 | RTL | 运行中 | 任务正在执行。 |
| `STATUS` | `STATUS_DONE` | RO/W1C | 0 | RTL/driver | 完成后 | 任务结束，等待清除。 |
| `STATUS` | `STATUS_PASS_FAIL` | RO | 0 | RTL | 完成后 | CRC/syndrome/list selector 结果。 |
| `STATUS` | `STATUS_STOP_REASON` | RO | 0 | RTL | 完成后 | `CRC_PASS/MAX_ITER/TIMEOUT/ABORT/ERROR`。 |
| `ERROR_IRQ` | `ERROR_CODE` | RO/W1C | 0 | RTL/driver | 错误时 | 稳定错误分类。 |
| `ERROR_IRQ` | `ERROR_FIRST_BAD_FIELD` | RO/W1C | 0 | RTL/driver | 合法性检查失败 | 第一个非法字段编号。 |
| `ERROR_IRQ` | `IRQ_ENABLE/IRQ_STATUS/IRQ_CLEAR` | RW/RO/W1C | 0 | driver/RTL | 完成或错误 | 中断控制。 |
| `TRACE` | `TRACE_MASK` | RW | 0 | driver | `LOCK_DESCRIPTOR` | trace 选择，实现策略。 |
| `TRACE` | `TRACE_PTR` | RO | 0 | RTL | 运行中/完成 | trace 写指针。 |
| `TRACE` | `TRACE_DESC_HASH` | RO | 0 | RTL | 锁存后 | descriptor 快照 hash。 |

`RO` 表示只读，`RW` 表示可读写，`W1P` 表示写 1 产生一个脉冲，`W1C` 表示写 1 清除。真实总线可用 APB、AXI-Lite 或片内控制总线；本节不绑定总线协议。

## 字段来源映射

| 字段 | 主要来源 | 上游处理 | 寄存器保存什么 | 错误后果 |
|:---|:---|:---|:---|:---|
| `COMMON_FAMILY` | TS 36.212/38.212 channel coding chain 和本地任务类型。 | 根据 channel type 选择 Turbo/LDPC/Polar。 | 枚举值。 | 选错引擎，输出全错或非法字段。 |
| `TURBO_K/f1/f2` | TS 36.212 Turbo interleaver Table 5.1.3-3。 | 上游查表，或由已复现表生成。 | 当前 CB 的交织参数。 | 交织/解交织地址错。 |
| `TURBO_E/NCB/RV` | TS 36.212 §5.1.4.1.2。 | rate recovery 计算 `Ncb/E/rvidx`。 | 访问长度和 RV。 | LLR 放错 circular buffer。 |
| `LDPC_BG/ZC/ILS` | TS 38.212 §5.2.2/§5.3.2。 | 分段、BG 选择和 lifting set 选择。 | LDPC 图构造参数。 | parity-check schedule 和地址生成错。 |
| `LDPC_E/K0/RV/Qm` | TS 38.212 §5.4.2；TS 38.214 §5.1.3/§6.1.4。 | 调度得到 `Qm/R/RV/TBS`，rate recovery 得到 `E_r/k0`。 | 本 CB 的 bit selection 访问参数。 | RV window、bit interleaving 或 soft combining 错。 |
| `POLAR_N/K/E` | TS 38.212 §5.3.1/§5.4.1。 | Polar construction 和 rate recovery。 | mother length、信息长度、输出长度。 | frozen mask 或 rate recovery 错。 |
| `POLAR_LIST_SIZE` | 实现策略。 | driver 根据模式/性能预算选择。 | CA-SCL list size。 | 写太小 BLER 变差，写太大超资源；不是协议违法。 |
| `HARQ_ID/NDI` | DCI、MAC HARQ context；NR 见 TS 38.214，LTE TS 36.213 精确字段 `待核验`。 | 调度解析和 HARQ 状态机。 | soft buffer context key。 | 新旧 TB 串扰或重传 miss。 |
| `CBG_MASK/CBGFI` | TS 38.214 §5.1.7/§6.1.5。 | DCI CBGTI/CBGFI 解析。 | 本次哪些 CBG 写入、旧证据能否合并。 | 未调度 CBG 被误写或损坏旧证据继续合并。 |
| `MAX_ITER` | 实现策略。 | driver 或 profile 选择。 | 引擎迭代上限。 | 过小性能差，过大延迟高；不是协议字段。 |
| `IRQ_ENABLE` | 软件策略。 | 驱动配置。 | done/error 是否产生中断。 | 中断风暴或软件漏收完成。 |

## 配置状态机

配置流必须避免“软件还在写寄存器，硬件已经启动”的竞态。推荐状态机如下：

| 状态 | 允许动作 | 退出条件 | 错误检查 |
|:---|:---|:---|:---|
| `IDLE` | 写配置寄存器，清 status/error。 | 写入 `CONTROL_START=1` 后进入 `WRITE_CFG` 或直接锁存。 | 若上次 `DONE` 未清，可拒绝 start。 |
| `WRITE_CFG` | 软件写 `COMMON/SOFTBUF/FAMILY_CFG`。 | 软件写 `LOCK_DESCRIPTOR` 或 `START` 触发自动锁存。 | 检查必须字段是否写齐。 |
| `LOCK_DESCRIPTOR` | RTL 复制配置到影子寄存器。 | 快照完成。 | 生成 `TRACE_DESC_HASH`。 |
| `LEGALITY_CHECK` | 范围检查和跨字段一致性检查。 | 全部通过进入 `START`，失败进入 `DONE/ERROR`。 | `family` 与参数组匹配、长度非零、`rv` 合法、`Qm` 合法、busy 未写。 |
| `START` | 给目标引擎一个启动脉冲。 | 引擎 accept。 | 若目标引擎不可用，报 `ERR_ENGINE_DISABLED`。 |
| `BUSY` | 硬件执行，软件只读 status，可写 abort。 | 译码完成、错误、timeout 或 abort。 | 任何配置写入报 `ERR_WRITE_WHILE_BUSY` 或被忽略并 trace。 |
| `DONE/ERROR` | status/error/trace 稳定，IRQ 可拉高。 | 软件读结果并写 1 清除。 | 清除前禁止覆盖结果。 |

配置锁存可写成：

$$
\mathrm{task\_snapshot}
=
\mathrm{hash}(
\mathrm{COMMON\_CFG},
\mathrm{SOFTBUF\_CFG},
\mathrm{FAMILY\_CFG},
\mathrm{CONTROL\_POLICY}
).
\tag{1}
$$

式 (1) 回答的是“失败后如何证明硬件看到的配置到底是什么”。driver 可以在日志中保存同一个 hash；RTL 在 trace 中保存 `TRACE_DESC_HASH`。若两者不同，说明配置写入、端序、位域或锁存时序有问题。

合法性检查可以写成集合约束：

$$
\mathrm{legal}
=
(family \in F_{\mathrm{cap}})
\land (llr\_width \in W_{\mathrm{cap}})
\land (E>0)
\land (rv \in \{0,1,2,3\})
\land \mathrm{family\_specific\_legal}.
\tag{2}
$$

式 (2) 是寄存器接口层的防线。它不替代完整协议解析，但能阻止明显错误配置进入译码核。

## 具体数值走读：三个配置例子

下面三个数值例子不是协议测试向量，而是把“协议/调度解析结果如何落到寄存器”的路径走一遍。数值只用于说明字段关系；真实项目必须由上游协议解析器、rate recovery 和 golden model 生成同一份 descriptor。

### LTE Turbo CB

| 字段 | 示例值 | 来源 | 说明 |
|:---|:---|:---|:---|
| `COMMON_FAMILY` | `TURBO` | TS 36.212 LTE transport channel coding。 | 选择 Turbo 引擎。 |
| `CB_INDEX/CB_COUNT` | `0/3` | TS 36.212 segmentation 上游结果。 | 当前 TB 第 0 个 CB。 |
| `TURBO_K` | `6144` | TS 36.212 Table 5.1.3-3 支持集合。 | 示例最大 CB 尺寸。 |
| `TURBO_F1/F2` | 查表结果 | 上游表格复现。 | Turbo internal interleaver 参数。 |
| `TURBO_E/TURBO_NCB` | 上游 rate recovery 结果 | TS 36.212 §5.1.4.1.2。 | 当前 RV 访问长度和 circular buffer 长度。 |
| `SOFTBUF_HARQ_ID/RV/NDI` | `3/2/0` | LTE 调度上下文，TS 36.213 精确字段 `待核验`。 | 选择 soft buffer 旧证据并合并。 |
| `TURBO_MAX_ITER` | `8` | 实现策略。 | 不是协议强制值。 |

走读步骤：

1. driver 先写 `COMMON_FAMILY=TURBO`、`CB_INDEX=0`、`CB_COUNT=3`、`TB_EPOCH=42`。
2. 上游根据 TS 36.212 Table 5.1.3-3 查到 `K=6144` 对应的 `f1/f2`，写入 `TURBO_K/TURBO_F1/TURBO_F2`。
3. rate recovery 模块已经算出本次 `rvidx=2`、`E=9216`、`Ncb=18432`，driver 写 `SOFTBUF.RV=2`、`TURBO_E=9216`、`TURBO_NCB=18432`。
4. driver 写 `TURBO_MAX_ITER=8`、`CONTROL_START=1`。硬件锁存后如果 `TURBO_K` 不在支持集合内，`ERROR_FIRST_BAD_FIELD` 应指向 `TURBO_K`，而不是让 Turbo 核启动后 CRC fail。

### NR LDPC CBG 重传

| 字段 | 示例值 | 来源 | 说明 |
|:---|:---|:---|:---|
| `COMMON_FAMILY` | `LDPC` | TS 38.212 DL-SCH/UL-SCH LDPC。 | 选择 LDPC 引擎。 |
| `LDPC_BG/ZC/ILS` | `1/384/7` | TS 38.212 BG/lifting 上游结果。 | 驱动 QC-LDPC 地址生成。 |
| `LDPC_E/LDPC_K0/RV` | `E_r/k0/2` | TS 38.212 §5.4.2；TS 38.214 RV。 | 当前 CB 的 bit selection 窗口。 |
| `Qm` | `4` | TS 38.214 §5.1.3 MCS procedure。 | bit deinterleaving 和 `E_r` 计算上下文。 |
| `CBG_MASK` | `0b0100` | TS 38.214 §5.1.7.2 CBGTI。 | 仅对应 CBG 写入。 |
| `CBGFI` | `1` | TS 38.214 §5.1.7.2。 | 允许与旧 CBG 证据合并。 |
| `LDPC_MAX_ITER` | `20` | 实现策略。 | 性能/延迟折中。 |

走读步骤：

1. DCI/MAC 上下文给出 `HARQ_ID=5`、`NDI=0`、`RV=2`；TS 38.214 §5.1.3 的 MCS procedure 给出 `Qm=4` 和目标码率，TBS procedure 给出 TB 尺寸。
2. 上游 TS 38.212 LDPC 流程得到 `BG=1`、`Zc=384`、`iLS=7`，并按 bit selection 得到当前 CB 的 `E_r=8448`、`k0=98304`、`Ncb=25344`。这里 `k0` 的数值是示例，不作为协议表复现。
3. CBG partial retransmission 给出 `CBG_MASK=0b0100`、`CBGFI=1`。寄存器接口保存 mask，不重新解释 DCI bit order；bit order 的协议核验在上游完成。
4. legality checker 检查 `RV in {0,1,2,3}`、`E_r>0`、`Zc` 属于支持集合、`CBG_MASK` 非空。通过后才向 LDPC 引擎发 start。

### NR Polar DCI

| 字段 | 示例值 | 来源 | 说明 |
|:---|:---|:---|:---|
| `COMMON_FAMILY` | `POLAR` | TS 38.212 DCI/UCI Polar coding。 | 选择 Polar 引擎。 |
| `POLAR_N/K/E` | `128/56/108` | TS 38.212 construction/rate matching 上游结果。 | 确定树深、信息位和 rate recovery。 |
| `POLAR_CRC_TYPE` | `CRC24C` 或项目枚举 | TS 38.212 控制信息 CRC 边界。 | CA-SCL final selector 使用。 |
| `POLAR_RNTI_CONTEXT` | RNTI mask hash | DCI CRC scrambling 上下文。 | 控制候选验收。 |
| `POLAR_LIST_SIZE` | `8` | 实现策略。 | 协议允许接收端实现选择。 |
| `MAX_ITER` | `1` 或不用 | 实现策略。 | SC/SCL 不是 Turbo/LDPC 迭代同义词。 |

走读步骤：

1. 上游 Polar construction 得到 `N=128`、`K=56`，rate recovery 得到 `E=108`，CRC/RNTI 上下文生成 `POLAR_CRC_TYPE` 和 `POLAR_RNTI_CONTEXT`。
2. driver 根据性能/面积 profile 选择 `POLAR_LIST_SIZE=8`。这个值会显著影响 BLER、延迟和 sorter 面积，但不是 TS 38.212 强制数值。
3. 硬件锁存 `POLAR_MASK_HASH`，用于确认 frozen mask 与 golden model 使用同一构造结果。
4. 若软件在 BUSY 期间把 `POLAR_LIST_SIZE` 改为 4，当前任务必须继续使用锁存的 8；否则同一 DCI 的候选路径数会在运行中变化。

## 驱动伪代码

```python
def launch_decoder_task(regs, desc):
    if regs.STATUS_BUSY:
        raise RuntimeError("decoder busy")

    regs.IRQ_CLEAR = 1
    regs.ERROR_CLEAR = 1

    regs.COMMON_FAMILY = desc.family
    regs.TASK_ID = desc.task_id
    regs.CARRIER_ID = desc.carrier
    regs.CODEWORD_ID = desc.codeword
    regs.TB_EPOCH = desc.tb_epoch
    regs.CB_INDEX = desc.cb_index
    regs.CB_COUNT = desc.cb_count
    regs.LLR_WIDTH = desc.llr_width
    regs.TIMEOUT_CYCLES = desc.timeout_cycles

    regs.SOFTBUF_HARQ_ID = desc.harq_id
    regs.SOFTBUF_KEY_HASH = desc.softbuf_key_hash
    regs.NDI = desc.ndi
    regs.RV = desc.rv
    regs.CBG_MASK = desc.cbg_mask
    regs.CBGFI = desc.cbgfi
    regs.SAT_MODE = desc.sat_mode

    if desc.family == "TURBO":
        regs.TURBO_K = desc.K
        regs.TURBO_F1 = desc.f1
        regs.TURBO_F2 = desc.f2
        regs.TURBO_E = desc.E
        regs.TURBO_NCB = desc.Ncb
        regs.TURBO_MAX_ITER = desc.max_iterations
    elif desc.family == "LDPC":
        regs.LDPC_BG = desc.bg
        regs.LDPC_ZC = desc.zc
        regs.LDPC_ILS = desc.ils
        regs.LDPC_E = desc.E
        regs.LDPC_NCB = desc.Ncb
        regs.LDPC_K0 = desc.k0
        regs.LDPC_MAX_ITER = desc.max_iterations
    elif desc.family == "POLAR":
        regs.POLAR_N = desc.N
        regs.POLAR_K = desc.K
        regs.POLAR_E = desc.E
        regs.POLAR_LIST_SIZE = desc.list_size
        regs.POLAR_CRC_TYPE = desc.crc_type
        regs.POLAR_RNTI_CONTEXT = desc.rnti_context
        regs.POLAR_MASK_HASH = desc.mask_hash
    else:
        raise ValueError(desc.family)

    regs.TRACE_MASK = desc.trace_mask
    regs.IRQ_ENABLE = desc.irq_enable
    regs.CONTROL_START = 1

    while not regs.STATUS_DONE:
        if software_timeout():
            regs.CONTROL_ABORT = 1
            break

    status = read_status_error_trace(regs)
    regs.STATUS_CLEAR = 1
    return status
```

这段伪代码有三个重点：第一，所有字段在 `CONTROL_START` 前写完；第二，family-specific 配置只写当前 family；第三，完成后同时读取 status、error 和 trace，不只读一个 `done`。

## 定点化与 RTL/ASIC 映射

| 设计点 | 建议 | 原因 |
|:---|:---|:---|
| 位域宽度 | 宽字段优先独立寄存器，不要硬塞。 | `E/Ncb/Zc/K` 可能超过 16 bit，硬塞会导致截断风险。 |
| 影子寄存器 | `LOCK_DESCRIPTOR` 时复制到 shadow。 | 避免 BUSY 期间软件写入影响运行中的任务。 |
| bad field id | 每个字段分配稳定编号。 | `ERROR_FIRST_BAD_FIELD` 能直接定位非法字段。 |
| hash | 对锁存后的 descriptor 做 hash。 | 软件日志、RTL trace 和 golden model 可比对。 |
| 跨时钟域 | start/status/IRQ 通过同步器或异步 FIFO。 | 配置总线和译码核时钟可能不同。 |
| W1C status | `DONE/ERROR/IRQ` 使用写 1 清。 | 防止读改写清错位。 |
| capability | 只读寄存器由综合参数生成。 | driver 可自动适配精简配置。 |
| trace | trace mask 控制关键字段。 | bring-up 时打开，量产时关闭或降级。 |

RTL 中推荐分成四个块：

1. `reg_file`：处理总线读写、复位、W1C/W1P、只读 capability。
2. `descriptor_locker`：在 start 时复制寄存器、计算 hash、冻结配置。
3. `legality_checker`：组合或短流水检查字段范围和跨字段一致性。
4. `task_controller`：向 Turbo/LDPC/Polar 引擎发 start，收 done/error，更新 status/IRQ/trace。

| 测试 | 输入 | 通过条件 |
|:---|:---|:---|

## 常见错误

| 错误 | 后果 | 防护 |
|:---|:---|:---|
| 把寄存器字段写成 3GPP 强制地址 | 文档误导，实现不可移植。 | 每个字段标来源和边界。 |
| BUSY 期间允许配置直接改 active 寄存器 | 失败不可复现。 | shadow lock + busy write policy。 |
| 只记录 `done` 不记录 `error_code` | 调试只能看到失败，不能分类。 | status/error/trace 三件套。 |
| `list_size` 写成协议值 | 混淆 Polar 协议与实现策略。 | 标注 implementation policy。 |
| `Qm` 不进入 LDPC/bit deinterleaving 上下文 | `E_r` 或 LLR 顺序错误。 | 字段来源表和 directed test。 |
| HARQ ID 和 TB epoch 混用 | 新旧数据串扰。 | soft buffer key hash + NDI 检查。 |
| CBG mask 位序反 | 错误 CBG 被保持或更新。 | MSB->CBG#0 directed test。 |
| 没有 first bad field | 非法配置定位困难。 | legality checker 输出字段编号。 |
| IRQ clear 与 status clear 语义混乱 | 软件漏中断或重复中断。 | W1C 单独验证。 |

## 工业用例

| 用例 | 输入 | 输出 | 边界条件 | 验证方式 | 失败案例 |
|:---|:---|:---|:---|:---|:---|
| 多引擎共享寄存器 bring-up | 连续运行 LTE Turbo、NR LDPC、NR Polar 三类任务。 | 每次 `TRACE_DESC_HASH`、`STATUS_DONE`、family-specific start pulse。 | 三类配置字段不同，未使用字段必须不污染当前任务。 | 寄存器回读、RTL trace 和 golden descriptor hash 对比。 | 上一次 LDPC `Zc` 残留导致 Polar 任务 legality checker 误判。 |

5. `CBG_MASK` 和 `CBGFI` 错了，会优先破坏哪一类接收端行为？
6. `max_iterations` 和 `list_size` 为什么不能写成协议强制数值？
7. `ERROR_FIRST_BAD_FIELD` 比单个 `err=1` 有什么价值？
8. descriptor hash 应该在软件写寄存器前算，还是硬件锁存后算？为什么两边都要有？

## 自测题参考答案

1. 3GPP 规定空口字段和处理规则，不规定芯片内部地址、bit 位、W1C 语义或 IRQ 线。寄存器表是实现接口，必须追溯协议来源但不能冒充协议原文。
2. `COMMON_FAMILY` 来自协议链路和本地任务类型；`LDPC_BG` 是 TS 38.212 派生算法字段；`POLAR_LIST_SIZE` 是 CA-SCL 实现策略。
3. 当前任务已经把配置复制到 shadow。BUSY 中改 active 配置会让同一任务前半段和后半段看到不同参数，失败后无法复现。
4. NR PDSCH/PUSCH 的 `Qm` 由 TS 38.214 的 MCS procedure 得到；它影响 rate matching 输出长度分配和 bit interleaving/deinterleaving 上下文，所以译码任务要能追踪它或追踪由它推导出的 `E_r`/排列。
5. 主要破坏 HARQ soft buffer 和 CBG 部分重传：该保持的 CBG 被覆盖，该合并的 CBG 被跳过，或 CBGFI=0 的损坏旧证据继续参与合并。
6. 协议规定编码结构和验收语义，不规定接收端必须迭代多少次或 SCL list size 取多少。它们是性能、功耗、面积和延迟折中。
7. `err=1` 只能说明失败；`ERROR_FIRST_BAD_FIELD` 能直接定位哪个字段越界或不一致，缩短 bring-up 和现场定位时间。
8. 软件应对准备写入的 descriptor 算 hash，硬件应对锁存后的 shadow descriptor 算 hash。两者一致说明寄存器写入、端序、位域和锁存时序一致；不一致说明边界接口有问题。
