# T2.5 软信息裁剪、缩放与量化预览：浮点 LLR 到定点译码器输入的表示转换
## 本节学习目标

前面几节把接收符号变成对数似然比。理论上，LLR 可以是任意实数，例如 $12.7$、$-3.2$ 或 $0.04$。但真实译码器不可能保存无限精度的小数。软件定点模型、寄存器传输级和专用集成电路都必须用有限位宽表示 LLR。RTL 是硬件设计中描述寄存器和组合逻辑如何按时钟传递数据的层次；ASIC 是把这些逻辑做成专用芯片。

这就引出三个工程动作：

| 动作 | 先这样理解 | 为什么需要 |
|:---|:---|:---|
| 裁剪 | 把过大的浮点 LLR 限制在一个范围内 | 防止极端值支配后续迭代或超过表示范围。 |
| 缩放 | 把浮点 LLR 乘一个比例因子 | 把实数映射到整数网格。 |
| 量化 | 把连续值变成有限个整数 | 硬件和定点模型只能保存有限状态。 |
| 饱和 | 超出整数范围时停在最大/最小值 | 防止溢出绕回造成符号错误。 |


- 解释为什么浮点 LLR 不能直接进入定点译码器。
- 区分裁剪、缩放、量化和饱和。
- 手算一个浮点 LLR 到 6-bit 有符号整数的映射。
- 说明过度自信 LLR、缩放不足 LLR 和符号错误分别会怎样伤害译码。
- 用 Python 复核一个小型量化流程。
- 说清楚本节为什么不是 3GPP 协议强制规则。

## 前置知识检查

| 问题 | 需要达到的程度 |
|:---|:---|
| LLR 的正负号怎么理解？ | 本课程约定正 LLR 更像 `0`，负 LLR 更像 `1`。 |
| 为什么硬件要关心位宽？ | 每增加 1 bit，寄存器、存储器、总线和运算单元都可能变大。 |
| 有符号整数范围怎么来？ | 6-bit 二进制补码通常表示 $[-32,31]$。 |
| 译码器输入是什么？ | 不是硬判决比特，而是一串带符号、带可靠度的软信息。 |

## 无限精度表示的工程不可行性

首先考察一个很具体的问题。软解调器输出 1000 个 LLR。如果每个 LLR 都用 Python 浮点数保存，仿真较为便利。但硬件里每个数都要占寄存器或静态随机存取存储器位宽。

如果每个 LLR 用 32-bit 浮点数，1000 个就是 32000 bit。如果改成 6-bit 有符号整数，1000 个就是 6000 bit。后续低密度奇偶校验码、Turbo或Polar译码器内部还会保存中间消息，位宽差异会迅速放大成面积、功耗和带宽差异。此处仅需知道它们是后续要精读的纠错码家族。

所以定点化不是“为了麻烦而麻烦”。它回答的是：

```text
在性能损失可接受的前提下，用尽可能少的位保存足够可靠的软信息。
```

## LLR 语义复核

本课程约定：

$$
L=\ln\frac{P(b=0\mid y)}{P(b=1\mid y)}
\tag{1}
$$

这个公式回答的问题是：接收证据 $y$ 下，比特更像 `0` 还是更像 `1`。

| LLR | 含义 |
|---:|:---|
| $L>0$ | 更像 `0`。 |
| $L<0$ | 更像 `1`。 |
| $L=0$ | 两边一样像。 |
| $|L|$ 大 | 更有把握。 |
| $|L|$ 小 | 不太确定。 |

定点化必须保护两件事：符号不能错，幅度要大致反映可靠度。符号错通常是灾难；幅度不准会降低性能，严重时也会导致译码失败。

## 浮点范围裁剪

裁剪把 LLR 限制到一个浮点范围。设裁剪上限为 $L_{\max}$，下限为 $L_{\min}$：

$$
L_{\mathrm{clip}}=\min(\max(L,L_{\min}),L_{\max})
\tag{2}
$$

常见对称裁剪写成：

$$
L_{\min}=-L_{\max}
\tag{3}
$$

例如 $L_{\max}=8$：

| 原始 LLR | 裁剪后 |
|---:|---:|
| $12.0$ | $8.0$ |
| $2.7$ | $2.7$ |
| $-8.1$ | $-8.0$ |
| $-12.0$ | $-8.0$ |

裁剪不是随便砍掉信息。它的工程意义是：当 LLR 已经大到“非常可靠”时，继续区分 $8$ 和 $80$ 对有限位宽译码器通常不值得；但如果裁剪太小，又会把真正可靠的信息压弱。

## 缩放和量化：把实数放到整数格点上

裁剪后，下一步是缩放。设缩放因子为 $\alpha$：

$$
u=\alpha L_{\mathrm{clip}}
\tag{4}
$$

然后量化成整数：

$$
q=\mathrm{round}(u)
\tag{5}
$$

如果用 6-bit 有符号整数，常见二进制补码范围是：

$$
q_{\min}=-32,\quad q_{\max}=31
\tag{6}
$$

有些设计会保留一个保护值，实际只用 $[-31,31]$。本节采用：

$$
q_{\min}=-31,\quad q_{\max}=31
\tag{7}
$$

最后做整数饱和：

$$
q_{\mathrm{sat}}=
\min(\max(q,q_{\min}),q_{\max})
\tag{8}
$$

把步骤连起来：

```text
浮点 LLR -> 裁剪 -> 乘缩放因子 -> 四舍五入 -> 整数饱和 -> 定点 LLR
```

## 手算例子：6-bit LLR 量化

设：

$$
L_{\max}=8,\quad \alpha=4,\quad q_{\min}=-31,\quad q_{\max}=31
\tag{9}
$$

对 $L=2.7$：

$$
L_{\mathrm{clip}}=2.7
\tag{10}
$$

$$
u=4\times 2.7=10.8
\tag{11}
$$

$$
q=\mathrm{round}(10.8)=11
\tag{12}
$$

所以定点 LLR 是 $11$。

对 $L=12.0$：

$$
L_{\mathrm{clip}}=8.0
\tag{13}
$$

$$
u=4\times 8.0=32.0
\tag{14}
$$

$$
q=32
\tag{15}
$$

但 $q_{\max}=31$，所以：

$$
q_{\mathrm{sat}}=31
\tag{16}
$$

这就是饱和。正确的饱和会停在边界；错误的溢出可能把 $32$ 变成负数，那会直接把可靠的 `0` 变成可靠的 `1`。

## 三个典型失败案例

### 过度自信 LLR

过度自信指 LLR 幅度太大，译码器几乎不愿意改变这个比特判断。

例如某个比特真实更像 `1`，但前端因为噪声估计过小，给出 $L=+20$。按本课程符号约定，它表示“非常可靠的 `0`”。后续校验约束即使发现矛盾，也可能很难把它拉回来。

工程后果：块错误率曲线可能出现地板，某些错误模式反复不过循环冗余校验。

### 缩放不足 LLR

缩放不足指 LLR 幅度整体太小。比如原始 LLR 是：

$$
(4.0,-2.0,0.6,-0.1)
\tag{17}
$$

如果缩放系数只有 $0.5$：

$$
(2.0,-1.0,0.3,-0.05)
\tag{18}
$$

符号没变，但可靠度变弱。译码器会觉得所有输入都不太可信，需要更多迭代，甚至在低码率或高噪声场景下性能明显下降。

### 符号错误

符号错误最危险。原始 LLR：

$$
(4.0,-2.0,0.6,-0.1)
\tag{19}
$$

对应硬判决：

$$
(0,1,0,1)
\tag{20}
$$

如果接口把符号取反，变成：

$$
(-4.0,2.0,-0.6,0.1)
\tag{21}
$$

硬判决就变成：

$$
(1,0,1,0)
\tag{22}
$$

这不是轻微性能损失，而是系统性错误。高信噪比下仍然大量失败时，LLR 符号约定是第一批要查的项目。

## 定点接口契约与逐位一致验证指标

LLR 量化一旦进入硬件设计，就不能只写“约 6 bit”或“缩放一下”。软件浮点模型、定点 C/C++ 模型、RTL 和验证脚本必须共享同一份接口契约。契约至少要包含：

| 项目 | 必须固定的内容 | 未固定时的典型问题 |
|:---|:---|:---|
| 数值语义 | 正值表示更像 `0` 还是更像 `1`。 | 高信噪比下仍然系统性失败。 |
| 输入范围 | 浮点裁剪上下限。 | 不同模型饱和比例不同。 |
| 缩放因子 | 浮点到整数的比例。 | BLER 曲线整体偏移。 |
| 舍入模式 | 四舍五入、向零截断、向负无穷取整等。 | 逐位一致（bit-exact）对比大量一位差异。 |
| 饱和范围 | 最小值、最大值、是否保留保护值。 | 溢出绕回或边界不一致。 |
| 存储格式 | 二进制补码、符号扩展、写 RAM 的位序。 | 负数被读成大正数，或字节序错位。 |

逐位一致（bit-exact）验证的意思是：同一组输入经过定点参考模型和 RTL 后，每一个输出整数都必须完全一致，而不是“曲线差不多”。对本节量化流程，可以定义最小验收集合：

| 测试类别 | 样本 | 目标 |
|:---|:---|:---|
| 正常值 | $-3.2,-0.2,0,0.2,2.7$ | 验证缩放和舍入。 |
| 裁剪边界 | $-8.1,-8.0,8.0,8.1$ | 验证浮点裁剪。 |
| 饱和边界 | 缩放后等于 $-32,-31,31,32$ 的输入 | 验证整数饱和而非绕回。 |
| 符号扩展 | 负定点 LLR 写入和读出 | 验证 RAM、总线和译码器解释一致。 |

这里要特别注意 Python 的 `round` 规则。Python 3 对 `.5` 的处理是银行家舍入，不一定等同于硬件里常用的“四舍五入到最近整数”或“向零截断”。如果工程实现要逐位一致，就必须在参考模型里显式写出目标舍入规则，不能依赖语言默认行为。

## 和 3GPP 协议的关系

本节是实现基础课，不是协议精读课。后续协议章节会分别在 TS 36.211/38.211 定位调制映射，在 TS 36.212/38.212 定位 CRC、信道编码和速率匹配，在 TS 38.214/36.213 定位调度、混合自动重传请求和调制与编码方案相关流程。本节只说明这些协议输出会约束译码链路，不把 LLR 位宽、裁剪范围或缩放因子写成 3GPP 强制规定。

因此这里要分清：

| 内容 | 是否协议强制 | 本节处理方式 |
|:---|:---:|:---|
| 调制映射、编码结构、速率匹配 | 是，需查 TS 36.211/36.212/38.211/38.212/38.214 等 | 后续具体协议章节精读；本节只标出入口。 |
| LLR 裁剪、缩放、量化位宽 | 通常不是 | 作为接收机实现策略讲解。 |
| 符号约定和接口格式 | 不是空口协议，但必须在工程接口中固定 | 后续 RTL/ASIC 和逐位一致验证继续使用。 |

这并不表示本节不重要。协议定义了译码器要恢复的比特流和 CRC 验收方式；LLR 定点化决定接收机能否把协议允许的传输可靠地译出来。

## 伪代码

```text
for each floating-point LLR L:
    L_clip = min(max(L, -clip), clip)
    scaled = scale * L_clip
    rounded = round(scaled)
    q = min(max(rounded, q_min), q_max)
    write q to decoder input buffer
```

这段伪代码的关键不是 `round` 这一行，而是所有模块必须共享同一套约定：正负号、裁剪范围、缩放因子、整数范围和饱和方式。

## Python 校验片段

```python
def quantize_llr(llr: float, clip: float, scale: float, qmin: int, qmax: int) -> int:
    # Time: O(1), Space: O(1)
    clipped = max(-clip, min(clip, llr))
    rounded = round(scale * clipped)
    return max(qmin, min(qmax, rounded))


def hard_from_llr(llr: float) -> int:
    # Time: O(1), Space: O(1)
    return 0 if llr >= 0.0 else 1


values = [-12.0, -8.1, -3.2, -0.2, 0.0, 0.2, 2.7, 8.1, 12.0]
quantized = [quantize_llr(v, 8.0, 4.0, -31, 31) for v in values]

llrs = [4.0, -2.0, 0.6, -0.1]
hard = [hard_from_llr(v) for v in llrs]
wrong_sign = [hard_from_llr(-v) for v in llrs]

print(quantized)
print(hard)
print(wrong_sign)
```

期望输出：

```text
[-31, -31, -13, -1, 0, 1, 11, 31, 31]
[0, 1, 0, 1]
[1, 0, 1, 0]
```

## 定点和 RTL/ASIC 映射预览

| 层次 | 做什么 | 风险 |
|:---|:---|:---|
| 浮点仿真 | 找到近似最优裁剪和缩放范围 | 只看单点，不看 BLER 曲线。 |
| 定点模型 | 逐位一致实现裁剪、舍入和饱和 | Python 舍入规则和硬件舍入规则不一致。 |
| RTL/ASIC | 比较器、加法器、饱和器、RAM 写入 | 溢出绕回、符号扩展错误、位宽截断。 |
| 验证 | 边界值、随机值、符号约定、饱和比例 | 只测普通值，不测 $q_{\min}$、$q_{\max}$ 附近。 |

硬件里最怕“看起来只是少一位”的错误。比如 6-bit 有符号数如果被当成无符号数解释，负 LLR 会变成很大的正数。

## 常见错误

| 错误 | 为什么错 | 正确做法 |
|:---|:---|:---|
| 把 LLR 当概率量化 | LLR 不是 $[0,1]$ 内的概率。 | 按有符号数处理。 |
| 裁剪范围太小 | 可靠信息被压扁。 | 通过 BLER 和饱和统计选范围。 |
| 缩放因子太大 | 大量饱和，细节丢失。 | 检查饱和比例和性能损失。 |
| 缩放因子太小 | 大多数值接近 0，可靠度不足。 | 检查量化直方图是否集中在 0 附近。 |
| 溢出绕回 | 正大值可能变成负值。 | 使用饱和而不是截断绕回。 |
| 符号约定不统一 | 译码器把 `0`/`1` 置信度反着用。 | 在接口文档、模型和 RTL 中固定正负号。 |

## 自测题

1. 为什么真实译码器不能保留无限精度 LLR？
2. 裁剪和饱和有什么区别？
3. 设 $L=2.7$、$L_{\max}=8$、$\alpha=4$、整数范围 $[-31,31]$，量化结果是多少？
4. 为什么 $L=12.0$ 在上述配置下最后是 31 而不是 32？
5. LLR 符号取反会造成什么现象？
6. 本节为什么不需要直接引用某个 3GPP 量化表？

## 自测题参考答案

1. 因为硬件存储、软缓存、消息 RAM 和运算单元都有有限位宽；无限精度会导致面积、功耗和带宽不可接受。
2. 裁剪发生在浮点 LLR 范围上，例如把 $12.0$ 限制为 $8.0$；饱和发生在整数表示范围上，例如把 32 限制为 31。
3. $L_{\mathrm{clip}}=2.7$，$4\times2.7=10.8$，四舍五入为 11。
4. 因为整数最大值设为 31，32 超出范围，必须饱和到 31。
5. 硬判决会系统性翻转，高信噪比下也可能大量 CRC 失败。
6. 因为 LLR 位宽、裁剪、缩放和饱和通常是接收机实现策略，不是 3GPP 空口协议强制的统一量化表。
