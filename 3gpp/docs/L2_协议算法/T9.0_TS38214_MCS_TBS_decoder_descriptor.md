# T9.0 TS 38.214 MCS/TBS 到译码 Descriptor
## 本节学习目标

本节精读 TS 38.214 Rel-19 `38214-j30` 中与 NR 数据译码规模直接相关的部分：调制与编码方案、调制阶数 $Q_m$、目标码率 $R$、物理资源块、资源元素、层数、传输块大小、冗余版本和码块组如何变成译码器 descriptor。

学完后应能做到：

- 说明 TS 38.214 §5.1.3 为什么是 NR 下行数据译码 descriptor 的上游，而不是 LDPC 算法本身。
- 把 MCS index 查表得到的 $Q_m/R$、TBS procedure 得到的 TBS、RV 字段和 CBG 调度背景翻译成 LDPC rate recovery、soft buffer 和回归向量压力。
- 明确 1024QAM 在 Rel-19 PDSCH 中使用 Table 5.1.3.1-4，而不是旧材料中可疑的 Table 5.1.3.1-3/MCS27 说法。
- 区分进入 Turbo/LDPC/Polar decoder 的字段和只属于系统调度或证据归档的元数据。

## 前置知识检查

| 前置项 | 本节要求 |
|:---|:---|
| LDPC 分段 | 知道 TBS 加 CRC 后会影响 CB 数、BG、Zc、filler。 |
| Rate recovery | 知道 $E_r$、$N_{\mathrm{cb}}$、RV 起点和 $Q_m$ 会影响 LLR 放置。 |
| HARQ soft buffer | 知道重传 LLR 需要按母码位置合并。 |
| MCS | 知道 MCS 是调度选择，不是 decoder core 内部迭代公式。 |
| 协议证据 | 知道表号必须核验本地 Rel-19 资料。 |

若这些概念尚不稳固，核心关系可归结为：MCS/TBS 决定”本次译码任务有多大、每个符号带几个 bit、rate matching 给每个 CB 多少 LLR”；LDPC BP/Min-Sum 决定”拿到这些 LLR 后如何迭代纠错”。

## 资料与协议边界

本节只讲 TS 38.214 的 MCS/TBS 如何影响译码器 descriptor，不把 TS 38.214 写成 LDPC 或 Polar 译码算法。TS 38.214 负责告诉接收端“本次传输规模和调度上下文是什么”；TS 38.212 才负责“这些比特如何被编码和 rate matched”。两者必须合并，但不能混同。

| TS 38.214 MCS tables | `3GPP_Rel19/processed/TS_38.214_38214-j30/tables/*.html/csv` | 本节未完整复现所有 MCS 表值。 |

## MCS/TBS 的核心问题

零基础读者容易把 MCS/TBS 看成“一个更复杂的码率公式”。更准确的理解是：MCS/TBS 先解决资源和任务规模问题。基站调度一次 PDSCH 时，必须让 UE 知道这次传输用了多少资源、每个调制符号带几个编码比特、目标码率大约是多少、这次是初传还是某个 RV 的重传。译码器拿到这些信息后，才能知道要从 LLR 流里切多少数据、每个 CB 该恢复多少母码位置、soft buffer 里该合并哪一段历史证据。

可以把链路分成三层：

| 层 | 问题 | 示例字段 |
|:---|:---|:---|
| 调度层 | 这次 PDSCH 给了多少资源，用哪个 MCS/RV？ | MCS index、RV、PRB、符号数、层数。 |
| 规模层 | 这些资源换算成多少信息 bit 和多少 CB？ | $Q_m$、$R$、$N_{\mathrm{RE}}$、$N_{\mathrm{info}}$、TBS、$C$。 |
| 译码层 | 每个 CB 的 LLR 如何恢复并迭代？ | $E_r$、$N_{\mathrm{cb}}$、$k_0$、BG、$Z_c$、soft buffer key。 |

MCS/TBS 属于前两层，LDPC BP/Min-Sum 属于第三层。若前两层错，第三层即使算法正确，也是在错误的 LLR 边界和矩阵尺寸上工作。

## 资源数量与译码压力的关系

想象有一排固定数量的 RE。每个 RE 可以放一个调制符号。若使用 QPSK，一个符号承载 2 个编码比特；若使用 16QAM，一个符号承载 4 个编码比特；若使用 1024QAM，一个符号承载 10 个编码比特。资源数量不变时，$Q_m$ 越大，demapper 输出的 bit LLR 越多，rate recovery 需要处理的 bit-channel 顺序也越密。

目标码率 $R$ 决定“这些编码比特里大约有多少信息量”。高 $R$ 表示冗余少，单位资源承载的信息多，但纠错余量小；低 $R$ 表示冗余多，单位资源承载的信息少，但抗噪声能力更强。TBS procedure 的作用是把“资源数量、调制阶数、目标码率、层数”变成一个合法 TB 大小，而不是让实现随便取一个实数。

接收端工程压力来自三个方向：

| 方向 | 直觉 | 工程表现 |
|:---|:---|:---|
| LLR 数量 | $Q_m$ 和 RE 越大，本次输入 LLR 越多。 | DMA、deinterleaver、soft buffer 写带宽增大。 |
| CB 数量 | TBS 越大，TB 越可能被分成多个 CB。 | LDPC core 并行调度、CB CRC、CBG 状态和回归向量数量增加。 |
| 有效码率 | $R$ 高或 puncturing 多时，冗余少。 | 译码迭代更紧张，失败定位更依赖正确 LLR scaling 和 rate recovery。 |

这也是本节反复强调 descriptor 的原因。MCS/TBS 的输出不是给人看的备注，而是译码器每次任务的边界条件。

## 符号来源和推导链

本节用到的核心符号并不多，但必须知道它们回答的问题：

| 符号 | 问题 | 来源 |
|:---|:---|:---|
| $I_{\mathrm{MCS}}$ | DCI 给出的 MCS index 是多少？ | PDCCH/DCI 调度结果。 |
| $Q_m$ | 一个调制符号承载几个编码 bit？ | MCS table 查表。 |
| $R$ | 目标码率是多少？ | MCS table 查表，通常以 `x1024` 存表。 |
| $N_{\mathrm{RE}}$ | 本次 PDSCH 有多少可用数据 RE？ | PRB、符号数、DM-RS、overhead。 |
| $\nu$ | 几个传输层？ | 调度和 MIMO 配置。 |
| $N_{\mathrm{info}}$ | 未量化的信息量估计是多少？ | $N_{\mathrm{RE}}Q_mR\nu$。 |
| TBS | 合法 TB 大小是多少？ | TS 38.214 TBS 量化过程。 |
| $C$ | TBS 加 CRC 后分几个 CB？ | TS 38.212 segmentation。 |
| $E_r$ | 第 r 个 CB 本次发送/接收多少 coded bits？ | rate matching 和资源分配。 |

推导链的关键不是公式本身，而是对象边界：

$$
I_{\mathrm{MCS}} + \mathrm{table\ selection}
\rightarrow (Q_m, R)
\tag{1}
$$

$$
(N_{\mathrm{RE}}, Q_m, R, \nu)
\rightarrow N_{\mathrm{info}}
\rightarrow \mathrm{TBS}
\tag{2}
$$

$$
\mathrm{TBS}
\rightarrow (C, K_r, BG, Z_c, F)
\rightarrow (E_r, N_{\mathrm{cb}}, k_0)
\tag{3}
$$

式 (1) 属于 TS 38.214 MCS table selection；式 (2) 属于 TS 38.214 TBS determination；式 (3) 开始进入 TS 38.212 LDPC segmentation 和 rate matching。把这三段混成一个“大公式”，就是很多 descriptor 错误的来源。

## MCS/TBS 的协议前因后果

TS 38.214 §5.1.3 的下行流程可以压缩为三步：

1. UE 读取 DCI 中的 5-bit MCS field，用 §5.1.3.1 的表选择过程得到 $Q_m$ 和 $R$。
2. UE 读取 DCI 中的 RV field，得到 redundancy version。
3. UE 使用层数 $\nu$、allocated PRB、RE 计算和 §5.1.3.2 的 TBS procedure 得到 TBS。

这些动作还没有进入 LDPC 迭代器。它们是在为译码器准备“任务规模”和“速率恢复上下文”。接收端后续会把 TBS 交给 TS 38.212 §5.2.2 做分段，把 $Q_m/R$ 和资源数量转换为每个 CB 的 $E_r$，把 RV 转换为 LDPC circular buffer 起点 $k_0$，把 CBG/CBGTI 转换为哪些 CB 本次有新 LLR。

## 从 MCS 到 $Q_m/R$

MCS index 不是码率本身，它是查表索引。不同 MCS table 下，同一个 index 可能对应不同 $Q_m$ 和 $R$。接收端 descriptor 不应只保存 `mcs_index`，至少还要保存上游已经解析出的：

| 字段 | 含义 | 为什么进入 descriptor |
|:---|:---|:---|
| `mcs_table_id` | 使用 Table 5.1.3.1-1/2/3/4 中哪一张或上行对应表 | 复现调度决策和 debug。 |
| `mcs_index` | DCI 中的 MCS field 值 | 回放向量和日志定位。 |
| `Qm` | 每个调制符号承载的编码 bit 数 | bit deinterleaving、LLR 分组、$E_r$ 计算。 |
| `R_x1024` | 目标码率乘以 1024 的表值 | TBS、BG 选择和有效码率检查。 |
| `rv` | redundancy version | rate recovery circular buffer 起点和 soft combining。 |

例如，1024QAM 表项在本地 `tables/table_0035.csv` 中作为 CQI table 出现了 1024QAM 行，但 PDSCH MCS 的规范表号仍必须按 §5.1.3.1 的 Table 5.1.3.1-4 口径记录。不要用文件名或表抽取编号替代表号。

## TBS 计算链路的必要子集

TS 38.214 §5.1.3.2 的 TBS determination 很长，本节只保留译码 descriptor 必需链路：

| 步骤 | 变量 | 译码意义 |
|:---|:---|:---|
| 计算每 PRB 可用 RE | $N'_{\mathrm{RE}}$ | 扣除 DM-RS 和 overhead 后得到可承载数据的 RE。 |
| 限制每 PRB RE 上界并乘 PRB 数 | $N_{\mathrm{RE}}$ | 得到本次 PDSCH 数据 RE 总数。 |
| 未量化信息量 | $N_{\mathrm{info}} = N_{\mathrm{RE}} \cdot R \cdot Q_m \cdot \nu$ | 决定 TBS 量级。 |
| TBS 量化/查表 | TBS | 交给 TS 38.212 TB CRC 和 LDPC segmentation。 |
| CB 分段 | $C$、$K_r$、BG、$Z_c$ | 决定 decoder 并行任务数和矩阵规模。 |
| 每 CB rate matching | $E_r$、$N_{\mathrm{cb}}$、$k_0$ | 决定本次 LLR 如何放回母码位置。 |

注意 $N_{\mathrm{info}}$ 只是中间量。真实 TBS 需要按协议量化规则和表格过程得到，不能把 $N_{\mathrm{info}}$ 直接当 TBS。

## 小型数值例子

假设一个教学 PDSCH 任务：

| 字段 | 值 |
|:---|:---|
| `mcs_table_id` | Table 5.1.3.1-2 |
| `mcs_index` | 10 |
| 查表结果 | $Q_m=6$，$R=466/1024$ |
| allocated PRB | 10 |
| 每 PRB 可用 RE | 120 |
| layer count | $\nu=1$ |

教学化计算：

$$
N_{\mathrm{RE}} = 10 \times 120 = 1200
\tag{4}
$$

$$
N_{\mathrm{info}} = 1200 \times 6 \times \frac{466}{1024} \times 1 \approx 3276.56
\tag{5}
$$

协议接下来会按 §5.1.3.2 的 TBS 量化流程得到合法 TBS。接收端随后把 TBS 交给 TS 38.212：

```text
TBS -> TB CRC -> LDPC BG selection -> CB segmentation -> Zc/filler
    -> 每个 CB 的 E_r/Ncb/k0 -> rate recovery -> LDPC decoder
```

这个例子故意不声称最终 TBS 数值，因为本节没有复现完整 TBS quantization table。若未来要做 bit-exact conformance 向量，必须把 §5.1.3.2 的全部分支、表格和边界条件脚本化。

## Rel-19 最大 TB/CB 压力的工程含义

Rel-19 支持高阶调制、更高带宽和多层传输时，decoder 压力不是单个字段造成的，而是多个字段叠加：

| 压力来源 | 对 decoder 的影响 |
|:---|:---|
| 高 $Q_m$，例如 1024QAM 的 $Q_m=10$ | demapper 输出更多 bit-channel LLR，bit interleaving 和 LLR 排序错误更难定位。 |
| 大 PRB / 大 RE | TBS 增大，CB 数可能增加，soft buffer 和回归向量尺寸增大。 |
| 多层 $\nu$ | 同一时隙内可能有更多数据并行到达，吞吐压力上升。 |
| CBG 部分重传 | soft buffer 不能只按 TB 粗粒度 flush，要按 CB/CBG 维护状态。 |
| RV 重传 | rate recovery 必须把不同 RV 覆盖区域合并到同一母码地址空间。 |

没有真实 Rel-19 最大吞吐仿真日志时，本节只写压力模型，不写“本项目已满足最大吞吐”。

## 常见错误

| 错误 | 后果 | 防止方法 |
|:---|:---|:---|
| 把 1024QAM 写成 Table 5.1.3.1-3/MCS27 | 表号和码率来源错，后续 descriptor 无法追溯。 | 固定写 Table 5.1.3.1-4，并引用 `content.md:1263-1269`。 |
| 只保存 MCS index，不保存 table id | 同一 index 在不同表下含义不同。 | descriptor 同时保存 `mcs_table_id`、`mcs_index`、`Qm`、`R_x1024`。 |
| 把 $N_{\mathrm{info}}$ 当 TBS | TBS 不合法，CB segmentation 全错。 | 必须执行 §5.1.3.2 量化流程。 |
| 把 CBG mask 当 LDPC 算法字段 | 混淆调度和 decoder core。 | CBG 是 soft buffer/HARQ 粒度字段，不改变 LDPC parity-check matrix。 |
| Polar 控制任务复用 LDPC TBS descriptor | A/K/E/N、CRC/RNTI 和 frozen mask 缺失。 | Polar 单独 descriptor。 |

## 自测题

1. 为什么 `mcs_index=10` 不能独立决定 $Q_m/R$？
2. 1024QAM PDSCH 在 Rel-19 中应核验哪张 MCS 表？
3. $N_{\mathrm{info}}$ 与 TBS 的关系是什么？
4. CBG mask 会不会改变 LDPC parity-check matrix？

## 自测题参考答案

1. 因为同一个 MCS index 在不同 MCS table 中可能对应不同调制阶数和目标码率，必须同时知道 table id。
2. 应核验 TS 38.214 Table 5.1.3.1-4；本地 `content.md:1263-1269` 明确 qam1024 使用该表。
3. $N_{\mathrm{info}}$ 是由 RE、$Q_m$、$R$ 和层数得到的未量化中间量；TBS 还要按 §5.1.3.2 的量化和表格规则得到。
4. 不会。CBG mask 决定哪些 CB/CBG 本次调度或重传，影响 soft buffer 和 rate recovery，不改变 LDPC 校验矩阵结构。
