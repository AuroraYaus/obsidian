# T7.4 LTE 码块重组与传输块 CRC
## 本节学习目标

本节讨论 LTE Turbo（Turbo 码，Turbo Code）接收链路的最后一段：多个码块译码完成以后，接收端怎样检查码块级循环冗余校验、删除码块 CRC（循环冗余校验，Cyclic Redundancy Check）、删除分段 filler、按码块编号重组传输块，最后再用 TB（传输块，Transport Block）CRC 决定是否交付。


- 区分码块CRC 和 TB CRC 的职责。
- 说明 [[T3.3_LTE_Turbo_segmentation_rules|T3.3]] 中 $K_-$ 短块在前、$K_+$ 长块在后的重组影响。
- 解释第 0 个 CB（码块，Code Block）开头 filler 为什么必须删除，且只能在重组阶段按 mask 删除。
- 说明打孔或本次未发送位置已经在 Turbo 译码前作为未知软信息处理，不能在重组阶段再当 filler 删除。
- 写出 LTE Turbo 译码后处理的接收端伪代码，并说明混合自动重传请求失败路径如何使用最终结果。
- 分析单个 CB 失败、所有 CB 通过但 TB CRC 失败、filler 处理错误三类失败。

## 前置知识检查

| 前置项 | 本节需要达到的程度 |
|:---|:---|
| LTE Turbo 分段 | 知道大 TB 可拆成多个 CB，且 $K_-$ 块在前、$K_+$ 块在后。 |
| 对数似然比 | 知道 Turbo 译码器输入是软信息，输出硬判决比特和可靠度。 |
| CRC | 知道 CRC 是错误检测，不是纠错；CRC 通过不等于绝对无错。 |
| filler bit | 知道分段 filler 是协议占位，不是业务数据。 |
| HARQ（混合自动重传请求，Hybrid Automatic Repeat Request） | 知道 HARQ 会根据译码结果反馈成功或失败。 |

一句话概括：CB CRC 先判断局部块是否可信，TB CRC 再判断整包拼接是否可信；两层 CRC 中间必须正确删除 CB CRC 和 filler。

## 资料与协议边界

| 协议位置 | 本地证据 |
| :--- | :--- |
| TS 36.212 Rel-19 `36212-j30` §5.1.1 | `3GPP_Rel19/processed/TS_36.212_36212-j30/content.md` |
| TS 36.212 §5.1.2 | `3GPP_Rel19/processed/TS_36.212_36212-j30/sections.jsonl` |
| TS 36.212 §5.2.2.1-§5.2.2.5 | `content.md` lines around uplink shared-channel processing |
| TS 36.212 §5.3.2.1-§5.3.2.5 | `content.md` lines around downlink shared-channel processing |
| T3.3 本地讲义 | `docs/L1_基础/T3.3_LTE_Turbo_segmentation_rules.md` |

协议前因后果是：发送端先给 TB 附加 TB CRC，再按 §5.1.2 分段并在需要时给每个 CB 附加 CB CRC；每个 CB 独立 Turbo 编码、速率匹配和传输。接收端必须先把每个 CB 恢复到 Turbo 译码器输入，再逐 CB 译码，最后按分段时的 $r$ 顺序重组。重组不是实现偏好，而是发送端分段顺序的逆操作。

本节的协议边界也要明确：TS 36.212 规定比特处理顺序、CRC 位置和分段关系；它不规定某个芯片必须如何并行调度 CB、如何设计写回仲裁、如何生成错误日志。这些属于工程实现策略，但实现策略必须保持协议位序不变。

## 名称来源与工程动机

“重组”这个词容易让人以为只是把数组拼起来。LTE Turbo 接收端的重组更严格：它是发送端“分段”的逆过程。发送端为了让每个块满足 Turbo 内部交织器的合法长度，把一个 TB CRC 后的序列切成若干 CB，并在必要时插入 filler、追加 CB CRC。接收端要恢复的不是“几个译码器输出的任意集合”，而是分段前的同一个 TB CRC 后序列。

工程上需要重组有三个原因。第一，Turbo 译码通常按 CB 独立运行，输出自然分散在多个 buffer。第二，CB CRC 只服务于局部验收，不属于最终交付的数据。第三，filler 是为了协议长度而加的占位，若留在 TB 中，上层会收到发送端从未发送过的假数据。因此，重组阶段必须同时处理顺序、删除和最终验收。

## 两层 CRC 的职责边界

CRC 在本节有两层，不要混成一个信号。

| 层级 | 附加位置 | 检查位置 | 失败含义 | 接收端动作 |
|:---|:---|:---|:---|:---|
| CB CRC | 分段后，每个 CB 末尾，只有 $C>1$ 时出现 | 每个 CB Turbo 译码后 | 某个局部块不可信 | 标记该 CB fail，通常不交付 TB。 |
| TB CRC | 分段前，整个 TB 末尾 | 所有 CB 重组后 | 整个 TB 候选不可信 | 向 HARQ 流程报告失败，不交付上层。 |

CB CRC 的工程价值是局部定位。若 CB3 失败，接收端可以知道问题集中在 CB3 的软信息、解速率匹配、Turbo 译码或 CRC 检查链路。TB CRC 的工程价值是最终验收。即使每个 CB 的局部 CRC 都通过，拼接顺序、filler 删除或 TB CRC 自身处理错，仍可能导致 TB CRC 失败。

## 接收端重组的对象

Turbo 译码器输出的是每个 CB 的硬判决序列。对第 $r$ 个 CB，可记为：

$$
\hat{\mathbf{c}}_r =
\left[
\hat{c}_{r,0},\hat{c}_{r,1},\ldots,\hat{c}_{r,K_r-1}
\right]
\tag{1}
$$

其中 $K_r$ 是该 CB 的 Turbo 输入长度。这个长度可能包含三类内容：

| 内容 | 出现条件 | 是否属于最终 TB |
|:---|:---|:---|
| 分段 filler | 只在第 0 个 CB 开头，且 $F>0$ | 不属于，必须删除。 |
| CB payload | 每个 CB 都有 | 属于 TB CRC 后的比特序列。 |
| CB CRC | $C>1$ 时每个 CB 末尾有 24 bit | 不属于最终 TB payload，检查后删除。 |

这就解释了为什么不能直接把所有 $\hat{\mathbf{c}}_r$ 串起来。正确重组要先按每个 CB 的描述符剥离局部 CRC，再删除第 0 个 CB 开头的 filler，最后恢复 $B$ bit 的 TB CRC 后序列。

## 三种空洞的边界

LTE Turbo 接收链路中有三种容易混淆的“空”。

| 名称 | 所在阶段 | 语义 | 接收端处理 |
|:---|:---|:---|:---|
| 分段 filler | TS 36.212 §5.1.2，CB 输入开头 | 占位，使 CB 长度落到合法 $K$ | 参与 CRC 计算时按 0 口径处理，重组时删除。 |
| 子块交织 `<NULL>` | TS 36.212 §5.1.4.1.1，速率匹配矩阵 | 矩阵补位，不是编码信息位 | 构造循环缓存时跳过，不交给 Turbo 译码为业务位。 |
| 打孔/未发送位置 | 速率匹配选择后 | 本次传输没有收到该编码比特 | Turbo 译码前作为未知或擦除软信息，不能在重组阶段删除。 |

打孔位置不是 filler。若某个校验比特本次没发送，它仍然是编码码字中的一个位置，只是接收端没有观测值。HARQ 重传可能在另一个冗余版本中补充该位置的 LLR（对数似然比，Log-Likelihood Ratio）。若在重组阶段把它当 filler 删除，会改变 CB 的位序，破坏 Turbo 译码和 TB CRC。

## 数值例子：两个 CB 的重组

沿用 [[T3.3_LTE_Turbo_segmentation_rules|T3.3]] 的边界例子：$B=6145$，分段后 $C=2$、$L=24$、$K_-=3072$、$K_+=3136$、$C_-=1$、$C_+=1$、$F=15$。因此：

| CB 编号 | 长度 | 开头 filler | 末尾 CB CRC |
|---:|---:|---:|---:|
| 0 | 3072 | 15 bit | 24 bit |
| 1 | 3136 | 0 bit | 24 bit |

CB0 的有效 payload 长度为：

$$
P_0=3072-15-24=3033
\tag{2}
$$

CB1 的有效 payload 长度为：

$$
P_1=3136-24=3112
\tag{3}
$$

重组后长度为：

$$
P_0+P_1=3033+3112=6145=B
\tag{4}
$$

这个例子说明三个细节。第一，CB0 是 $K_-$ 短块，CB1 是 $K_+$ 长块，短块在前。第二，filler 只删 CB0 开头 15 bit，不删 CB1。第三，两个 CB 的 CRC 都在各自末尾删除，而不是把所有 CB 拼起来以后统一删除 48 bit。

## 接收端流程

```text
输入：
  cb_desc[r]：每个 CB 的 K_r、filler_count、cb_crc_len、r
  decoded_bits[r]：Turbo 译码器输出的硬判决

流程：
  1. 按 r 从小到大读取 CB 描述符。
  2. 对每个 CB 执行 CB CRC 检查；若 C=1，则没有 CB CRC。
  3. 若任一 CB CRC fail，记录失败 CB 和首个错误证据，不交付 TB。
  4. 删除每个 CB 末尾的 CB CRC。
  5. 删除第 0 个 CB 开头的 filler_count 个位置。
  6. 按 r=0,1,...,C-1 拼接剩余比特，得到 TB CRC 后候选。
  7. 对候选执行 TB CRC 检查。
  8. TB CRC pass 则删除 TB CRC 并交付；fail 则触发 HARQ 失败路径。
```

注意第 6 步必须按 $r$ 顺序。硬件并行译码时 CB1 可能先完成，但完成时间不能改变重组顺序。

## Python 参考片段

```python
def reassemble_lte_turbo_cb(
    decoded_blocks: list[list[int]],
    filler_count: int,
    cb_crc_len: int,
) -> list[int]:
    """Reassemble decoded CB payloads. Time: O(N), Space: O(N)."""
    payload: list[int] = []
    for cb_index, bits in enumerate(decoded_blocks):
        end = len(bits) - cb_crc_len if cb_crc_len else len(bits)
        body = bits[:end]
        if cb_index == 0 and filler_count:
            body = body[filler_count:]
        payload.extend(body)
    return payload


cb0 = [0] * 15 + [1] * 3033 + [9] * 24
cb1 = [2] * 3112 + [8] * 24
tb_candidate = reassemble_lte_turbo_cb([cb0, cb1], filler_count=15, cb_crc_len=24)
assert len(tb_candidate) == 6145
assert tb_candidate[:3] == [1, 1, 1]
assert tb_candidate[-3:] == [2, 2, 2]
print("T7.4_REASSEMBLY_OK")
```

## 浮点仿真方案

| 仿真层 | 输入 | 输出 | 验收 |
|:---|:---|:---|:---|
| 尺寸层 | [[T3.3_LTE_Turbo_segmentation_rules|T3.3]] 分段描述符 | $K_r$、$F$、$L$、$C$ | 与协议尺寸模型一致。 |
| 译码层 | 每个 CB 的浮点 LLR | 每个 CB 硬判决和 CRC 状态 | 单 CB 错误能定位到 CB 编号。 |
| 重组层 | decoded CB bit arrays | TB CRC 后候选 | 长度等于 $B$，位序按 $r$。 |
| 端到端层 | 多 SNR（信噪比，Signal-to-Noise Ratio）点链路仿真 | TB CRC pass/fail、块错误率 | 高 SNR 下 BLER（块错误率，Block Error Rate）下降，错误案例可复现。 |

## 定点化策略

重组本身主要处理 bit 和 descriptor，不是复杂定点运算。但定点译码会影响 CRC 结果。

| 对象 | 定点风险 | 策略 |
|:---|:---|:---|
| LLR 量化 | 饱和导致 CB CRC fail 概率变化 | 记录输入 LLR 位宽和缩放。 |
| 译码输出 | 硬判决符号约定错 | 在 CB CRC 前做 bit-exact 对比。 |
| CRC 输入 | filler mask 错 | CRC 输入 dump 同时记录 bit 和 mask。 |
| 重组 buffer | 写地址错或乱序写回 | descriptor 中保存 `cb_id` 和 output base。 |

## 硬件映射

寄存器传输级实现通常把本节逻辑拆成四个单元：CB 状态表、CRC 检查单元、payload 写回单元和 TB CRC 单元。专用集成电路实现还会考虑多 CB 并行写回和片上存储 bank。

| 硬件对象 | 输入 | 输出 | 检查点 |
|:---|:---|:---|:---|
| CB status table | `cb_id`、CRC pass/fail、timeout | all-pass 标志 | 任一 CB fail 必须阻止 TB 交付。 |
| payload writer | decoded bits、filler_count、cb_crc_len | TB candidate buffer | 写地址按 $r$ 顺序，不按完成顺序。 |
| TB CRC unit | TB CRC 后候选 | TB pass/fail | 只在所有 CB pass 后启动。 |
| error reporter | CB fail、TB fail、timeout | HARQ/NACK 原因 | 日志包含 CB 编号和配置。 |

## 验证方法

| 用例 | 注入方式 | 期望结果 |
|:---|:---|:---|
| 单 CB CRC fail | 翻转 CB1 的一个 payload bit | CB1 fail，TB CRC 不应作为成功依据。 |
| 全 CB pass 但拼接错 | 交换 CB0/CB1 写回顺序 | CB CRC pass，TB CRC fail。 |
| filler 未删除 | 保留 CB0 开头 filler | TB CRC fail，输出长度错误。 |
| 打孔位置误删 | 在重组阶段删除未知软信息位置 | 长度和位序错误，TB CRC fail。 |
| 乱序完成 | CB1 先完成、CB0 后完成 | 最终仍按 $r$ 拼接。 |

## 失败案例

独立列出失败案例的目的，是让调试日志能直接落到“哪一层的逆操作错了”，而不是只看到最后一个 TB CRC fail。

| 失败案例 | 典型现场 | 根因判断 | 必留证据 | 修复方向 |
|:---|:---|:---|:---|:---|
| 单个 CB CRC fail | CB1 fail，CB0 pass，TB 未交付 | 多数问题发生在 CB1 的 soft input、Turbo 译码、CB CRC 输入或硬判决符号 | `cb_id=1`、CB LLR 摘要、译码迭代数、CB CRC syndrome、首个 mismatch | 先定位 CB1，不要把 TB 重组作为第一怀疑对象。 |
| 全部 CB CRC pass 但 TB CRC fail | 每个 CB 局部通过，最终 TB fail | 拼接顺序、CB CRC 删除、filler 删除、TB CRC 输入范围或 bit 端序错误 | 每个 CB 的 payload 长度、写入 base address、TB candidate 长度、TB CRC 输入 dump | 用 $r=0,1,\ldots,C-1$ 的协议顺序重组，重查删除长度。 |
| CB0 filler 未删除 | TB candidate 比 $B$ 长，前部多出占位位 | 把分段 filler 当作业务位保留 | `filler_count`、CB0 删除前后前 32 bit、重组长度 | 只删除第 0 个 CB 开头的 filler，不删除其他 CB。 |
| 误删打孔或未观测位置 | 重组长度可能看似接近，但位序错 | 混淆“译码前未知软信息”和“分段 filler” | unknown mask、filler mask、重组前 decoded CB 长度 | 打孔/未观测位置属于译码输入侧问题，重组阶段不能删除。 |
| 按完成顺序拼接 | 高并行硬件中偶现 TB CRC fail | CB1 先完成时被写到 CB0 区域 | `cb_id`、completion order、write base、TB CRC dump | 写回地址由 `cb_id=r` 决定，不由完成时间决定。 |
| C=1 时误删 CB CRC | 单 CB 场景长度少 24 bit | 把多 CB 的 CB CRC 规则套到单 CB | `C`、`cb_crc_len`、TB CRC 输入长度 | 只有 $C>1$ 才有每 CB 的 24 bit CRC。 |

## 常见错误

| 错误 | 后果 | 修正 |
|:---|:---|:---|
| 把 CB 译码完成顺序当拼接顺序 | TB 位序错，TB CRC fail。 | 永远用 `cb_id=r` 排序。 |
| 把 filler 当业务 0 保留 | TB 多出占位位。 | 用 mask 删除第 0 个 CB 开头 filler。 |
| 把未发送位置当 filler 删除 | CB 位序改变。 | 未发送位置在译码前用软信息缺省值处理。 |
| 只看 CB CRC | 拼接错误可能漏过局部检查。 | 最终必须检查 TB CRC。 |
| C=1 时仍删除 CB CRC | 单 CB 场景长度错。 | 只有 $C>1$ 时 `cb_crc_len=24`。 |

## 工程思考题

1. 为什么 CB CRC pass 不能替代 TB CRC pass？
2. 为什么 $K_-$ 和 $K_+$ 的顺序会影响接收端重组？
3. 如果两个 CB 都 pass，但 TB CRC fail，优先检查哪些模块？
4. 分段 filler 和打孔位置的接收端处理有什么根本差别？
5. RTL（寄存器传输级，Register Transfer Level）中为什么要保存 `cb_id`，而不是按完成顺序写回？

## 工程思考题参考答案

1. CB CRC 只验证局部块，不能验证多个 CB 的拼接顺序、filler 删除和 TB 级 CRC 位。
2. 分段时按 $r$ 顺序把 $K_-$ 短块放在前面，接收端若顺序相反会重建出不同 TB 位序。
3. 检查拼接顺序、filler 删除、CB CRC 删除长度、TB CRC 输入范围和 bit 端序。
4. filler 是分段占位，重组时删除；打孔位置是编码比特未观测，译码前作为未知软信息保留在码字位置。
5. 并行译码完成顺序受信道质量和迭代次数影响，不等于协议顺序。

## 自测题

1. LTE Turbo 多 CB 场景下 CB CRC 长度是多少？
2. $F>0$ 时 filler 位于哪个 CB 的哪个位置？
3. 本节例子中 $K_-=3072$、$K_+=3136$ 时哪个 CB 在前？
4. TB CRC fail 一定意味着某个 CB CRC fail 吗？
5. 打孔位置能否在重组阶段删除？

## 自测题参考答案

1. 24 bit。
2. 第 0 个 CB 开头。
3. $K_-$ 短块对应的 CB0 在前。
4. 不一定。也可能是拼接顺序、filler 删除、TB CRC 输入或 CRC 实现错误。
5. 不能。它在译码前作为未知软信息处理，不是重组阶段的占位删除对象。
