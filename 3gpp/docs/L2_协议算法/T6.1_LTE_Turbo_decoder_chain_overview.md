# T6.1 LTE Turbo 译码链路总览
## 本节学习目标

本节从接收机已经得到软信息的位置开始，建立 LTE Turbo（Turbo 码，Turbo Code）译码链路的完整地图。软信息在本课程中用对数似然比表示，它不是已经判定为 0 或 1 的硬比特，而是“更像 0 还是更像 1，以及有多可靠”的数字。LLR（对数似然比，Log-Likelihood Ratio）为正通常表示更像 0，LLR 为负通常表示更像 1，绝对值越大表示接收机越有把握。

学完本节后，应能完成四件事：

- 画出从 LLR 输入到传输块判决的 LTE Turbo 接收侧逆流程。
- 说明码块在链路中的作用，以及码块级循环冗余校验和 TB（传输块，Transport Block）级 CRC（循环冗余校验，Cyclic Redundancy Check）的判决层级。
- 区分三类空洞：[[T3.3_LTE_Turbo_segmentation_rules|T3.3]] 讲过的码块填充比特（filler bit）、子块交织矩阵中的 `<NULL>`、速率匹配和冗余版本造成的未发送位置。
- 把 TS 36.212 Rel-19 `36212-j30` 的章节、图、表翻译成接收端工程动作，而不是只背协议索引。

如果只记住一句话：LTE Turbo 接收不是“把 LLR 扔进译码器”这么简单，而是先把发送端的 CRC、分段、编码、子块交织、循环缓存、比特选择逐步反过来，恢复出每个 CB（码块，Code Block）的三路 Turbo 软输入，再由 Turbo 译码、CB CRC、CB 拼接和 TB CRC 给出最终判决。

## 前置知识检查

| 前置项 | 本节需要达到的程度 |
|:---|:---|
| LLR | 知道正负号表示比特倾向，绝对值表示可靠度。 |
| CRC | 知道它用于检错，不用于纠错本身。 |
| TB 和 CB | 知道大 TB 会被拆成一个或多个 CB 独立编码和译码。 |
| Turbo 码 | 知道它是 LTE 数据传输使用的主要信道编码之一，本节只做链路总览。 |
| 混合自动重传请求 | 知道重传会带来软信息合并和冗余版本选择。 |

一个容易混淆的起点是“解调器输出的是比特”。严格说，软解调器输出的是 LLR，硬判决比特只是后续根据 LLR 符号做出的选择。Turbo 译码器需要的是 LLR 这类软信息，因为它要利用可靠度在多次迭代中修正判断。

## 历史角色与系统背景

Turbo 码在 LTE 里不是一个“和 NR LDPC（低密度奇偶校验码，Low-Density Parity-Check Code）对比时顺手提到”的旧名词，而是 LTE 数据业务接收链的主线编码。TS 36.212 Table 5.1.3-1 把上行共享信道、下行共享信道、寻呼信道（Paging Channel, PCH）、多播信道（Multicast Channel, MCH）以及部分 sidelink 传输信道归入 Turbo coding；接收端只要处理这些 LTE 传输信道，就必须先恢复 Turbo 码块，再谈 CB CRC、TB CRC 和 HARQ（混合自动重传请求，Hybrid Automatic Repeat Request）反馈。

从历史和硬件时代看，Turbo 码的意义在于它把并行级联卷积码（Parallel Concatenated Convolutional Code, PCCC）、内部交织器和迭代软输入软输出（Soft-Input Soft-Output, SISO）译码结合起来，在 3G/4G 时代提供了接近信道容量的长块性能。LTE 标准化时，基站和终端 ASIC（专用集成电路，Application-Specific Integrated Circuit）能接受若干个 SISO（软入软出，Soft-Input Soft-Output）核、交织地址发生器、外信息存储和 HARQ 软缓存（soft buffer）的组合；系统峰值吞吐、载波带宽、多输入多输出（Multiple-Input Multiple-Output, MIMO）层数和码块规模也与这种架构相匹配。因此本课程讲 LTE 译码时，T6/T7 的 Turbo 链路应被当作完整主线，而不是 NR LDPC 的附录。

NR 后续把数据业务主码换成 LDPC，原因也不应写成绝对优劣。更准确的工程背景是：NR 面向更高峰值吞吐、更灵活的带宽和更强并行硬件，准循环（Quasi-Cyclic, QC）LDPC 的提升值（lifting size）、分层调度（layered schedule）、规则化矩阵存储和大规模并行校验节点（check node）/ 变量节点（variable node）更新更贴合这些目标；LTE Turbo 的网格图（trellis）递推、交织访存和多轮 SISO 交换在高吞吐扩展上更吃紧。换到 LTE 场景内，Turbo 仍然是协议指定的数据传输主线，接收端不能因为 NR 采用 LDPC 就简化或跳过 Turbo rate recovery 与迭代译码。

## 协议链路在接收端的位置

LTE 下行或上行数据到达 Turbo 译码链路之前，接收机已经做过同步、信道估计、均衡、层解映射、解调和软解调。到本节起点时，输入可以抽象为一串 LLR：

$$
\mathbf{L}^{\mathrm{rx}}=\left[L_0,L_1,\ldots,L_{E-1}\right]
\tag{1}
$$

这个公式回答的问题是“译码链路最早看到的数据是什么”。其中 $E$ 是本次传输实际承载的编码比特数，$L_j$ 是第 $j$ 个接收编码比特的软可靠度。$E$ 不是原始 TB 长度，也不是某个 CB 的 Turbo 母码长度，因为速率匹配可能打孔、重复和选择不同冗余版本。

接收端逆流程可以用以下图表示：

```mermaid

    B --> C["解速率匹配"]

    D --> E["子块解交织"]
    E --> F["三路 Turbo 软输入"]
```

## 发送端顺序与接收端逆序

理解逆流程的关键是把发送端和接收端逐项配对。协议章节大多按发送端生成顺序写，因为空口要定义“发什么”。接收机实现则按逆序恢复“原本是什么”。

| 发送端协议动作 | 发送端输出 | 接收端逆动作 | 接收端输出 |
|:---|:---|:---|:---|
| TB CRC 附加 | 带 TB CRC 的 TB 比特 | TB CRC 检查 | 整个 TB pass/fail |
| CB 分段和 CB CRC | 一个或多个 CB | CB 拼接前检查和去除 | 每个 CB 的有效载荷 |
| Turbo 编码 | 三路编码流 | Turbo 译码 | 每个 CB 的硬判决和软置信度 |
| 子块交织 | 每路交织后的编码流 | 子块解交织 | 恢复每路母码顺序 |
| 比特收集和循环缓存 | 循环缓存 | 循环缓存反映射 | 三路位置上的 LLR |
| 速率匹配选择 | 实际发送比特 | 解速率匹配和 HARQ 合并 | 填回母码位置的软信息 |

工程上最重要的是：接收端不是在一个线性数组里随便找比特，而是要根据协议元数据恢复每个 CB 的逻辑位置。元数据包括 CB 数量 $C$、每个 CB 长度 $K_r$、速率匹配输出长度 $E_r$、冗余版本、调制阶数和 HARQ 进程上下文。

## 三类空洞的定义和后果

LTE Turbo 链路里常见三类“没有普通业务比特”的位置。它们都像空洞，但含义完全不同。

| 空洞类型 | 发生位置 | 发送端含义 | 接收端处理 | 错误后果 |
|:---|:---|:---|:---|:---|
| 码块 filler | TS 36.212 §5.1.2 的 CB 输入端 | 为匹配允许的 $K$ 而在第 0 个 CB 前部补占位 | 参与 CB CRC 计算时按协议假定值处理，重组 TB 时删除 | 留在 TB 中会导致 TB CRC 失败和载荷错位。 |
| 子块交织 `<NULL>` | TS 36.212 §5.1.4.1.1 的矩阵补齐位置 | 为填满交织矩阵行列而插入的无效元素 | 解交织时不能当业务位输出，不能送入 Turbo 母码位置 | 当成真实 LLR 会污染三路输入。 |
| 未发送位置 | 速率匹配、打孔、冗余版本选择后 | 本次传输没有承载该母码位置 | 置为擦除软信息，常用 $0$ LLR 或软缓存缺省值表示未知 | 当成硬 0 会制造虚假可靠度，导致迭代译码偏置。 |

这里的 $0$ LLR 和硬比特 0 完全不同。LLR 为 $0$ 表示“不知道，更像 0 和更像 1 的证据相等”；硬比特 0 表示“已经决定是 0”。若把未发送位置当成可靠的 0，就等于给 Turbo 译码器灌入了不存在的观测证据。

## 数值例子：四个位置的软信息反填

这是一个教学例子，不是 LTE 合法块长。假设某个 CB 的母码三路位置为系统路 $s_0,s_1,s_2,s_3$，校验一路 $p0_0,\ldots,p0_3$，校验二路 $p1_0,\ldots,p1_3$。速率匹配后本次只发送了 8 个位置：

| 接收顺序 | 母码位置 | 接收 LLR |
|---:|:---|---:|
| 0 | $s_0$ | $+3.0$ |
| 1 | $p0_0$ | $-1.2$ |
| 2 | $p1_0$ | $+0.4$ |
| 3 | $s_1$ | $-2.6$ |
| 4 | $p0_1$ | $+1.1$ |
| 5 | $s_2$ | $+0.9$ |
| 6 | $p1_2$ | $-0.7$ |
| 7 | $s_3$ | $+4.1$ |

接收端反填后，三路 Turbo 软输入为：

$$
\mathbf{L}^{(0)}=[+3.0,-2.6,+0.9,+4.1]
\tag{2}
$$

$$
\mathbf{L}^{(1)}=[-1.2,+1.1,0,0]
\tag{3}
$$

$$
\mathbf{L}^{(2)}=[+0.4,0,-0.7,0]
\tag{4}
$$

式 (3) 和式 (4) 中的 $0$ 是擦除 LLR，不是业务比特 0。这个数值例子说明了解速率匹配的本质：它把“实际收到的顺序”转成“Turbo 母码三路顺序”。Turbo 译码器随后利用系统路和两路校验路的约束关系，在迭代中给每个信息位形成更可靠的判断。

## Turbo 译码器的输入输出契约

对每个 CB，Turbo 译码器至少需要以下输入：

| 输入 | 含义 | 来源 |
|:---|:---|:---|
| $\mathbf{L}^{(0)}$ | 系统比特 LLR | 解速率匹配和子块解交织后的第 0 路。 |
| $\mathbf{L}^{(1)}$ | 第一组成编码器校验 LLR | 解速率匹配和子块解交织后的第 1 路。 |
| $\mathbf{L}^{(2)}$ | 第二组成编码器校验 LLR | 解速率匹配和子块解交织后的第 2 路。 |
| $K_r$ | 当前 CB 编码输入长度 | TS 36.212 §5.1.2 分段结果和 Table 5.1.3-3 块长集合。 |
| 内部交织地址 | 第二个组成译码器使用的地址映射 | TS 36.212 §5.1.3.2.3。 |
| 最大迭代次数 | 工程停止上限 | 实现选择，不是 TS 36.212 固定位。 |

输出通常包括硬判决比特、CB CRC 状态、实际迭代次数和错误标志：

$$
\hat{\mathbf{b}}_r=\left[\hat{b}_{r,0},\hat{b}_{r,1},\ldots,\hat{b}_{r,K_r-1}\right]
\tag{5}
$$

式 (5) 回答“Turbo 译码器对第 $r$ 个 CB 输出什么”。帽号表示估计值，不保证一定正确。后续 CB CRC 和 TB CRC 用来检验估计结果是否满足协议规定的校验关系。

## 算法伪代码

以下伪代码是接收端导向的教学伪代码，不是协议逐字伪代码：

```text
for each HARQ process and codeword:
    collect demodulator LLRs for the current transmission
    combine with previous soft buffer according to redundancy version
    for r in 0 .. C-1:
        recover E_r received LLRs belonging to CB r
        map selected circular-buffer positions back to mother-code positions
        remove sub-block interleaver permutation and NULL positions
        form L0, L1, L2 for Turbo decoder
        run Turbo iterations with interleaver and deinterleaver addresses
        check CB CRC after hard decision
        if CB CRC fails:
            mark CB r failed
    if all CBs pass:
        remove CB CRC and segmentation filler
        concatenate CB payloads in r order
        check TB CRC
    return decoded TB bits and ACK/NACK decision
```

这里的复杂度主要来自两类循环：按 CB 数 $C$ 的外层循环，以及每个 CB 内按迭代次数和块长 $K_r$ 的 Turbo 译码循环。若每次迭代需要对 $K_r$ 个状态位置做前向、后向和外信息更新，粗略计算量随 $C\sum_r K_r I_r$ 增长，其中 $I_r$ 是第 $r$ 个 CB 的迭代次数。

## 定点化策略

定点化首先要保护语义，而不是只压缩位宽。推荐把 LLR 存成有符号定点整数，擦除位置用整数 0 表示“无信息”。如果采用 6 bit LLR，范围可能类似 $[-31,31]$，但具体范围是实现选择。

定点策略需要检查三点：

| 检查项 | 原因 | 失败表现 |
|:---|:---|:---|
| 擦除值固定为中性 | 未发送位置不能偏向 0 或 1 | 低信噪比下 CB CRC 失败率异常。 |
| 重复位置做软合并 | 重复发送提供更多证据 | 重复比特没有带来可靠度提升。 |
| 饱和加法可控 | HARQ 合并可能累积大 LLR | 过早饱和会让错误证据难以被后续传输纠正。 |

对于重复位置，若同一母码位置收到两次 LLR $L_a$ 和 $L_b$，常见工程合并是饱和加法：

$$
L_{\mathrm{comb}}=\mathrm{sat}(L_a+L_b)
\tag{6}
$$

式 (6) 是工程实现公式，不是 TS 36.212 的强制公式。它回答“同一编码位置多次收到软证据时怎样合成一个软输入”。`sat` 表示限制到定点范围内，防止溢出。

## RTL/ASIC 架构映射

硬件上，本节链路通常分成五类模块：

| 模块 | 主要存储 | 控制要点 |
|:---|:---|:---|
| HARQ soft buffer | 跨重传保存的 LLR | 按进程、码字、CB 和冗余版本寻址。 |
| 解速率匹配地址生成器 | 循环缓存索引和有效标志 | 区分未发送、重复、打孔和 `<NULL>`。 |
| 子块解交织器 | 三路流缓冲 | 反置换和 NULL 跳过。 |
| Turbo 译码核 | 系统路、两路校验路、外信息、状态度量 | 迭代控制、早停、内部交织地址。 |
| CRC 与拼接单元 | CB 输出 buffer 和 TB buffer | 按 CB 序号提交结果，避免乱序拼接。 |

吞吐估算的第一层近似为：

$$
T_{\mathrm{CB}}=\frac{K_r}{N_{\mathrm{cycle,dematch}}+N_{\mathrm{cycle,decode}}+N_{\mathrm{cycle,crc}}}
\tag{7}
$$

式 (7) 回答“一个 CB 从软输入到硬输出的有效吞吐如何估算”。它不是最终芯片指标，因为真实系统还要考虑多 CB 并行、DMA（直接存储器访问，Direct Memory Access）、HARQ buffer 读写冲突、时钟频率和早停概率。

## 验证方法

验证应按从协议映射到算法输出的顺序组织：

| 层级 | 验证对象 | 关键断言 |
|:---|:---|:---|
| 地址级 | 解速率匹配和解交织 | 每个收到的 LLR 回到唯一合法母码位置；NULL 不输出。 |
| 软信息级 | 擦除和合并 | 未发送位置为中性 LLR；重复位置按约定合并。 |
| CB 级 | Turbo 译码和 CB CRC | 单个 CB 通过时输出长度正确；失败时不参与最终 ACK。 |
| TB 级 | CB 拼接和 TB CRC | CB 按 $r$ 顺序拼接；filler 被删除；TB CRC 通过才 ACK。 |

代表性用例 1：单 CB、无 filler、无重传。输入为一个 CB 的 LLR 序列，输出为 TB 比特和 TB CRC pass。边界条件是 $C=1$。验证方式是固定向量 bit-exact 对比。失败案例是把子块 `<NULL>` 当成普通 LLR，导致 CB CRC fail。

代表性用例 2：多 CB、第 0 个 CB 有 filler、存在 HARQ 重传。输入为两次传输的 LLR 和冗余版本元数据，输出为拼接后的 TB。边界条件是第 0 个 CB 前部 filler 和某些母码位置第一次未发送。验证方式是检查 filler 删除、软合并和 CB 顺序。失败案例是按译码完成顺序拼接 CB，导致 TB CRC fail。

## 常见错误

| 错误 | 根因 | 诊断信号 |
|:---|:---|:---|
| 把未发送位置填成硬 0 | 混淆擦除 LLR 和业务比特 | 高码率或特定冗余版本下错误集中。 |
| 把 `<NULL>` 送入 Turbo 译码器 | 混淆子块交织补齐和母码位置 | 三路长度或地址断言失败。 |
| filler 留在 TB 中 | 只检查 CB CRC，忘记分段逆操作 | CB 全过但 TB CRC 失败。 |
| CB 乱序拼接 | 多核译码完成顺序替代协议序号 | 偶发 TB CRC 失败，日志中 CB pass 顺序不稳定。 |
| HARQ soft buffer 覆盖错误 | 进程、码字或 CB 地址少维度 | 重传后性能反而下降。 |

## 自测题

1. 接收端为什么不能把未发送的母码位置当成业务比特 0？
2. CB CRC 和 TB CRC 在接收链路中的职责有什么不同？
3. 子块交织 `<NULL>` 和 [[T3.3_LTE_Turbo_segmentation_rules|T3.3]] 的 filler 有什么本质区别？
4. 如果两个 CB 都通过了 CB CRC，但 TB CRC 失败，优先检查哪两个工程环节？

## 自测题参考答案

1. 未发送位置没有观测证据，正确语义是擦除软信息。业务比特 0 是硬判决，会给 Turbo 译码器虚假的强证据。
2. CB CRC 检查单个 CB 的译码结果，常用于早停和定位失败 CB；TB CRC 检查所有 CB 去 CRC、去 filler、按序拼接后的整体载荷，是最终 ACK/NACK 的关键依据。
3. `<NULL>` 是子块交织矩阵补齐产生的无效元素，作用在编码比特交织阶段；filler 是码块分段阶段为匹配允许块长而加入的输入端占位，影响 CB 输入和最终 TB 删除。
4. 优先检查 CB 拼接顺序和 filler 删除；其次检查 TB CRC 初始输入范围是否错误地包含了 CB CRC 位。
