# T9.8 CBG 码块组：配置、分组与反馈的完整语义

## 本节学习目标

T9.7 从译码侧缓存操作切入 CBG（它决定增量写的粒度）；本篇把 CBG 作为协议对象**系统性讲完整**：为什么 NR 引入它（LTE 没有）、高层如何配置、码块如何分组成 CBG、CBGTI/CBGFI 两个 DCI 字段的完整语义、反馈流程如何按组进行，以及与 TB 粒度 HARQ 的全面对比。它是 T9.0（descriptor 的 CBG 字段）、T9.5（reassembly）、T9.7（增量写）、T11.x（对比）的共同背景知识。

学完本节后，应能做到：

- 说明 CBG 解决什么问题（LTE 整 TB 重传的浪费），以及它引入的历史脉络（NR R15）。
- 说出 CBG 相关的三个高层配置参数及其作用。
- 用 $M = \min(N, C)$ 与 $K_1/M_1$ 分组公式完成任意 C/N 的分组推导。
- 解释 CBGTI 与 CBGFI 的语义分工（管传输 vs 管反馈），并给出四种组合的行为。
- 画出 CBG 级 HARQ 的反馈流程（CBGFI=0 按组反馈如何构造）。
- 对比 TB 粒度与 CBG 粒度的 HARQ 在重传、反馈、软缓存上的差异。
- 说明 CBG 对译码器（descriptor、软缓存、增量写）的影响。

## CBG 的引入动机：LTE 整 TB 重传的浪费

LTE 的 HARQ 粒度是**整个传输块**：一个 TB 译码失败（哪怕只有 1 个 CB 出错），重传的是整个 TB——大量没出错的码块跟着重传，浪费频谱、功率和处理时延。TB 越大（NR 数据速率更高，TB 可达数千 KB），这种浪费越突出。

NR R15 引入**码块组（Code Block Group, CBG）**：把 TB 的码块分组，重传与反馈都以 CBG 为单位——哪组出错重传哪组，未出错组保持不动。这是"细粒度 HARQ"在 NR 的落地，也是 T9.7 的 CB 增量写在调度侧的配对机制：**CBG 决定"重传什么"，增量写决定"缓存怎么更新"**。

## 配置参数：CBG 如何开启与设定

CBG 不是默认开启的——需要 RRC 高层配置（三件套）：

| 参数 | 作用 | 协议位置 |
|:---|:---|:---|
| `PDSCH-CodeBlockGroupTransmission` | 开启 PDSCH（下行）CBG 传输 | TS 38.214 §5.1.7（PDSCH-ServingCellConfig 中） |
| `PUSCH-CodeBlockGroupTransmission` | 开启 PUSCH（上行）CBG 传输 | TS 38.214 §6.1.5 |
| `maxCodeBlockGroupsPerTransportBlock` | 每个 TB 最大 CBG 数 $N$ | 决定分组粒度 |

配置要点：

- **开启即承诺**：配置了 CBG 传输后，UE 的 HARQ 反馈与重传语义从 TB 级切到 CBG 级（T9.7 的"未传输 CBG 缓存保持"等行为随之生效）。
- **$N$ 的取值**：`maxCodeBlockGroupsPerTransportBlock` 决定分组上限，实际 CBG 数还受码块数限制（见下节分组公式）。
- **CBGFI 相关配置**：DCI 中的 CBGFI 字段是否存在也由配置决定（`cbg-Feedback` 相关），未配置时反馈恒为 TB 级或按 CBG 级（视配置组合）。

## 分组公式与推导（TS 38.214 §5.1.7.1）

CBG 数量：

$$
M = \min(N, C)
$$

其中 $N$ 是 `maxCodeBlockGroupsPerTransportBlock`，$C$ 是 TB 的码块数（TS 38.212 §7.2.3 分段结果）。

分组规则（使各 CBG 大小尽可能均衡）：设

$$
K_1 = \lfloor C/M \rfloor, \qquad M_1 = C - M K_1
$$

则前 $M_1$ 个 CBG（索引 $m = 0, \ldots, M_1-1$）各含 $K_1 + 1$ 个 CB，其余 $M - M_1$ 个各含 $K_1$ 个；码块按索引顺序依次填入。

**数值推导（C=10, N=4）**：

- $M = \min(4, 10) = 4$
- $K_1 = \lfloor 10/4 \rfloor = 2$，$M_1 = 10 - 4 \times 2 = 2$
- 前 2 个 CBG 各含 3 个 CB，后 2 个各含 2 个：

| CBG | 包含 CB | 大小 |
|:---:|:---|:---:|
| CBG 0 | CB 0, 1, 2 | 3 |
| CBG 1 | CB 3, 4, 5 | 3 |
| CBG 2 | CB 6, 7 | 2 |
| CBG 3 | CB 8, 9 | 2 |

**边界情形**：

- $C \le N$：$M = C$，每个 CBG 恰 1 个 CB（最细粒度——此时 CBG 退化为 CB）。
- $N = 1$：$M = 1$，整个 TB 一个 CBG（退化为 TB 级，等价于未配置 CBG）。
- $C$ 不能被 $M$ 整除：靠 $M_1$ 前多后少均衡（上例）。

本地核对：38.214 `full.md` §5.1.7.1 确认了 $M = \min(N, C)$ 与 $K_1/M_1$ 分组公式（与抽取件文本一致）。

## CBGTI 与 CBGFI：一对分工明确的 DCI 字段

### CBGTI（传输指示）

- DCI 中长度 $M$ 的位图，bit $m$ = 1 表示本次传输包含 CBG $m$。
- 长度由 $M$（实际 CBG 数）决定；DCI format 中的位宽按配置预留。
- 语义：**管"本次传什么"**——接收端按位图决定哪些 CBG 有本次 LLR（对应 T9.7 的增量写触发）。

### CBGFI（反馈指示）

- DCI 中的 1 bit。
- 为 1：UE 反馈**单个 TB 级 ACK/NACK**（不管 CBG 粒度）。
- 为 0：UE 按 CBG **逐个反馈**（$M$ 个 ACK/NACK）。
- 语义：**管"反馈怎么报"**——不影响传输内容，但决定 UE 需要保存哪些译码结果。

### 四种组合的行为

| CBGTI | CBGFI | 传输内容 | 反馈粒度 | 接收端要点 |
|:---:|:---:|:---|:---|:---|
| 全 1 | 1 | 全部 CBG | TB 级单 bit | 与 TB-HARQ 几乎相同 |
| 部分 | 1 | 部分 CBG | TB 级单 bit | 未传输 CBG 缓存保持，但反馈不区分 |
| 全 1 | 0 | 全部 CBG | 按 CBG | 需记录每个 CBG 的译码结果 |
| 部分 | 0 | 部分 CBG | 按 CBG | **典型配置**：只重传出错组 + 逐组反馈 |

**与 T9.7 的衔接**：无论 CBGFI 如何，缓存操作（覆盖/增量/保持）只由 NDI + CBGTI 决定；CBGFI 只影响 UE 保存与上报什么。

## CBG 级 HARQ 反馈流程

以"CBGTI=部分、CBGFI=0"的典型场景为例：

1. gNB 发送 TB（全部 CBG），UE 逐 CBG 译码；
2. UE 按 CBG 构造反馈：$M$ 个 ACK/NACK（每个 CBG 一个），经 PUCCH/PUSCH 上报；
3. gNB 只重传 NACK 的 CBG，DCI 携带对应 CBGTI 位图；
4. UE 对命中的 CBG 执行增量写（T9.7），对未命中的保持缓存；
5. 循环直到全部 CBG 通过（TB CRC 最终把关——**注意：CBG 反馈是中间粒度，TB 级 CRC 仍是最终交付判据**，T9.5 的 reassembly 语义）。

## 与 TB 粒度 HARQ 的对比

| 维度 | TB 粒度（LTE，或 CBG 未配置） | CBG 粒度（NR 配置后） |
|:---|:---|:---|
| 重传单位 | 整个 TB | 命中的 CBG |
| 反馈粒度 | 1 bit（TB） | $M$ bit（按 CBG）或 1 bit（CBGFI=1） |
| 未出错码块 | 跟着重传（浪费） | 缓存保持不动 |
| 软缓存操作 | TB 级整块处理 | CB 级增量写/保持（T9.7） |
| 协议字段 | NDI、RV | NDI、RV、CBGTI、CBGFI |
| 引入 | LTE 一直如此 | NR R15 引入（可选配置） |

**代价**：CBG 粒度不是免费的——反馈开销增大（$M$ bit vs 1 bit）、UE 需要逐 CBG 记录译码结果、调度复杂度上升。因此它是**配置选项**而非默认：小 TB / 低重传率场景用 TB 粒度更省。

## 对译码器的影响

- **descriptor 字段**：CBG 开启后，descriptor 需要携带 CBG mask（CBGTI 转换结果）、CBG 数量 $M$、每 CBG 的 CB 边界——T9.0 的 descriptor 设计中 CBG 相关字段由此而来。
- **软缓存管理**：增量写/保持按 CB 独立进行（T9.7），CBG 只是调度语义，缓存操作仍以 CB 为原子单位。
- **reassembly**：CBG 全部通过后按 CB 顺序拼接回 TB，TB CRC 最终验证（T9.5）。
- **edge cases**：CBG 数量在重传间可能变化（调度重新配置）——descriptor 必须每轮重建（T9.6 与 T9.7 的共同提醒）。

## 自测题

1. LTE 为什么浪费？NR 用什么机制解决？
2. CBG 的三个配置参数分别是什么？
3. C=8、N=4 时分组结果如何？（写出 $M$、$K_1$、$M_1$ 与各 CBG 大小）
4. CBGTI 与 CBGFI 的分工是什么？
5. CBGTI=部分、CBGFI=0 时，未传输 CBG 的缓存如何？反馈如何构造？
6. CBG 粒度的代价是什么？
7. CBG 与 CB 在缓存操作上的关系是什么？

## 自测题参考答案

1. LTE 整 TB 重传——哪怕只有 1 个 CB 出错，整个 TB 的码块跟着重传；NR R15 用 CBG 细粒度重传解决。
2. `PDSCH-CodeBlockGroupTransmission`（下行开启）、`PUSCH-CodeBlockGroupTransmission`（上行开启）、`maxCodeBlockGroupsPerTransportBlock`（每 TB 最大 CBG 数）。
3. $M=\min(4,8)=4$；$K_1=2$、$M_1=0$；四个 CBG 各含 2 个 CB（0-1、2-3、4-5、6-7）。
4. CBGTI 管"本次传什么"（位图指示传输的 CBG），CBGFI 管"反馈怎么报"（1=TB 级单 bit，0=按 CBG 逐组）。
5. 未传输 CBG 缓存保持不动（不清零）；反馈按 CBG 构造 $M$ 个 ACK/NACK（每个 CBG 一个）。
6. 反馈开销增大（$M$ bit vs 1 bit）、需逐 CBG 记录译码结果、调度复杂度上升——因此是配置选项。
7. CBG 是调度/反馈语义粒度，缓存操作（增量写/保持）仍以 CB 为原子单位——CBG 决定哪些 CB 参与本次传输。
