# T16.4 MAC 层映射：逻辑信道到物理信道的协议全景

## 本节学习目标

M16 系列前三篇讲了调度（时频/空间/多载波）——它们都是 MAC（媒体接入控制，Medium Access Control）层的行为。本节收官：**MAC 层的信道映射全景**——逻辑信道（数据/控制承载）→ 传输信道（编码/调度载体）→ 物理信道（物理传输）的三层映射，以及 MAC PDU（协议数据单元，Protocol Data Unit）的结构与复用。

信道映射回答"数据怎么从高层走到天线"：RRC 的逻辑信道（DCCH/DTCH 等）经 MAC 复用成 MAC PDU，映射到传输信道（DL-SCH/UL-SCH），再映射到物理信道（PDSCH/PUSCH）——**每一层映射都有协议定义（38.300 §6.4 的信道映射表）**。MAC PDU 结构（38.321 §6.1/§6.2）是复用的实现：多个逻辑信道的 SDU（服务数据单元，Service Data Unit）各带 subheader 拼接成 PDU——接收端按 subheader 拆解。

学完本节后，应能做到：

- 画出逻辑 → 传输 → 物理的三层信道映射（38.300 的信道映射表）。
- 说出 MAC PDU 的结构（subheader + payload）与 subheader 的关键字段（LCID/长度），完成 numpy 组装/解析往返验证。
- 说出 MAC 复用的语义（多逻辑信道拼接、按优先级）与接收端拆解（逐 subheader 解析）。
- 把调度（T16.1）与 descriptor（T9.0）放进 MAC 层语境——descriptor 是 MAC 到物理的交接产物。

## 信道映射的引入缘由：MAC 层的分拣与打包

M16 系列前三篇讲"怎么决定、怎么扩展"，本节讲"怎么组织"——数据从高层走到天线要经过三层信道的组织。但在画映射表之前，先回答为什么需要这三层抽象：内容语义与物理资源如果直接耦合，协议会变成什么样子。下文先给直觉模型，再给三个逻辑信道复用进一个 MAC PDU 的手算例子，最后落到正式定义与接收端后果。

### 它解决的问题：内容语义与物理资源的分离

RRC 层只关心"发什么内容"（控制信令、用户数据、广播、寻呼），物理层只关心"什么波形、什么时频资源"——两者的语言完全不同。如果没有中间的组织层，每一种内容类型都要单独设计一套物理传输，协议规模会爆炸式膨胀。信道映射解决的就是这个问题：用一张表把"内容语义 → 传输方式 → 物理载体"三层抽象接起来，让高层与物理层各自演进、互不牵连。

可以做一个反事实推演：若控制信令与用户数据共用同一套物理设计，任何一方的优化（如控制信令加优先级保护）都要改动另一方——分层的本质是"变化隔离"，让每一层的变化不传导到另外两层。这正是"逻辑/传输/物理"三层名称的来源："逻辑"对应语义分类，"传输"对应编码调度方式，"物理"对应实际资源。

这个三层结构在 3GPP 体系里自 WCDMA（宽带码分多址，Wideband Code Division Multiple Access）时代沿用至今，是协议稳定性的来源之一；每一层只需要在自己的抽象上变化，不需要惊动另外两层。三层的对应关系也不是任意的——38.300 的表是协议规定的最小事实集，发送端与接收端按同一张表执行，任何一方私自改动都会失配。

### 直观模型：搬家打包

搬家时不同房间（书房/卧室）的物品分别装箱，箱子上贴标签清单（subheader），统一装车（传输信道）运到新家，收件人按清单把物品放回对应房间（接收端分发）。逻辑信道是"房间"，MAC PDU 是"箱子 + 清单"，传输信道是"货车"，物理信道是"路面"。

复用就是"多个房间的物品拼进一个箱子"，前提是清单能让对方无损拆箱——清单丢了，箱子就只能整箱报废。另一个细节：清单贴在箱子最前面、每件物品一个标签（subheader 与 payload 交替排列），这样收货人从第一个标签开始逐个读就能定位每件物品——这正是 MAC PDU 逐位解析的直觉来源。

### 最小手算模型：三个逻辑信道复用进一个 MAC PDU（手算例子）

调度器（T16.1）给了一次传输的授权：本 slot 可发送 100 bit 的 MAC PDU（教学简化数值）。发送端要把三个逻辑信道的 SDU 按优先级打包，subheader 为教学简化 13 bit（LCID（逻辑信道标识，Logical Channel ID）5 bit + 长度 8 bit；完整结构含 F/R 标志，见 38.321 §6.2.1）：

- DCCH（专用控制信道，Dedicated Control Channel）：RRC 控制消息，LCID = 1，SDU 长 40 bit；
- CCCH（公共控制信道，Common Control Channel）：接入信令，LCID = 0，SDU 长 12 bit；
- DTCH（专用业务信道，Dedicated Traffic Channel）：用户数据，LCID = 5，SDU 长 16 bit。

(1) 控制优先排序。按 LCP（逻辑信道优先级，Logical Channel Prioritization）控制信道先装：DCCH → CCCH → DTCH。

(2) 装 DCCH。LCID 00001、长度 40 = 0b00101000，subheader = 0b0000100101000（13 bit），加 payload 40 bit 共 53 bit。

(3) 装 CCCH。LCID 00000、长度 12 = 0b00001100，subheader = 0b0000000001100，加 payload 12 bit 共 25 bit；累计 $53 + 25 = 78$ bit。

(4) 装 DTCH（截断）。授权 100 bit，剩余 $100 - 78 = 22$ bit；subheader 占 13 bit，DTCH 只能装 $22 - 13 = 9$ bit——16 bit 的 SDU 截断为 9 bit，剩余 7 bit 留到下一 PDU（分段）。截断是授权约束的直接工程后果：授权多少，就装多少。

(5) 接收端按清单拆箱。从 bit 0 读 13 bit subheader：LCID = 1、长度 40 → payload 占 bit 13-52；下一个 subheader 从 bit 53 起：LCID = 0、长度 12 → payload 占 bit 66-77；再下一个 subheader 从 bit 78 起：LCID = 5、长度 9 → payload 占 bit 91-99。100 bit 全部解析完毕、零剩余——拆箱成功，三个 SDU 各自交回对应的 RLC（无线链路控制，Radio Link Control）实体。最终 PDU 的逐位布局如下表：

| bit 范围 | 内容 | 数值 |
|:---|:---|:---|
| 0-12 | DCCH subheader | 0b0000100101000 |
| 13-52 | DCCH payload（40 bit） | RRC 消息 |
| 53-65 | CCCH subheader | 0b0000000001100 |
| 66-77 | CCCH payload（12 bit） | 接入信令 |
| 78-90 | DTCH subheader | 0b0010100001001 |
| 91-99 | DTCH payload（9 bit） | 用户数据（截断） |

整个例子的推导只需加法与减法（$53 + 25 = 78$、$100 - 78 = 22$、$22 - 13 = 9$），但完整演示了复用、优先级、截断与逆解析四件事——这正是接收端逐 subheader 解析的由来。

### 正式定义：映射关系与 PDU 序列

用符号定义本节对象。映射关系 M 是 38.300 §6.4 表定义的三层对应：逻辑信道集合 → 传输信道集合 → 物理信道集合，多对多。一个 MAC PDU 是序列 $\{(h_i, s_i)\}_{i=1}^{n}$，其中 $h_i = (\mathrm{LCID}_i, L_i)$ 是第 i 个 SDU 的 subheader（标识 + 长度），$s_i$ 是 SDU 比特串，且满足授权约束 $\sum_{i=1}^{n} (13 + L_i) \le G$（G 为调度授权的 PDU 大小）。接收端解析就是沿序列依次读取 $h_i$、定位 $s_i$、按 $\mathrm{LCID}_i$ 分发到对应逻辑信道。

G 与 T16.1/T9.0 的 TBS（传输块大小，Transport Block Size）同源：调度授权给出传输块能装多少 bit，MAC 复用在这个上限内装箱——调度（T16.1）、授权（T14.2）、装箱（本节）三者以 G 为接口衔接。手算例子里 G = 100，三个 SDU 装完恰好用满。

### 理论底座的三点误解辨析

| 误解 | 正确理解 |
|:---|:---|
| 逻辑信道是物理上的通道 | 逻辑信道只是内容语义的分类，时频资源只存在于物理层——三层映射正是为了分离这两者 |
| MAC PDU 大小固定 | PDU 大小由每次调度授权决定（本例 100 bit），逐 slot 可变——复用必须服从授权约束 |
| 复用就是简单拼接 | 拼接必须带清单（subheader）且按优先级排序，接收端能逆拆解才是复用成立的判据——本例截断场景说明拼接受约束 |

三点误解的共同根源：把"组织层"当成了"物理层"——信道的三层抽象各有各的职责，混淆层级是本节最常见的错误。

### 接收端后果：解析的雪崩效应

subheader 的逐位解析有一个显著后果：一个偏移错误会雪崩。若接收端把第一个长度读错 1 bit，第二个 subheader 的起点就错位，之后所有 SDU 的边界全部错乱——这就是为什么长度字段必须紧跟在 LCID 后面（自描述格式），以及为什么协议把复用结构定死而不是留给实现发挥。

更深一层的后果是交付错误：LCID 解析错 → SDU 交付到错误的 RLC 实体 → 高层状态机错乱（比物理层丢一个包更严重，物理层有 HARQ 兜底，高层语义错乱没有自动修复）。MAC PDU 的"打包清单"因此不是便利设施，而是接收端正确性的结构前提——这正是本节与 T9.0 descriptor 交接的地方：descriptor 保证物理层译码正确，subheader 保证高层交付正确。

## 三层信道映射

### 映射全景（38.300）

| 逻辑信道（承载内容） | 传输信道（编码/调度载体） | 物理信道（物理传输） |
|:---|:---|:---|
| DCCH/DTCH（控制/数据承载） | DL-SCH/UL-SCH | PDSCH/PUSCH |
| CCCH（公共控制） | DL-SCH/UL-SCH（随机接入 Msg3） | PDSCH/PUSCH |
| BCCH（广播控制） | BCH/DL-SCH | PBCH（物理广播信道，Physical Broadcast Channel）/PDSCH |
| PCCH（寻呼控制） | PCH | PDSCH |
| —（随机接入） | RACH | PRACH |

**映射的方向**：逻辑信道是"承载语义"（传什么内容），传输信道是"传输方式"（怎么编码调度），物理信道是"物理载体"（用什么资源波形）。**一个逻辑信道可映射多个传输信道、一个传输信道可承载多个逻辑信道**——多对多映射由协议表定义。

### 教学要点：MAC 层在映射中的角色

MAC 层是逻辑信道与传输信道之间的"复用器"：多个逻辑信道的数据经 MAC 复用（拼接成 PDU）后交给传输信道（DL-SCH/UL-SCH），传输信道经物理层编码调制后走物理信道。**T16.1 的调度器正是"传输信道资源分配"的决策者**——调度决定 PDU 在哪个传输/物理信道上、用什么资源发。

### 生活类比：邮件分拣中心

信道映射像邮件分拣：逻辑信道是"寄件类型"（平信/挂号/快递——控制/数据/广播），传输信道是"运输方式"（货车/飞机——编码/调度），物理信道是"最终投递"（地址/路线——物理资源）。MAC 层是分拣台：把不同类型信件（逻辑信道）打包成一车（MAC PDU 复用）发给对应运输方式（传输信道）。

## MAC PDU 结构（38.321 §6.1/§6.2）

### 结构

```
MAC PDU = [subheader 0][payload 0][subheader 1][payload 1]...
```

| 字段 | 内容 | 教学简化 |
|:---|:---|:---|
| LCID（逻辑信道标识，Logical Channel ID） | 标识承载的逻辑信道 | 5 bit |
| 长度（L） | payload 字节数 | 8 bit |
| F/R 等 | 标志/保留位 | 教学省略 |

**subheader 的语义**：每个 SDU 带一个 subheader（标识 + 长度）——接收端按顺序解析：读 subheader → 取对应长度 payload → 下一个 subheader。**subheader 是"打包清单"**，解析是"按清单拆包"。

### 复用与优先级

| 环节 | 机制 |
|:---|:---|
| 复用 | 多个逻辑信道的 SDU 拼接成一个 MAC PDU（每 SDU 带 subheader） |
| 优先级 | 按逻辑信道优先级（LCP）排序（控制信道优先于数据） |
| 组装 | 调度授权（T16.1）决定 PDU 大小 → MAC 按优先级填充 |

**复用的语义**：一次传输（一个 PDU）可以携带多个逻辑信道的数据——接收端按 subheader 区分并分发到对应高层实体。**优先级排序保证控制信息不被数据挤掉**（与 T14.3 的 UCI 优先级哲学一致）。

### numpy 验证的数值走读

numpy 验证实现 MAC PDU 的组装/解析：多个 LCID（1/5/13/28）与随机长度的 SDU 打包（subheader 13 bit = LCID 5 bit + 长度 8 bit），解析严格互逆（往返精确）；多 SDU 复用（3 个逻辑信道拼接一个 PDU）按 subheader 逐个拆解——LCID 与 payload 完全恢复。**"打包-拆包"的位操作往返是 MAC 层最基础的正确性保证**。

## 调度与 MAC 的交接：descriptor 的语境

### descriptor 在 MAC 层的位置

| 环节 | 层 | 产物 |
|:---|:---|:---|
| 调度决策 | MAC（T16.1） | 资源/MCS/HARQ 参数 |
| DCI 下发 | 物理（T14.2） | DCI 字段 |
| UE 解析 | 物理 → MAC | descriptor（T9.0） |
| 数据交付 | MAC | PDU 到译码链路 |

**descriptor 是"MAC 调度决策"在 UE 侧的完整投影**：T9.0 的字段（mcs_table_id/mcs_index/RV/HARQ 进程/资源边界）全部来自 MAC 调度器经 DCI 的下发——**本节把 descriptor 放回它的生产语境（MAC 层）**。

### 收束视角：MAC 层的三件事

M16 系列在 MAC 层收束为三件事：

1. **调度**（T16.1）：资源 + MCS + HARQ 三元组决策；
2. **空间/多载波扩展**（T16.2/T16.3）：波束与 CC/BWP；
3. **信道组织**（本节）：逻辑 → 传输 → 物理映射与 PDU 复用。

三者共同回答"数据如何从高层走到天线"——MAC 层是协议栈的"交通枢纽"（T0.1 的协议栈视角）。

## 示范例题

### 例题 1：subheader 解析

PDU 前 13 位 = 0b000010000000011：LCID 与长度？

**求解**：LCID = 前 5 位 00001 = 1；长度 = 后 8 位 00000011 = 3——逻辑信道 1 的 3 bit payload。

### 例题 2：复用解析

PDU = [subheader(LCID=5, len=2)][2 bit][subheader(LCID=13, len=1)][1 bit]：解析结果？

**求解**：两个 SDU——LCID 5 的 2 bit + LCID 13 的 1 bit，按顺序拆解。

### 例题 3：映射归类

RRC 建立消息走哪个逻辑/传输/物理信道？

**求解**：CCCH（逻辑）→ UL-SCH（传输）→ PUSCH（物理）——随机接入 Msg3 的路径（T15.2 衔接）。

## 引导练习（带提示）

### 练习 1：复用优先级

控制逻辑信道（DCCH）与数据逻辑信道（DTCH）的复用顺序？

**提示**：LCP 优先级。（答案：DCCH 优先——控制信息不被数据挤掉。）

接收端怎么知道 payload 的边界？

**提示**：subheader 的长度字段。（答案：每 SDU 的 subheader 带长度——按顺序解析边界。）

### 练习 3：映射多对多

一个传输信道可以承载多个逻辑信道吗？

**提示**：复用。（答案：可以——MAC 复用把多逻辑信道拼进一个 PDU 走一个传输信道。）

## 独立习题（附参考答案）

### 习题 1：三层映射

广播控制（BCCH）的传输与物理信道？

**参考答案**：BCH/DL-SCH（传输）→ PBCH/PDSCH（物理）——MIB 走 PBCH、SIB 走 PDSCH（T14.4）。

### 习题 2：PDU 组装

LCID=7、长度 5 的 subheader（教学 13 bit）二进制？

**参考答案**：LCID 00111 + 长度 00000101 = 0b0011100000101。

### 习题 3：解析边界

PDU 长度 30（含 subheader 13 + payload 17）：下一个 subheader 从第几位开始？

**参考答案**：第 30 位（13+17）——顺序解析的偏移。

## 常见误解

| 误解 | 正确理解 |
|:---|:---|
| 逻辑信道 = 物理信道 | 三层映射（逻辑 → 传输 → 物理）——多对多关系 |
| MAC PDU 只有数据 | 含 subheader（标识/长度）+ payload——复用需要清单 |
| 复用是任意的 | 按 LCP 优先级排序（控制优先）——协议规定 |
| MAC 层与调度无关 | 调度器在 MAC 层（T16.1）——本节是它的信道组织语境 |

## 常见错误

| 错误 | 正确理解 |
|:---|:---|
| 混淆逻辑/传输/物理信道 | 逻辑=承载语义、传输=传输方式、物理=物理载体 |
| 忘记 subheader 的长度字段 | 长度是解析边界的依据——无长度无法拆包 |
| 忽略复用优先级 | LCP 排序保证控制优先（与 UCI 优先级同哲学） |
| 认为 descriptor 是 MAC 产物 | descriptor 是 UE 侧解析 DCI 的产物（T9.0）——MAC 决策的投影 |

## 内嵌 numpy 验证

下列断言先实跑通过再写入本节，输出与断言一致（MAC PDU 组装/解析往返 + 复用）：

```python
import numpy as np

def pack_mac_pdu(lcid, data_bits):
    """MAC PDU 组装：subheader（LCID 5 bit + 长度 8 bit，教学简化）+ payload"""
    subheader = (lcid << 8) | len(data_bits)
    header_bits = [int(b) for b in f"{subheader:013b}"]
    return np.array(header_bits + list(data_bits), dtype=np.uint8)

def parse_mac_pdu(pdu):
    """MAC PDU 解析：提取 subheader 与 payload（与组装严格互逆）"""
    header = pdu[:13]
    payload = pdu[13:]
    subheader = int(''.join(map(str, header)), 2)
    lcid = subheader >> 8
    length = subheader & 0xFF
    assert length == len(payload)
    return lcid, payload

rng = np.random.default_rng(15)

# (1) 组装-解析往返（多个 LCID 与长度）
for lcid in (1, 5, 13, 28):
    data = rng.integers(0, 2, rng.integers(1, 100))
    pdu = pack_mac_pdu(lcid, data)
    l, pay = parse_mac_pdu(pdu)
    assert l == lcid and np.array_equal(pay, data)

# (2) 复用：多个逻辑信道 SDU 拼接成一个 PDU
sdus = [(1, rng.integers(0, 2, 20)), (5, rng.integers(0, 2, 30)), (13, rng.integers(0, 2, 15))]
pdu_full = np.concatenate([pack_mac_pdu(l, d) for l, d in sdus])
offset = 0
parsed = []
while offset < len(pdu_full):
    header = pdu_full[offset:offset+13]
    sub = int(''.join(map(str, header)), 2)
    lcid, length = sub >> 8, sub & 0xFF
    pay = pdu_full[offset+13:offset+13+length]
    parsed.append((lcid, pay))
    offset += 13 + length
assert len(parsed) == 3
assert [p[0] for p in parsed] == [1, 5, 13]
assert all(np.array_equal(p[1], d) for p, (_, d) in zip(parsed, sdus))

print(f"T16.4_OK pdu_roundtrip=True lcids={[1,5,13,28]} multiplex=3-SDU "
      f"parse_complete=True")
```

## 资料与协议边界

本节内容落在"协议规定"与"实现策略"的分界线上，分三层说明边界：

- **协议规定（机制层）**：三层信道映射表（38.300 §6.4）、MAC PDU 与 subheader 的结构（38.321 §6.1/§6.2；完整 subheader 含 F/R 标志，见 §6.2.1）。
- **协议不规定（策略层）**：复用时的具体截断与分段策略、LCP 的排序算法参数、MAC 内部缓冲管理——实现域；协议只保证接收端能够按 subheader 无损逆拆解。
- **接收端义务（执行层）**：按 subheader 顺序解析、按 LCID 分发到对应 RLC 实体、把重建的调度参数交给物理层译码（descriptor，T9.0）——打包与拆包的对称性由协议结构保证。

上述边界为 M16 系列收官：协议规定机制、实现决定策略、接收端执行决策——三层抽象之上是同一条协议观。

## 小结

MAC 层是协议栈的交通枢纽：逻辑信道（承载语义）→ 传输信道（传输方式）→ 物理信道（物理载体）的三层映射由 38.300 定义；MAC PDU（38.321 §6.1）用 subheader（LCID + 长度）实现多逻辑信道复用，接收端按清单逆拆解。调度（T16.1）是 MAC 的资源决策，descriptor（T9.0）是决策在 UE 侧的投影。

**阶段 5 收官**：M16 系列四篇（调度/HARQ、波束、CA/BWP、MAC 映射）完成。结合 M14（控制面）、M15（上行）、TX（发送端），**全链路规划的第二优先级（G3/G6-G10）正式收口**——剩余阶段 6（远期：Modem 子系统仿真/RTL）按规划待定。
