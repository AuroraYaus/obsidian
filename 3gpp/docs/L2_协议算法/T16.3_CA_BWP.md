# T16.3 载波聚合与 BWP：多载波调度与带宽自适应

## 本节学习目标

T16.1 讲了单载波的调度与 HARQ（混合自动重传请求，Hybrid Automatic Repeat Request），T16.2 讲了空间维度（波束）。本节讲调度的**多载波与带宽维度**：载波聚合（CA，Carrier Aggregation）把多个载波（CC，分量载波，Component Carrier）聚合给一个 UE——吞吐成倍；BWP（带宽部分，Bandwidth Part）在单载波内划分带宽子集——带宽自适应（大带宽能力 UE 用小带宽省电）。

CA 的调度语义：每个 CC 独立调度（每 CC 独立 HARQ 进程与 k1），DCI 的载波指示字段（CIF）实现跨载波调度（T14.2 衔接）；BWP 的调度语义：DCI 的 BWP 指示字段切换活动 BWP（T14.2 衔接），切换改变带宽、功率密度与调度粒度。**CA 是"多载波并行"，BWP 是"单载波内伸缩"**——两者都是"调度资源的组织方式"的扩展。

学完本节后，应能做到：

- 说出 CA 的结构（PCell/SCell、CC 数上限）与动机（吞吐聚合），并完成多 CC HARQ 时序仿真。
- 说出跨载波调度机制（CIF 字段，T14.2 衔接）与每 CC 独立 HARQ 的语义。
- 说出 BWP 的概念（带宽子集、活动 BWP、BWP 切换）与省电动机，完成带宽/功率换算。
- 说出 BWP 切换对调度的影响（DCI 的 BWP 指示字段）与休眠（DRX 衔接）。

## 多载波与带宽适配的引入缘由：吞吐与功耗的账

T16.1/T16.2 在单载波的时频与空间维度上做调度，本节把问题换成"资源总量不够或太多怎么办"。两个方向相反的答案就是本节主角：载波聚合（CA）把多个载波加在一起突破单载波吞吐上限，BWP 在载波内伸缩带宽适配流量。下文先给直觉模型，再给 2CC 聚合与 BWP 切换的手算账，最后落到正式定义与接收端后果。

### 它解决的问题：吞吐上限与功耗下限

单载波的带宽受频谱分配限制——运营商手里的连续频谱有限（如 100 MHz），单载波吞吐因此有天花板；另一方面，UE 射频前端的带宽越大功耗越高，而业务流量时高时低：高峰期需要大带宽，闲时需要省电。CA 解决前者（把分散的多个载波聚合起来突破单载波上限），BWP 解决后者（在载波内伸缩带宽适配流量）。两者的共同点是都改变"调度资源的总量"，方向相反：CA 做加法，BWP 做伸缩。

这两个问题的来源不同：吞吐上限来自频谱的碎片化——运营商手上的频谱常常是分散的不连续频段，把它们聚合成一个"大带宽"是唯一出路；功耗下限来自能力与流量的失配——UE 的射频带宽能力可能小于载波带宽，且流量稀疏时全带宽待机是纯粹的浪费。一个加法、一个伸缩，正是对这两个来源的分别回答。本节所有数值都是教学口径，用于读账；协议标准值 273 与 51 个 PRB（物理资源块，Physical Resource Block）已由正文 numpy 核验。

历史背景：CA 自 LTE Rel-10 引入，是 3GPP 对"单载波带宽不够"的第一次回答；BWP 是 NR 的新设计，应对更大的载波带宽与能力更小的 UE。这段历史解释了为什么两者在协议里并存且各管一段：CA 管"载波之间"，BWP 管"载波之内"。

### 直观模型：并管与阀门

CA 像把多根水管并成一根粗管：每根管子（载波）独立供水（独立调度与 HARQ），总流量等于各管之和。BWP 像同一根管子上的阀门：半夜用水少就拧小（小 BWP 省电），高峰拧大（大 BWP 提吞吐）。区别在于：CA 加的是管子的根数，BWP 变的是单管的开度。

阀门的比喻还有一层：阀门不是用户自己拧的，而是调度中心远程控制（DCI 的 BWP 指示字段）——UE 只执行切换，不决定切换。这与 T16.1"接收端只执行决策"的分工完全一致。并管与阀门还能组合：每根管子都可以装阀门（每个 CC 内都有 BWP）——这正是后文"两个算子正交"的直观版。

### 最小手算模型：2CC 聚合与 BWP 切换的吞吐账（数值例子）

读题：CC0 与 CC1 对应两套射频接收链（CA 的物理前提），每套链有自己的活动 BWP（阀门）——本例子 20 MHz 与 100 MHz 就是两套链各自的开度。

场景：UE 聚合两个载波，CC0 带宽 20 MHz（51 PRB（物理资源块，Physical Resource Block），30 kHz 子载波间隔），CC1 带宽 100 MHz（273 PRB）。频谱效率取教学简化的 4 bit/s/Hz（对应中高 MCS（调制与编码方案，Modulation and Coding Scheme））。

(1) 聚合吞吐账。$R_{\mathrm{CC0}} = 20 \times 4 = 80$ Mbit/s；$R_{\mathrm{CC1}} = 100 \times 4 = 400$ Mbit/s；聚合后 $R = 80 + 400 = 480$ Mbit/s。对比单载波 100 MHz 的 400 Mbit/s，聚合增益为 $480/400 = 1.2$ 倍——20 MHz 的 CC0 贡献了 80 Mbit/s 的边际吞吐。另一种读法：总带宽从 100 MHz 扩展到 20 + 100 = 120 MHz，带宽比 1.2 与吞吐增益 1.2 一致（频谱效率相同，带宽与吞吐同比例）。这就是"做加法"的账：每个 CC 的吞吐线性累加。

(2) 控制开销账。聚合不是免费的：每个 CC 都要独立监听 PDCCH 与独立反馈 HARQ。若每 CC 每 slot 需 20 次盲检（T14.1 的候选试错，教学取值），2 个 CC 就是 40 次——盲检总开销随 CC 数线性增长；反馈同理：每 CC 独立 k1 与 HARQ-ACK，上行控制开销也在做加法。UE 的盲检能力有上限，这就是"多载波并行"在控制面上的账单。

(3) BWP 省电账。射频前端功耗拆成固定底与带宽比例两部分（教学模型）：$P = P_0 + \alpha \cdot BW$，取 $P_0 = 100$ mW、$\alpha = 3$ mW/MHz。100 MHz 时 $P = 100 + 300 = 400$ mW；20 MHz 时 $P = 100 + 60 = 160$ mW。若一天中 30% 时间业务繁忙（大 BWP）、70% 时间业务稀疏（小 BWP），平均功耗为 $0.3 \times 400 + 0.7 \times 160 = 232$ mW，比全天大 BWP 的 400 mW 省 42%——算式为 $1 - 232/400 = 0.42$。参数 $P_0$ 与 $\alpha$ 是教学取值，真实曲线由厂商工艺决定，但"固定底 + 带宽比例"的形态是行业公认的一阶近似。这个账与正文"相同功率密度下 7 dB"的发射功率账互补：7 dB 算的是功放发射侧，本模型算的是射频前端静态侧——两个账从不同侧面支撑同一个结论：小 BWP 确实省电。

(4) 切换开销账。BWP 切换需要重配置接收链（带宽/采样率），教学口径按 2 slot 计。若业务突发每 10 slot 切换一次，100 slot 内切换 10 次、开销 20 slot，等效吞吐损失 $20/100 = 20\%$——切换太频繁会吃掉省电收益。因此工程上切换频率按业务突发长度设定，这正是"带宽自适应"的工程后果：省电收益要与切换代价算总账。

(5) 读账。四笔账的关系：聚合吞吐 +80 Mbit/s（加法收益）、控制开销 +20 次盲检（加法代价）、小 BWP 省 42%（伸缩收益）、切换损失 20%（伸缩代价）。收益与代价成对出现——CA 与 BWP 都不是免费的午餐，工程决策就是在这四笔账之间取平衡。

### 正式定义：聚合与伸缩的两个算子

用符号定义两者。CA 把 K 个分量载波组织成一个服务小区集合，聚合吞吐 $R = \sum_{i=1}^{K} R_i$，每个 CC 独立调度、独立 HARQ 进程与独立反馈时序。BWP 是在一个载波内取连续 PRB 子集 $\mathcal{B}$ 作为活动带宽，活动 BWP 决定调度解释基准（FDRA 位宽、MCS 表、功率控制的带宽项）。形式上的区别：CA 改变求和的项数（加法的项），BWP 改变每项的带宽宽度（伸缩的幅度）——一个是加法算子，一个是伸缩算子。

两个算子正交：每个 CC 内还可以有自己的 BWP 集合，组合空间等于 CC 数 × 每 CC 的 BWP 数——加法与伸缩可以叠加使用，这正是"调度资源组织"的完整自由度。与 T16.1 的决策函数对照：调度器在"每个 CC 的每个活动 BWP 内"做资源分配，决策函数的定义域被本节两个算子扩展。

### 理论底座的三点误解辨析

| 误解 | 正确理解 |
|:---|:---|
| CA 让吞吐免费翻倍 | 每个 CC 都要付控制面账单（盲检、反馈、保护带）——本数值例子里盲检开销随 CC 数线性翻倍 |
| BWP 是网络侧的负载均衡工具 | BWP 是每 UE 的能力适配与功耗适配（射频带宽 vs 流量），不是多用户资源切分 |
| 频繁切换 BWP 更省电 | 切换有重配置时延与信令开销，本例 20% 的吞吐损失账说明频繁切换得不偿失——省电要按占空比算总账 |

三点误解的共同根源：只算了收益那一半账——CA 与 BWP 的收益都附带成对的代价，读账必须两半一起读。

### 接收端后果：解释基准的多重性

接收端的核心负担是"基准随上下文变化"：DCI 的 CIF 改变目标载波——判错载波就会在错误的载波上盲检与译码；BWP 指示改变调度解释基准——按旧 BWP 解释新 DCI，FDRA 位宽与 MCS 表全错；每 CC 独立 HARQ 状态与软缓存构成内存账单——缓存总量等于 CC 数 × 每 CC 进程数。

这些后果的共同根源是：同一套 DCI 字段的语义依赖于当前的载波与 BWP 上下文。接收端必须先维护好上下文状态，再解释每一次调度决策——多载波时代的译码器，多了一层"上下文管理"的义务。BWP 切换期间还有窗口问题：切换生效时点前后，旧基准与新基准都不可靠，协议规定切换的生效时点，接收端必须按生效时点切换解释，不能提前也不能滞后。

## 载波聚合：多载波并行

### 结构与动机

| 要素 | 内容 |
|:---|:---|
| PCell（主小区） | 主载波（承载 RRC/安全/随机接入） |
| SCell（辅小区） | 聚合的辅载波（数据为主，可激活/去激活） |
| CC 数 | 最多 16 个（Rel-15 起） |
| 动机 | 多载波并行 → 吞吐聚合（带宽扩展） |

**CA 的语义**：一个 UE 同时使用多个 CC——每个 CC 独立调度（独立 DCI、独立 HARQ 进程、独立 k1）。PCell 承担控制面（接入/配置），SCell 补充数据面。

### 跨载波调度（CIF）

| 调度方式 | PDCCH 位置 | 调度目标 | CIF 字段 |
|:---|:---|:---|:---|
| 同载波调度 | CC i 的 PDCCH | CC i 的 PDSCH/PUSCH（物理上行共享信道，Physical Uplink Shared Channel） | 无/0 |
| 跨载波调度 | 调度载波的 PDCCH | 目标 CC 的 PDSCH/PUSCH | 3 位（CIF 指示目标 CC） |

**跨载波调度的语义**：一个 CC 的 PDCCH 可以调度另一个 CC 的数据——CIF（载波指示字段，Carrier Indicator Field）告诉 UE"这条 DCI 调度哪个 CC"（T14.2 的 0/3 位字段）。省 PDCCH 资源（一个 CC 管多个 CC 的调度）但增加 DCI 尺寸。

### 多载波 HARQ（numpy 验证的数值走读）

每 CC 独立 HARQ 状态机：numpy 验证实现 3 CC（PCell + 2 SCell），每 CC 8 进程、独立 k1（4/5/6）——60 slot 轮转调度，每 CC 进程覆盖完整、反馈时隙 = 传输时隙 + k1（CC 相关）。**每 CC 的 k1 独立**：不同 CC 的反馈时序不同（各 CC 帧结构/时延独立）——接收端按 CC 分别管理软缓存与反馈。

## BWP：带宽自适应

### BWP 概念

| 要素 | 内容 |
|:---|:---|
| BWP | 载波内的一组连续 PRB（带宽子集） |
| 活动 BWP | 当前使用的 BWP（每 CC 一个活动 BWP） |
| BWP 切换 | DCI 的 BWP 指示字段切换活动 BWP（T14.2 衔接） |

**BWP 的动机**：UE 能力（射频带宽）可能小于载波带宽——大带宽载波（100 MHz）给能力受限 UE 分配一个小子集（20 MHz）；且小带宽省电（射频前端带宽越小功耗越低）。

### 带宽与功率换算（numpy 验证的数值走读）

| 换算 | 数值 |
|:---|:---|
| 100 MHz / 30 kHz → PRB 数 | 273（协议值，含保护带） |
| 20 MHz / 30 kHz → PRB 数 | 51 |
| 带宽比 | 5:1 |
| 功率密度相同时的功率比 | 10log₁₀(5) ≈ 7 dB |

**BWP 切换的语义**：从 100 MHz 切到 20 MHz——PRB 273 → 51，相同功率密度下功耗降 7 dB（功放预算，T15.4 衔接）。**带宽自适应 = 功耗自适应**：数据少时用小 BWP 省电（DRX 衔接），数据多时切大 BWP 提吞吐。

### BWP 休眠与省电

| 机制 | 内容 |
|:---|:---|
| BWP 切换 | 大 BWP ↔ 小 BWP（按业务动态切换） |
| BWP 休眠（dormancy） | SCell 的 BWP 进入休眠（停止监听 PDCCH）——省电 |
| 与 DRX 衔接 | DRX 关断接收 + 小 BWP 降低功耗——联合省电 |

**BWP 的调度影响**：切换后调度解释基准变化（频域资源分配位宽、MCS 表、功控带宽项全部按新 BWP 重解释）——T14.2 的 BWP 指示字段正是切换的通道，T15.4 的带宽项随 BWP 变化。

### 生活类比：多车道高速公路

CA 像多条平行高速公路（每个 CC 一条路）：车辆（数据）可以同时在多条路上跑（并行调度），每条路有独立的收费站（HARQ 进程）；BWP 像一条路上的"可变车道"：车少时只开几条车道（小 BWP 省电），车多时全开（大 BWP 提吞吐）——切换车道由调度中心（DCI 指示）决定。

## 与 T16.1 的衔接：调度语义扩展

| 维度 | 单载波（T16.1） | 多载波（CA） | 带宽（BWP） |
|:---|:---|:---|:---|
| 资源 | RBG/VRB（单 CC） | 每 CC 独立 RBG/VRB | 活动 BWP 内的 RBG/VRB |
| HARQ | 8 进程 | 每 CC 8 进程 | 不改变（同 CC） |
| k1 | 单一 | 每 CC 独立 | 不改变 |
| DCI 字段 | FDRA/MCS/进程 | + CIF（跨载波） | + BWP 指示 |

**调度的三维扩展**：T16.1（时频）→ T16.2（空间波束）→ 本节（多载波 + 带宽）——调度的完整维度在 M16 系列里收齐。

## 示范例题

### 例题 1：跨载波调度

CC 0 的 PDCCH 调度 CC 2 的 PDSCH：CIF 字段值？

**求解**：CIF = 2（指示目标 CC）——UE 按 CIF 解析调度目标，PDSCH 在 CC 2 上接收。

### 例题 2：BWP 切换

100 MHz 载波，UE 从 273 PRB 的 BWP 切到 51 PRB：PRB 数与功耗变化？

**求解**：273 → 51 PRB；带宽比 5:1 → 相同功率密度下功耗降 10log₁₀(5) ≈ 7 dB。

### 例题 3：多 CC 反馈

CC 0/1/2 的 k1 分别为 4/5/6：slot 10 在 CC 1 的传输何时反馈？

**求解**：10 + 5 = slot 15 反馈——每 CC 独立时序。

## 引导练习（带提示）

### 练习 1：PCell 的角色

PCell 与 SCell 的分工？

**提示**：控制面 vs 数据面。（答案：PCell 承载 RRC/安全/随机接入；SCell 补充数据。）

### 练习 2：跨载波调度的代价

跨载波调度的优点与代价？

**提示**：PDCCH 资源 vs DCI 尺寸。（答案：省 PDCCH（一 CC 管多 CC）；代价 CIF 增加 DCI 尺寸 3 位。）

### 练习 3：BWP 切换的时机

什么场景切小 BWP？

**提示**：业务量 vs 功耗。（答案：数据少/待机时切小 BWP 省电（射频带宽功耗）；数据多切大 BWP 提吞吐。）

## 独立习题（附参考答案）

### 习题 1：CC 数

Rel-15 起的最大 CC 数？

**参考答案**：16 个（每 UE）——吞吐聚合的扩展空间。

### 习题 2：CIF 位宽

跨载波调度时 CIF 位宽与可指示 CC 数的关系？

**参考答案**：3 位 → 最多 8 个目标 CC（含自身）。

### 习题 3：BWP 与功率

**参考答案**：带宽比 5:1 → 10log₁₀(5) ≈ 7 dB 功耗下降（相同功率密度）。

## 常见误解

| 误解 | 正确理解 |
|:---|:---|
| CA 增加单 CC 带宽 | CA 聚合多个 CC——每 CC 带宽不变，吞吐聚合 |
| 所有 CC 用同一 k1 | 每 CC 独立 k1（帧结构/时延独立） |
| BWP 是负载均衡 | BWP 是带宽子集（能力适配 + 省电）——不是多用户分配 |
| CIF 与 BWP 指示相同 | CIF 选 CC、BWP 指示选活动 BWP——不同字段不同语义 |

## 常见错误

| 错误 | 正确理解 |
|:---|:---|
| 混淆 PCell/SCell | PCell 控制面（接入/配置）、SCell 数据面（可激活/去激活） |
| 忽略跨载波调度的 CIF | 无 CIF 时 PDCCH 只调度本 CC——跨载波必须有 CIF |
| 认为 BWP 切换瞬时无开销 | 切换需重配置接收链（带宽/采样率）——有切换时延 |
| 忘记每 CC 独立 HARQ | 每 CC 8 进程独立软缓存（多载波 × 进程数 = 总软缓存） |

## 内嵌 numpy 验证

下列断言先实跑通过再写入本节，输出与断言一致（多 CC HARQ + BWP 带宽换算）：

```python
import numpy as np

rng = np.random.default_rng(13)

# (1) 多 CC HARQ：每 CC 独立进程与 k1
N_CC = 3
N_PROC_PER_CC = 8
k1 = {cc: 4 + cc for cc in range(N_CC)}   # 每 CC 独立 k1（4/5/6）
n_slots = 60
acks = {cc: [] for cc in range(N_CC)}
for s in range(n_slots):
    cc = s % N_CC
    p = (s // N_CC) % N_PROC_PER_CC
    ok = rng.random() < 0.8
    acks[cc].append((p, s, ok))

# 断言：每 CC 进程轮转覆盖全部 8 进程
for cc in range(N_CC):
    procs = [x[0] for x in acks[cc]]
    assert len(set(procs)) == N_PROC_PER_CC
# 反馈时隙 = 传输时隙 + k1（CC 相关）
fb = {cc: [(s, s + k1[cc], ok) for (p, s, ok) in acks[cc]] for cc in range(N_CC)}
assert all(f[1] >= f[0] for cc in range(N_CC) for f in fb[cc])

# (2) BWP 带宽与功率（协议值：100MHz/30kHz -> 273 PRB，20MHz -> 51 PRB）
prb1, prb2 = 273, 51
power_reduction_db = 10*np.log10(100/20)
assert prb1 == 273 and prb2 == 51
assert abs(power_reduction_db - 6.99) < 0.01

print(f"T16.3_OK cc_harq: 3CC independent k1={[k1[c] for c in range(N_CC)]} "
      f"procs_per_cc={N_PROC_PER_CC} | bwp: {prb1}PRB->{prb2}PRB "
      f"power_reduction={power_reduction_db:.1f}dB")
```

输出：

```text
T16.3_OK cc_harq: 3CC independent k1=[4, 5, 6] procs_per_cc=8 | bwp: 273PRB->51PRB power_reduction=7.0dB
```

## 资料与协议边界

本节内容落在"协议机制"与"网络/厂商策略"的分界线上，分三层说明边界：

- **协议规定（机制层）**：多载波的结构与调度语义（38.213 §12 的锚点：每 CC 独立 HARQ 进程与反馈时序）、CA/BWP 的配置 IE（38.331）、BWP 切换对调度字段解释基准的影响（38.214）。
- **协议不规定（策略层）**：聚合哪些载波给哪个 UE（网络规划策略）、CIF 与 BWP 指示的切换时机（厂商算法）、射频前端功耗模型与省电策略的具体实现——协议定义机制与字段，不定义本节的能量账与吞吐账。
- **接收端义务（执行层）**：按 CIF 定位目标载波；按 BWP 指示切换解释基准；按每 CC 独立维护 HARQ 状态与软缓存；反馈按各自 CC 的 k1 时序——接收端的上下文管理是本节机制正确运行的前提。

上述边界与 T16.1/T16.2 一致：协议规定机制、实现决定策略、接收端执行决策——多载波维度不改变这条协议观。

## 小结

CA 用多 CC 并行调度提升吞吐（每 CC 独立 HARQ 与 k1，CIF 实现跨载波调度），BWP 用带宽子集实现能力适配与省电（切换改变 PRB 数与功耗，273→51 PRB 降 7 dB）。调度的三维扩展在 M16 系列收齐：T16.1 时频、T16.2 空间、本节多载波 + 带宽。

下一节 T16.4 是本系列收官：**MAC（媒体接入控制，Medium Access Control）层映射**——把逻辑信道 → 传输信道 → 物理信道的映射与 MAC PDU 结构讲清，收束调度/控制/数据的协议全景。

## 本节在 M16 系列中的位置

M16 系列推进到第三站：T16.1（调度/HARQ）→ T16.2（波束）→ T16.3（CA/BWP，本节）→ T16.4（MAC 映射收官）。本节的 CA/BWP 是"调度资源组织"的扩展——T16.4 将把资源组织放进 MAC（媒体接入控制，Medium Access Control）层的完整信道映射。
