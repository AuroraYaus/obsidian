# T20.5 时序收敛与关键路径调试：从负 slack 到可验证的架构修复
## 本节学习目标

本节讲解译码寄存器传输级的时序收敛。时序收敛不是简单地让综合工具多优化几轮，而是从静态时序分析报告中定位最慢路径，理解它为什么慢，选择流水线、retiming、寄存器复制、banking 或算法结构调整，再用协议向量和回归证据证明修复没有破坏译码语义。


- 从 timing report 中抽取 startpoint、endpoint、slack、logic depth、cell list 和 path family。
- 解释为什么 LDPC check-node min tree、Polar sorter、Turbo ACS/度量更新容易成为关键路径。
- 区分 pipeline、retiming、寄存器复制、banking、hierarchy 调整和算法结构调整各自解决什么问题。
- 评估面积、时序、功耗、延迟、吞吐和 debug trace 的取舍。
- 给出一个违例样例的诊断和修复计划，并列出修复后必须重跑的协议向量和覆盖点。
- 说明哪些 timing fix 是工程实现策略，不能写成 3GPP 协议要求。

如果只记住一句话：时序修复只有在“报告变好”和“回归证据仍然通过”同时成立时才算完成；负 slack 不能靠隐藏路径来解决。

## 关键路径识别

一个 timing violation 不能只看 slack 数字。最小诊断字段如下：

| 字段 | setup 口径 | hold 口径 | 作用 |
|:---|:---|:---|:---|
| `startpoint` | launch flop、input port 或 memory output。 | launch flop 或 clock-gating cell 输出。 | 判断路径从哪个 engine 或接口出发。 |
| `endpoint` | capture flop、output port 或 memory input。 | 近端 capture flop 或 latch。 | 判断落在哪个状态/数据寄存器。 |
| `slack` | 数据太晚到达会负 slack。 | 数据太早到达会负 slack。 | 判断违例严重程度。 |
| `path group` | setup path group，例如 `core_clk`。 | hold path group，例如 `core_clk` min。 | 确认属于哪个 clock 或约束组。 |
| `data arrival time` | cell/net 延迟越大越危险。 | cell/net 延迟太小也可能危险。 | 区分慢路径和短路径。 |
| `data required time` | 由周期、uncertainty、setup 和 skew 决定。 | 由 capture hold、skew、uncertainty 决定。 | 解释 required 为什么变化。 |
| `logic depth` | 判断单元级数过多或某个大 cell 慢。 | 判断是否几乎没有数据延迟。 | 指导 pipeline 或 hold buffer。 |
| `cell list` | compare、adder、mux、memory wrapper、fanout buffer、control decode。 | buffer、inverter、小 mux、clock gate。 | 判断慢在 datapath、memory、route 还是控制。 |
| `hierarchy` | Turbo、LDPC、Polar、soft buffer 或 unified top。 | 同左。 | 防止只凭顶层 slack 修错模块。 |
| `corner/mode` | slow/max corner 常主导 setup。 | fast/min corner 常主导 hold。 | 确认修复是否跨角有效。 |

路径分类公式可以写成：

$$
\mathrm{path\_class}
=
f(\mathrm{hierarchy},\mathrm{cell\_list},\mathrm{startpoint},\mathrm{endpoint}).
\tag{1}
$$

式 (1) 的意思是：不要只凭 module 名猜。比如 `softbuf_mgr` 里可能既有 RV address，也有 CBG mask，也有 reset rollback；需要结合 startpoint、endpoint 和 cell list 判断真正慢在哪里。

## Setup、Hold 和多角视图

setup 与 hold 是两类不同问题，修法不能混用。setup 违例通常表示一拍内组合逻辑太慢；hold 违例通常表示数据路径太短或 clock skew/uncertainty 使数据过早到达。给 setup 路径加 pipeline 可能改善最大延迟，但也可能制造新的 hold 短路径；给 hold 路径加 delay buffer 可能恶化 setup 或功耗。

| 检查 | 典型角 | 常见根因 | 常见修复 | 验证风险 |
|:---|:---|:---|:---|:---|
| setup/max | slow process、低电压、高温、RC worst。 | CNU min tree、Polar sorter、SISO ACS、bank mux、barrel shifter 过深。 | pipeline、tree split、retiming、architecture change。 | latency、checkpoint、protocol vector replay。 |
| hold/min | fast process、高电压、低温、RC best。 | 近端寄存器到寄存器路径太短、clock skew、gating cell 附近短路径。 | hold buffer、delay cell、useful skew、约束修正。 | 不得破坏 setup 和 clock-gating enable。 |
| recovery/removal | reset deassertion 或 async control。 | 异步 reset 释放未同步。 | reset synchronizer、RDC 约束和 directed reset vector。 | reset/abort 半提交。 |
| pulse width | clock gate、generated clock、macro clock。 | clock gate enable 或 generated clock 波形异常。 | 修正 clock definition、ICG 接法和 test mode。 | gate-level timing check。 |

多角多模式（Multi-Corner Multi-Mode, MCMM）记录至少要列 `mode`、`process`、`voltage`、`temperature`、`rc_corner`、`clock_period`、`uncertainty` 和 `derate_policy`。示例模板：

| View | Mode | PVT/RC | 检查 | 目的 |
|:---|:---|:---|:---|:---|
| `func_slow_setup` | functional decode | slow / low V / hot / rc_worst | setup | 主频和最慢 datapath。 |
| `func_fast_hold` | functional decode | fast / high V / cold / rc_best | hold | 短路径和 clock skew。 |
| `scan_shift_hold` | scan shift | fast / high V / cold / rc_best | hold | scan enable 和 scan chain。 |
| `low_power_sleep_exit` | SRAM sleep exit | slow+fast mixed | setup/hold/recovery | sleep/wake 控制和 retention。 |

OCV、AOCV 和 POCV 都是在处理片上变异，但精度不同：

| 方法 | 含义 | 使用风险 |
|:---|:---|:---|
| OCV | 对数据/时钟路径使用固定 derate。 | 简单保守，但可能过度悲观或漏掉深度相关差异。 |
| AOCV | derate 随 path depth、cell 类型和位置变化。 | 需要库表和流程支持；浅路径 hold 可能更敏感。 |
| POCV | 用统计 sigma/分布建模路径变异。 | 报告字段更复杂，需要 sign-off 团队统一阈值。 |

文档阶段不能声称某个 derate 已签核。真实报告应写清 `derate_table`、`aocv_table`、`pocv_sigma`、`clock/data derate` 和工具版本。

## LDPC Check-Node Min Tree

LDPC check-node update 需要找输入消息绝对值的最小值和次小值，通常还要计算符号奇偶。若并行度高，min tree 会变深。

简化关系：

$$
d_{\mathrm{tree}}
\approx
\lceil \log_2 n_{\mathrm{inputs}} \rceil
\tag{2}
$$

式 (2) 只表示比较树层数直觉。真实路径还包括绝对值、比较器、mux、符号处理、offset/scale、saturation、bank select 和 write-data mux。

常见慢路径：

```text
msg_ram_q -> abs -> compare tree -> min1/min2 mux -> OMS/NMS adjust -> saturation -> msg_ram_d
```

修复候选：

| 修复 | 改善 | 代价 | 需要重验 |
|:---|:---|:---|:---|
| 比较树分级 pipeline | 降低单周期比较深度。 | 增加 layer latency。 | layered schedule、syndrome checkpoint。 |
| min1/min2 预计算 | 把部分工作移到上一拍。 | 增加 buffer 和控制。 | message memory consistency。 |
| bank select 前移 | 减少最后一级 mux。 | 控制路径更复杂。 | bank conflict counter。 |
| 降低并行度 | 缩短树和 mux。 | 吞吐下降。 | throughput/latency sign-off。 |

## Polar Sorter

Polar SCL 的 sorter 需要在路径扩展后保留度量最小的 $L$ 条路径。list size 越大，比较和交换网络越深。

如果每个 information bit 把 $L$ 条路径扩展到 $2L$ 条，再选回 $L$ 条，粗略比较复杂度可写为：

$$
C_{\mathrm{sort}}
=
O(L\log L)
\quad\text{到}\quad
O(L^2),
\tag{3}
$$

具体取决于 sorter 结构。式 (3) 不是协议公式，而是硬件实现复杂度直觉。

常见慢路径：

```text
pm_old + branch_metric -> candidate_pm -> compare/swap network -> path_select -> lazy_copy_addr
```

修复候选：

| 修复 | 改善 | 代价 | 需要重验 |
|:---|:---|:---|:---|
| staged sorter | 缩短单周期比较网络。 | 增加每 bit latency。 | PM trace、path id、tie-break。 |
| partial sort | 减少比较器数量。 | 需要证明选择策略等价或有界。 | CA-SCL 块错误率spot、CRC selector。 |
| path metric 预归一化 | 减少位宽或比较范围。 | 数值策略变化。 | fixed-point PM regression。 |
| lazy-copy 地址寄存 | 减少 mux 深度。 | memory control 更复杂。 | path memory consistency。 |

Polar sorter 修复后，必须重跑 PM tie、all CRC fail、second-best CRC pass、RNTI mismatch 和 frozen mask negative 向量。否则可能 timing 过了，但路径选择错了。

## Turbo ACS 与度量更新

Turbo SISO/trellis 译码中，ACS 和 alpha/beta 度量更新容易形成长路径：

```text
branch_metric -> add path metric -> compare candidates -> select -> normalize/saturate
```

若 window 内并行度高，路径还会叠加 interleaver address、extrinsic RAM read/write 和 saturation。

修复候选：

| 修复 | 改善 | 代价 | 需要重验 |
|:---|:---|:---|:---|
| branch metric 预计算 | 缩短 ACS 当拍输入。 | 增加 metric buffer。 | branch metric checkpoint。 |
| ACS pipeline | 缩短 add/compare/select 链。 | 迭代 latency 增加。 | alpha/beta trace 对齐。 |
| normalization 分离 | 减少度量更新后级逻辑。 | 多一拍或多资源。 | fixed-point saturation counter。 |
| interleaver address 提前 | 减少 RAM 地址路径。 | 控制提前。 | interleaver address regression。 |

Turbo 的风险是“cycle 对齐”。pipeline 后外信息、交织地址、CRC gate 和 iteration counter 都可能偏一拍。必须更新 checkpoint manifest，而不是只改 RTL。

## Pipeline、Retiming 与寄存器复制

| 技术 | 适合场景 | 风险 |
|:---|:---|:---|
| Pipeline | 明确的数据路径过长，例如 sorter、min tree、ACS。 | latency 增加，valid/ready 和 trace 对齐改变。 |
| Retiming | 同步 datapath 边界清晰，工具可移动寄存器。 | reset、scan、debug trace 和等价验证复杂。 |
| Register duplication | 单个 enable/status/config fanout 很大。 | 面积增加，多副本一致性要检查。 |
| Tree split | 比较树、加法树、mux tree 过深。 | 中间结果需要寄存和控制。 |
| Banking | memory mux 或 route congestion 主导。 | bank conflict 和地址生成复杂。 |

判断流程：

1. 如果 cell list 主要是 compare/add/mux tree，优先考虑 pipeline/tree split。
2. 如果路径主要是一个信号驱动很多端点，考虑 register duplication。
3. 如果路径穿过 memory wrapper 和 mux，先检查 banking、地址提前和输出寄存。
4. 如果路径是配置/status fan-in，考虑分层 status、局部寄存和 IRQ 汇总。
5. 如果路径是 false-path 候选，先证明它真的不需要单周期检查。

## 面积、时序与功耗取舍

时序修复通常不是免费的：

| 修复 | 时序 | 面积 | 功耗 | 延迟 | 验证影响 |
|:---|:---|:---|:---|:---|:---|
| Pipeline | 改善明显。 | 增加寄存器。 | 可能增加 clock power。 | 增加。 | 需要更新 latency/checkpoint。 |
| Retiming | 可能改善。 | 变化不定。 | 变化不定。 | 表面不变。 | 等价验证和 reset 审查复杂。 |
| Register duplication | 改 fanout。 | 增加。 | 可能增加。 | 不变。 | 需要一致性断言。 |
| 降低并行度 | 改善路径和面积。 | 通常减少。 | 通常减少。 | 吞吐下降。 | throughput sign-off 需重算。 |
| Algorithmic approximation | 可能大幅改善。 | 变化较大。 | 变化较大。 | 变化较大。 | BLER/fixed-point 需重验。 |

面积/时序取舍必须回到产品目标：若目标是高吞吐 NR LDPC，简单降低并行度可能不可接受；若目标是低功耗控制信道 Polar，降低 list size 或 staged sorter 可能更合理，但要用 BLER/FER 或 directed vectors 证明风险可控。

## 具体数值例子：Polar Sorter 违例

假设 T20.4 的教学 timing triage 得到：

```text
Path: polar_sorter/candidate_pm_q -> polar_sorter/path_select_d
Clock: core_clk 2.000 ns
Arrival: 2.231 ns
Required: 1.920 ns
Slack: -0.311 ns
Cells: add, compare, swap_mux, lazy_copy_mux
```

slack 计算：

$$
\mathrm{slack}
=
1.920 - 2.231
=
-0.311\ \mathrm{ns}.
\tag{4}
$$

诊断：

| 项 | 判断 |
|:---|:---|
| Path family | NR Polar SCL sorter。 |
| 根因假设 | path metric update、compare/swap network 和 lazy-copy mux 放在同一拍。 |
| 第一修复 | 把 sorter 分成两级：第一级计算 candidate PM 并做局部比较，第二级做 final select 和 lazy-copy address。 |
| 预期收益 | 每拍比较/mux 深度降低，slack 改善。 |
| 代价 | 每个 information bit 增加 1 拍或改变内部 valid 对齐。 |
| 必须重验 | PM tie、CRC-aided selector、RNTI mismatch、all CRC fail、latency counter、trace checkpoint。 |

修复后，scoreboard 不能仍按旧 cycle 比较 `polar.pm_prune.stage7`。应更新 checkpoint manifest，例如把 checkpoint 从 `cycle_offset=0` 改成 `cycle_offset=1`，并让 T20.3 coverage report 标注 sorter pipeline bin 已命中。

小型 Python 分诊片段：

```python
violation = {
    "module": "polar_sorter",
    "slack_ns": -0.311,
    "cells": ["add", "compare", "swap_mux", "lazy_copy_mux"],
}
if violation["module"] == "polar_sorter" and violation["slack_ns"] < 0:
    fix = "stage_sorter"
    rerun = ["pm_tie", "crc_aided_selector", "rnti_mismatch", "latency_counter"]
```

## 修复后的验证方法

| 验证 | 内容 |
|:---|:---|
| Lint/elaboration | 新 pipeline 寄存器、valid 对齐、reset 行为无结构错误。 |
| Unit regression | 对应 engine 的 directed vectors pass。 |
| Checkpoint manifest | cycle offset、checkpoint id、trace hash 更新。 |
| Reset/abort | pipeline 中间状态 reset/abort 后不半提交。 |
| Coverage | 新增 timing-fix bin 或 microarchitecture bin 被命中。 |
| DC/STA | 重新综合或 STA，确认 WNS/TNS 改善且无新增 unconstrained path。 |
| Area/power | 记录寄存器、比较器、mux、clock power 增量。 |

若修复只改善 STA，但 directed vector 或 reset/abort 失败，不能签收。

## 常见错误

| 错误 | 后果 | 修正 |
|:---|:---|:---|
| 用 false path 隐藏真实数据路径 | 芯片可能真实违例。 | false path 必须有结构理由和验证证据。 |
| pipeline 后不更新 checkpoint | regression 大量假失败或漏失败。 | 更新 checkpoint manifest 和 latency policy。 |
| 只看最差 slack，不看 path family | 修错模块或只做局部缓解。 | 按 hierarchy/cell/start/end 分类。 |
| retiming 后忽略 reset | reset 行为可能变化。 | 做 reset/RDC/等价和 directed reset vector。 |
| register duplication 无一致性检查 | 副本漂移导致随机错误。 | 加断言和 gate-level sanity。 |
| 降并行度不重算吞吐 | 时序过了但性能不达标。 | 更新 throughput/latency/coverage sign-off。 |

## 自测题

1. LDPC check-node min tree 为什么容易成为关键路径？
2. Polar sorter 分两级 pipeline 后，为什么必须重跑 PM tie 和 CRC-aided selector？
3. register duplication 改善什么问题？带来什么风险？
4. 一个 false path 申请至少需要哪些证据？
5. 如果 Turbo ACS pipeline 后所有 payload 仍 pass，但 trace checkpoint 全部偏一拍，这算修复完成吗？

## 自测题参考答案

1. 因为 check-node 需要对多个输入消息求最小值/次小值、符号奇偶、缩放/offset 和饱和，比较树、mux、bank select 和写回可能叠在同一周期。
2. 因为 sorter 决定保留哪些路径，PM tie 和 CRC-aided selector 对路径顺序、tie-break、CRC pass/fail 都敏感；pipeline 可能改变 path id、valid 对齐或 selector 输入顺序。
3. 它改善高 fanout 信号的负载和走线延迟；风险是面积增加、多副本一致性、reset/enable 对齐和 debug 可读性下降。
4. 起点/终点、结构理由、为什么不需要单周期检查、替代验证方法、owner、批准记录、复核期限，以及 CDC/RDC 或功能回归证据。
5. 不算。payload pass 只能说明最终输出未暴露错误；checkpoint 偏移必须更新 manifest 或修复对齐，否则 bit-exact regression 和 failure localization 不可信。
