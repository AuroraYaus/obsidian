# T15.6 最终译码验证与证据报告：把协议、模型、RTL、覆盖率和综合边界汇成可审计签核包
## 本节学习目标

本节定义译码器项目最后一份验证与证据报告的格式。这里的“最终报告”不是把前面章节复制成一个长摘要，而是把每个结论连接到证据：哪一份协议、哪一个本地文件、哪条命令、哪个输出工件、哪个阈值、哪个失败分类、哪个已知限制、谁负责关闭。


- 设计一份可审计的最终证据报告，而不是只写“仿真通过”“综合通过”。
- 为三类重点译码工作列出协议证据、仿真证据、定点证据、RTL 证据、覆盖率证据、综合时序面积功耗证据和已知限制。
- 判断一个证据项是“真实已运行结果”“命令模板”“当前工具不可用边界”还是“需要关闭的缺口”。
- 把 Rel-19 协议锚点写到 TS 包名、章节、表/图/公式和 `3GPP_Rel19/processed/...` 本地路径粒度。
- 用签核清单防止静默跳过协议表格、失败向量、定点损失、覆盖率缺口、时序未跑和图表审计问题。

如果只记住一句话：最终证据报告的价值不是说项目“应该正确”，而是让每个正确性声明都有可追溯证据，让每个没跑的项目都以限制形式出现。

协议前因后果是：协议给出“应该译什么”和“接收端必须如何解释输入字段”；工程证据给出“这个实现如何被测试、量化、综合和审计”。最终报告必须把二者接起来。若报告只列协议章节，没有命令和结果，它只是索引；若报告只列测试通过，没有协议锚点，它不能证明 LTE/NR 译码语义正确。

## 最终报告的对象模型

最终报告至少应有七类对象：

| 对象 | 回答的问题 | 最小证据 |
|:---|:---|:---|
| `protocol_claim` | 这个字段或规则来自哪份协议？ | TS 包名、Release、章节、表/图/公式、本地路径、上游讲义。 |
| `simulation_result` | 浮点模型在什么信道和种子下表现如何？ | 命令、seed、SNR 点、帧数、BER/BLER、置信口径、输出文件。 |
| `fixed_point_result` | 定点模型相对浮点损失多少？ | 位宽、scale、clip、sat_count、bit-exact diff、性能损失阈值。 |
| `rtl_regression_result` | RTL 是否通过 directed/stress/replay？ | suite id、case id、expected status、pass/fail、assertion、failure bundle。 |
| `coverage_result` | 关键功能和代码是否覆盖？ | coverage bin、cross、hit/miss、waiver、close condition。 |
| `synthesis_result` | 工程实现是否有时序/面积/功耗证据？ | 工具版本、library、SDC、WNS/TNS、area、power、report path。 |
| `limitation_or_waiver` | 哪些项目未完成或有风险？ | 影响范围、原因、owner、关闭条件、过期时间。 |

一个最终报告若缺少 `limitation_or_waiver`，通常更危险，因为它暗示所有项都已完成。正确做法是：没跑真实 RTL 仿真就写“真实 RTL 仿真未运行”；没安装 DC 就写“无真实 mapped netlist、timing、area、power 报告”；没有 BLER campaign 就写“只有 toy snippet 或计划模板”。这不是削弱报告，而是让报告可信。

## 最终设计报告与最终证据报告

最终设计报告和最终证据报告可以放在同一个交付包里，但它们回答的问题不同：

| 报告 | 回答的问题 | 典型章节 | 不能做的事 |
|:---|:---|:---|:---|
| 最终设计报告 | 为什么这样设计译码器？架构、算法和实现取舍是什么？ | 需求、协议角色、算法选择、微架构、数据流、定点策略、接口、PPA 取舍、后续优化。 | 不能把“设计意图”写成“已经验证通过”。 |
| 最终证据报告 | 哪些结论已有可复现实验、回归、综合、STA 或审计证据？ | 协议证据、仿真结果、定点损失、RTL regression、coverage、gate-level、Formality、STA、限制和 sign-off。 | 不能用模板、toy 片段或口头判断冒充真实证据。 |

一个合格的最终设计报告应能让读者理解 LTE Turbo、NR LDPC、NR Polar 为什么共享子系统，为什么某些数据结构进入 soft buffer，为什么 LDPC CNU、Polar sorter 和 Turbo SISO 是 PPA 重点。一个合格的最终证据报告则要把这些设计主张逐条落到 `command`、`seed`、`artifact_path`、`report_id`、`failure_class` 和 `close_condition`。本项目当前文档阶段可以形成设计报告骨架和证据报告模板，但真实 sign-off 仍是 `hold`。

## 仿真摘要格式

仿真摘要要回答“模型在什么假设下跑了什么，结果是否达到阈值”。建议字段如下：

| 字段 | 含义 | 示例 |
|:---|:---|:---|
| `campaign_id` | 一批仿真的唯一编号。 | `t12_nr_ldpc_awgn_bg1_2026_06_21` |
| `decoder_family` | `lte_turbo`、`nr_ldpc`、`nr_polar`。 | `nr_ldpc` |
| `protocol_vector_set` | 使用的协议向量或参数集合。 | `rel19_decoder_corner_suite_2026_06` |
| `channel_model` | AWGN、fading 或其他信道模型。 | `AWGN` |
| `snr_points` | SNR 或 Eb/N0 点。 | `[0.5, 1.0, 1.5, 2.0]` |
| `seed_policy` | 主 seed、派生 seed 和可重放规则。 | `master_seed=0x12030001` |
| `frames_or_blocks` | 每点统计帧/块数量。 | `10000 TB per point` |
| `metric` | BER、BLER、FER 或 bit-exact pass rate。 | `BLER` |
| `threshold` | 验收阈值。 | `within reference curve tolerance` |
| `artifact_path` | 输出文件。 | `runs/t12/nr_ldpc_awgn_bg1/summary.json` |
| `status` | `pass`、`fail`、`not_run`、`partial`。 | 当前仓库应写 `not_run` 或 `partial`，不能写成真实通过。 |

本项目当前文档阶段有 T12 浮点仿真方案和 toy 片段，但没有完整真实 BLER campaign 输出。因此最终报告模板中应写：

| 项目 | 当前状态 | 正确写法 |
|:---|:---|:---|
| LTE Turbo BLER 曲线 | 未生成完整真实曲线。 | `status=not_run`，close condition 为运行 T12.2 指定 campaign 并归档 summary。 |
| NR LDPC BLER 曲线 | 未生成完整真实曲线。 | `status=not_run`，close condition 为运行 T12.3 指定 campaign。 |
| NR Polar BLER/FER 曲线 | 未生成完整真实曲线。 | `status=not_run`，close condition 为运行 T12.4 指定 campaign。 |
| 文档 toy snippet | 可作为格式验证。 | `status=pass_for_toy_only`，不能外推为性能签核。 |

## 定点损失摘要格式

定点损失不是只写“6 bit LLR 可用”。最终报告应把浮点、定点和 RTL 数值口径连起来：

| 字段 | 含义 | 审计风险 |
|:---|:---|:---|
| `quant_profile` | LLR 宽度、小数位、scale、clip、rounding 和 saturation。 | 未写 rounding 时，C/C++ 与 RTL 容易 bit-exact mismatch。 |
| `float_baseline` | 对照浮点模型、commit/hash、命令和输出。 | 没有 baseline 就无法谈“损失”。 |
| `fixed_result` | 定点命令、seed、输出、BER/BLER 或 bit-exact pass。 | 只给截图或口头结果不可审计。 |
| `loss_budget` | 允许损失，例如某 SNR 点 BLER 增量上限。 | 阈值必须在跑之前定义。 |
| `sat_statistics` | 饱和次数、最大值、最小值、溢出保护。 | sat_count 过高可能掩盖 scaling 错误。 |
| `trace_diff` | first mismatch、checkpoint id、trace hash。 | 只有最终 CRC fail 无法定位。 |

一个定点摘要可以这样写：

```json
{
  "fixed_point_result": {
    "decoder_family": "nr_ldpc",
    "quant_profile": "llr_q6_msg_q7_acc_q10_v1",
    "float_baseline_artifact": "runs/t12/nr_ldpc_bg1_float/summary.json",
    "fixed_artifact": "runs/t13/nr_ldpc_bg1_q6/summary.json",
    "loss_budget": {"bler_delta_abs_max": 0.002},
    "observed_loss": {"status": "not_run"},
    "sat_statistics": {"status": "not_run"},
    "close_condition": "Run T13.3 bit-exact model and archive trace hashes."
  }
}
```

当前仓库没有真实定点 campaign 结果和 RTL bit-exact trace，因此最终报告不能声称定点损失已通过。它可以声称的是：T13 已定义应记录哪些字段，T15.6 提供最终报告容器。

## RTL 回归摘要格式

RTL 回归摘要要把 T15.1 的 testbench、T15.2 的 vector suite 和 T15.3 的 coverage 连接起来。建议最小表如下：

| 字段 | 含义 | 示例 |
|:---|:---|:---|
| `regression_id` | 一次回归的唯一编号。 | `rtl_rel19_decoder_directed_2026_06_21` |
| `testbench_top` | testbench 顶层。 | `tb_decoder_subsystem` |
| `dut_version` | RTL commit/hash 或版本。 | `not_available_in_current_repo` |
| `vector_suite` | 向量套件。 | `rel19_decoder_corner_suite_2026_06` |
| `tiers` | smoke、directed、stress、replay。 | `smoke,directed_positive,directed_negative` |
| `assertions` | 启用断言集合。 | `reset_no_half_commit, soft_buffer_addr_range` |
| `timeout_policy` | DUT timeout 和 testbench timeout。 | `both_required` |
| `result_summary` | pass/fail/expected-fail 数量。 | 当前应写 `not_run`。 |
| `failure_bundle_index` | 失败包索引。 | `failures/index.json` |

expected-fail 的签核口径要写清楚：若 `ldpc_rv_mismatch_negative` 预期失败，并且 RTL 报出 `RATE_RECOVERY_OR_RV_MISMATCH`、保存 RV/k0/address trace、没有交付 TB，则该 case 是通过；若 RTL 译成 CRC pass 或只报 generic fail，则该 case 是失败。

当前仓库没有真实 SystemVerilog simulator 命令、波形、RTL coverage database 或真实 failure bundle。最终报告应写成“RTL 回归格式已定义，真实运行项未完成”，而不是把 T15.1-T15.3 的讲义规划误写成已通过。

## 覆盖率摘要格式

覆盖率摘要要覆盖功能覆盖率、代码覆盖率、断言覆盖率和 waiver：

| 覆盖对象 | 必备字段 | 签核条件 |
|:---|:---|:---|
| 功能覆盖率 | family、block size、RV、Qm、CRC status、reset、timeout、CBG、list size、LLR saturation。 | 关键 bins hit 或有批准 waiver。 |
| 交叉覆盖率 | LDPC `BG x Zc x RV x CBG`；Polar `context x crc_len x list_size`；LTE `rv x Ncb x filler/null`。 | 关键 cross 不得无解释缺失。 |
| 代码覆盖率 | line、branch、toggle、FSM。 | 工具报告归档并解释无法覆盖分支。 |
| 断言覆盖率 | assertion fired/pass/vacuous 统计。 | 断言不是只“没有失败”，还要证明被激活。 |
| waiver | owner、原因、影响、关闭条件、到期时间。 | 不允许无限期、无 owner waiver。 |

覆盖率不是越高越好这么简单。译码器中一些 error path 很少由随机测试触发，因此 directed negative vector 与 coverage bin 必须绑定。例如：

$$
\mathrm{critical\_coverage}
=
\mathrm{protocol\_bins}
\cap
\mathrm{state\_bins}
\cap
\mathrm{numeric\_bins}.
\tag{1}
$$

式 (1) 的含义是：协议字段、状态机和数值边界要同时被证明。一个 `RV=2` bin hit 了，但没有命中 soft buffer rewrite 或 saturation，不足以证明 RV 重传路径安全。

## Gate-Level Simulation 与 SDF 模板

Gate-level simulation（门级仿真）用于检查综合后网表、延迟反标和时序检查是否暴露 RTL 仿真看不到的问题。它不替代 STA，也不替代 RTL regression；它通常覆盖少量 smoke、reset、handshake、代表性协议向量和已知关键路径附近的 directed vector。

| 项 | 证据字段 | 失败分类 |
|:---|:---|:---|
| gate netlist | `mapped_netlist_path`、`netlist_hash`、`synthesis_report_id`。 | `NETLIST_MISSING`、`NETLIST_HASH_MISMATCH`。 |
| SDF back-annotation | `sdf_path`、`sdf_hash`、`sdf_corner`、`annotation_log`。 | `SDF_ANNOTATION_FAIL`、`SDF_INSTANCE_MISMATCH`。 |
| timing check | setup/hold/recovery/removal/pulse width 违规日志。 | `TIMING_CHECK_VIOLATION`。 |
| glitch | 输出 valid、IRQ、write enable、clock gate enable 是否出现非法短脉冲。 | `GLITCH_ON_CONTROL`。 |
| X propagation | reset 后 X 是否清除，casez/casex 或未初始化 memory 是否污染输出。 | `X_PROPAGATION_FAIL`。 |
| protocol replay | T15.2 directed vectors 的 gate-level smoke。 | `GATE_PROTOCOL_MISMATCH`、`GATE_TIMEOUT`。 |

脚本骨架示例：

```bash
simulator -64bit \
  +define+GATE_LEVEL \
  +sdf_verbose \
  -sdf max:decoder_subsystem_tb.dut:reports/dc/decoder_subsystem_top.mapped.sdf \
  -f scripts/sim/gate_filelist.f \
  +VECTOR=vectors/t15_2/nr_ldpc_cbg_rv2_smoke/vector.json \
  +SEED=20260620 \
  +DUMP_FAILURE_BUNDLE=1 \
  -l runs/gate/nr_ldpc_cbg_rv2_smoke/sim.log
```

这只是脚本形态模板。当前仓库没有真实 mapped netlist、SDF、gate filelist 或 simulator log，因此最终证据报告中这些项必须写 `status=not_run`。若后续运行，报告必须保存 annotation 覆盖率、timing check 违规数、X trace 摘要、失败 bundle 和 replay 命令。

## Formality 与等价验证模板

综合、retiming、ungroup、register duplication、clock gating 和 memory wrapper 替换都可能改变网表结构。等价验证的目标是证明 RTL reference 与综合 implementation 在约束条件下功能等价。常见工具可以是 Formality 或等价工具；报告中不要把工具名写成协议要求。

最小流程：

| 步骤 | 输入 | 输出 |
|:---|:---|:---|
| 读 reference | RTL filelist、define、library、top。 | reference design loaded。 |
| 读 implementation | mapped netlist、library、black-box/memory model。 | implementation design loaded。 |
| setup match | top、clock/reset、scan/test mode、undriven policy、constant constraints。 | compare points matched。 |
| verify | combinational/sequential/retiming aware compare。 | pass/fail、unmatched、aborted、inconclusive。 |
| debug | compare point、cone、constant、black box、state mapping。 | failure class 和 owner。 |

脚本骨架：

```tcl
set_svf reports/dc/decoder_subsystem_top.svf
read_verilog -r -f scripts/formality/rtl_filelist.f
set_top r:/WORK/decoder_subsystem_top
read_db libs/slow.db
read_verilog -i reports/dc/decoder_subsystem_top.mapped.v
set_top i:/WORK/decoder_subsystem_top
set_constant i:/WORK/decoder_subsystem_top/scan_en 0
set_constant i:/WORK/decoder_subsystem_top/test_mode 0
match
report_unmatched_points > reports/formality/unmatched.rpt
verify
report_failing_points > reports/formality/failing_points.rpt
```

等价失败分类建议：

| 失败类 | 含义 | 处理 |
|:---|:---|:---|
| `UNMATCHED_POINT` | RTL 和网表寄存器、端口或 compare point 未匹配。 | 检查 hierarchy、uniquify、retiming、SVF。 |
| `BLACK_BOX_MISMATCH` | SRAM wrapper、DesignWare 或 macro 模型不一致。 | 统一库模型或批准 black-box 策略。 |
| `RESET_STATE_MISMATCH` | reset 初值、同步/异步 reset 或 retention 状态不同。 | 回查 reset/RDC 和 directed reset vector。 |
| `CLOCK_GATE_CONSTRAINT_ERROR` | ICG enable/test mode 约束错误。 | 修正 constant 和 scan/test assumptions。 |
| `RETIMING_MAPPING_FAIL` | retiming 后状态映射缺失或 SVF 不完整。 | 保存 SVF，必要时限制 retiming。 |
| `REAL_FUNCTIONAL_MISMATCH` | 在同一约束下存在真实功能差异。 | 不能 waiver 成通过，需 RTL/netlist 修复并重跑回归。 |

Formality 通过也不证明协议向量通过；它只证明网表相对 RTL 没有被综合改变语义。最终证据报告应同时要求 RTL/gate-level vector replay、coverage 和 STA。

## 具体数值例子：一条 NR LDPC CBG 重传证据包

假设有一条 NR LDPC directed vector，目标是验证 CBG 部分重传和 RV2 soft combining。这里不用真实协议大表值，只构造一个小型证据包说明最终报告如何组织。

输入事实：

| 字段 | 值 |
|:---|:---|
| `decoder_family` | `nr_ldpc` |
| `ts_spec` | TS 38.212 + TS 38.214 |
| `source_sections` | TS 38.212 §5.4.2.1；TS 38.214 §5.1.7.2 |
| `cb_count` | 4 |
| `cbg_to_cb_map` | CBG0 = CB0/CB1，CBG1 = CB2/CB3 |
| `CBGTI` | `01`，表示只传 CBG1 |
| `CBGFI` | `1`，表示可与早前相同 CBG 实例合并 |
| `RV` | 2 |
| `expected_status` | `fail` for negative variant 或 `pass` for positive variant |

若 circular buffer 地址空间简化为 $N_{\mathrm{cb}}=8$，初传已覆盖地址 `[0,1,2,3]`，重传 RV2 应覆盖 `[4,5,6,7]`。soft buffer 覆盖率从 4 增到 8：

$$
C_{\mathrm{known}}^{(0)}=4,\qquad
C_{\mathrm{known}}^{(2)}=8.
\tag{2}
$$

若实现把 `CBGTI=01` 反成 CBG0，或把 RV2 地址写成 `[2,3,4,5]`，最终报告不能只写 CRC fail。它应记录：

| 证据 | 正确值 | 错误实现症状 |
|:---|:---|:---|
| 协议锚点 | TS 38.212 §5.4.2.1；TS 38.214 §5.1.7.2 | 错误实现无法解释 CBG/RV 来源。 |
| 地址轨迹 | `[4,5,6,7]` | `[2,3,4,5]` 或错误 CBG CB 列表。 |
| coverage | 新增 4 个 known 位置。 | 出现 repeat coverage，仍有 missing addresses。 |
| fail class | `RATE_RECOVERY_OR_RV_MISMATCH` 或 `CBG_MASK_MISMATCH` | generic `CRC_FAIL` 不合格。 |
| failure bundle | descriptor、LLR、soft before/after、trace hash、replay command | 缺任一项都不能 replay。 |

这个例子的核心是：最终报告要证明“为什么失败被正确归类”，而不是只证明“这条坏向量没有通过 CRC”。

## Python 证据清单校验片段

下面的 Python 片段只校验 manifest 的结构完整性，不证明译码正确。它适合作为最终报告提交前的 smoke check。

```python
def validate_final_evidence(report):
    required_top = [
        "schema_version",
        "project",
        "release_baseline",
        "protocol_evidence",
        "simulation",
        "fixed_point",
        "rtl_regression",
        "coverage",
        "synthesis",
        "known_limitations",
        "signoff",
    ]
    missing_top = [key for key in required_top if key not in report]
    if missing_top:
        return {"status": "fail", "missing_top": missing_top}

    missing_protocol = []
    for item in report["protocol_evidence"]:
        for key in ["ts", "package", "section", "local_path", "used_by"]:
            if key not in item or not item[key]:
                missing_protocol.append((item.get("evidence_id", "unknown"), key))

    silent_not_run = []
    for area in ["simulation", "fixed_point", "rtl_regression", "coverage"]:
        for idx, item in enumerate(report[area]):
            if item.get("status") == "not_run" and not item.get("close_condition"):
                silent_not_run.append((area, idx))

    if missing_protocol or silent_not_run:
        return {
            "status": "fail",
            "missing_protocol": missing_protocol,
            "silent_not_run": silent_not_run,
        }
    return {"status": "pass"}


toy_report = {
    "schema_version": "decoder_final_evidence_v1",
    "project": "lte_nr_decoding",
    "release_baseline": "Rel-19",
    "protocol_evidence": [
        {
            "evidence_id": "lte_turbo_rv",
            "ts": "TS 36.212",
            "package": "36212-j30",
            "section": "5.1.4.1.2",
            "local_path": "3GPP_Rel19/processed/TS_36.212_36212-j30/TS_36.212_36212-j30_content.md:817-923",
            "used_by": ["lte_turbo_rv_vectors"],
        }
    ],
    "simulation": [
        {
            "decoder_family": "lte_turbo",
            "status": "not_run",
            "close_condition": "Run T12.2 campaign and archive summary.",
        }
    ],
    "fixed_point": [],
    "rtl_regression": [],
    "coverage": [],
    "synthesis": {"status": "not_run", "reason": "DC unavailable"},
    "known_limitations": [],
    "signoff": {"decision": "hold"},
}

result = validate_final_evidence(toy_report)
assert result["status"] == "pass"
print("T15.6_FINAL_EVIDENCE_SCHEMA_OK", result["status"])
```

这个检查能抓住两类常见问题：协议证据只有口号没有路径，以及 `not_run` 项没有关闭条件。它不能替代协议精读、仿真、RTL 回归或综合工具。

## 常见错误

| 错误 | 后果 | 防护 |
|:---|:---|:---|
| 最终报告只写“通过”。 | 无法判断依据、范围和限制。 | 每个 pass 都要有命令、工件、阈值和协议锚点。 |

| 把讲义模板当真实运行结果。 | 虚假签核。 | `template`、`toy_only`、`not_run`、`pass` 分状态。 |
| expected-fail 被误记成失败。 | negative vector 无法用于回归。 | 记录 `expected_status` 和 `expected_fail_class`。 |
| 未跑 DC 却写时序收敛。 | ASIC 签核风险极高。 | 工具不可用必须写成 hold。 |
| coverage 只写百分比。 | 关键协议 cross 可能没命中。 | 保存关键 bins/cross hit/miss 和 waiver。 |
| 已知限制没有关闭条件。 | 风险永久悬空。 | 每个限制必须有 owner、close condition 和 expiry。 |
| 图表或公式审计不进最终证据。 | 文档证据本身可能不可读或公式失败。 | 把 LaTeX、引用、图形几何/可读性审计纳入签核 gate。 |

## 自测题

1. 为什么最终报告必须区分 `not_run`、`toy_only`、`template` 和 `pass`？
2. 一条 NR LDPC CBG 向量至少要引用哪两份 TS 的哪些语义？
3. 为什么 DC 不可用不能用“本节是教学文档”一句话略过？
4. 为什么 coverage closure 不能只写一个百分比？
5. 为什么协议证据表要写 `3GPP_Rel19/processed/...` 本地路径？
6. expected-fail vector 在什么条件下算通过？
7. 定点损失摘要为什么必须保存 saturation 统计？
8. 图形审计为什么进入最终证据报告？

## 自测题参考答案

1. 因为四者代表完全不同的证据等级。`pass` 是真实运行并满足阈值；`toy_only` 只证明小例子或代码片段；`template` 只证明格式；`not_run` 是未执行项。混用会导致虚假签核。
2. 至少引用 TS 38.212 的 LDPC rate matching/RV/CB 规则，以及 TS 38.214 的 CBG、CBGTI、CBGFI 调度上下文。前者决定地址，后者决定哪些 CBG 本次出现和是否可合并。
3. 因为最终报告是签核包。DC 不可用直接影响时序、面积、功耗和 mapped netlist 证据，必须作为 hold 或 limitation 出现。
4. 因为高百分比可能仍漏掉关键协议 cross。例如 RV2、CBGFI、reset 和 saturation 的组合未 hit，仍可能有产品级风险。
5. 本地路径证明证据来自当前项目抽取和核验的 Rel-19 文件，避免只凭记忆或外部网页引用协议。
6. 当 DUT 按预期失败、fail class 匹配、没有错误交付 payload，并保存 required dump/replay 字段时，expected-fail vector 才算通过。
7. saturation 统计能暴露 scaling、clip、符号扩展和累加宽度问题。即使最终 CRC pass，过高饱和也可能说明定点模型不可推广。
8. 本项目的文档本身也是交付物。若公式渲染失败、图表遮挡、箭头端点错误或表格字太小，证据不可读，审核无法复现结论。
