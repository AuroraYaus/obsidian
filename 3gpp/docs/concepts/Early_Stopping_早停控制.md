# Early Stopping 早停控制

早停控制是在译码迭代或路径搜索过程中用 syndrome、CRC 或路径选择条件提前结束无意义计算。它是实现策略，但必须尊重协议定义的 CRC 和输出验收边界。一句话本质：**早停是"考试提前交卷"——卷子已核对无误时继续检查收益很小，但检查标准不严就可能把错题提前交出去**。

## 独立解释任务

任务目标：解释早停如何在性能、时延、功耗和误通过风险之间折中。

## 起源与演进

迭代译码的收敛曲线是边际递减的：前几轮置信度快速爬升，后面每多跑一遍只换来一点点增益，功耗与时延却线性累加。早停控制就是在这条递减曲线上找"停点"的机制——它本身不是协议对象，而是接收端实现策略：3GPP 只规定验收边界（CRC 与 TB 交付条件），不规定厂商内部第几轮必须停。

可用的判据有四个，松紧不同、风险各异。最可靠的是 CRC 通过——译码结果过了整块验收就直接交付，几乎不存在误通过；LDPC 的 syndrome 全零是编码约束检查，比 CRC 便宜，但只说明"码字合法"、不说明"数据正确"，也不能替代 TB 重组边界检查；Polar CA-SCL 的路径度量与 CRC 辅助选择在搜索过程中修剪候选路径，属于另一类"边搜边停"；最大迭代次数则是硬上限——它不是早停而是兜底，防止某个码块在极端信道下永不收敛。误停的代价是真实的：门控标准不严时可能把错误候选提前放行，而一旦交付，后续流水线已经 flush，追不回来。

所以早停的设计永远是一个四元折中：性能（停早了损失增益）、时延（停晚了拖慢流水）、功耗（每轮迭代都是成本）、误通过风险（放行错误候选的代价）。这也解释了它为什么横跨三种译码器——Turbo 看 CRC、LDPC 看 syndrome、Polar 看路径度量，判据形态不同，折中结构相同。

## 科学定义

早停是接收端实现策略。迭代译码器每轮会得到新的候选 bit 或可靠度状态；如果 syndrome、CRC、路径度量或其他门控条件已经满足设计要求，就可以提前终止后续计算。协议通常规定验收对象和 CRC 边界，不规定厂商内部第几轮必须停。

## 直观模型

早停像考试提前交卷。题目已经全部核对无误时，继续检查收益很小；但如果检查标准不严，可能把错误答案提前交出去。因此早停要把节省功耗和避免误通过一起考虑。

## 常见误解

| 误解 | 正确理解 |
|:---|:---|
| syndrome pass 等于 TB pass | syndrome 是编码约束，TB 交付还要看 CRC 和重组边界。 |
| 早停是 3GPP 固定公式 | 早停策略多为实现设计。 |
| 越早停越好 | 早停要控制误停、CRC latency 和 pipeline flush 风险。 |

## 协议锚点

- CRC 验收边界：TS 36.212 Rel-19 §5.1.1；TS 38.212 Rel-19 §5.1。
- LDPC syndrome 语义来自奇偶校验矩阵和 Tanner 图算法，不是单独的 3GPP 停止公式。
- Polar CA-SCL 的 CRC 辅助选择与 TS 38.212 控制信息 CRC 章节相关。

## 关键要点

1. 早停是接收端实现策略——3GPP 只规定验收边界，不规定第几轮停。
2. 迭代收益边际递减：早停是在"增益-功耗"曲线上找停点。
3. 四类判据：CRC 通过（最可靠）、syndrome 全零（便宜但只证码字合法）、路径度量（CA-SCL 边搜边停）、最大次数（兜底不是早停）。
4. syndrome pass ≠ TB pass：交付还要 CRC 与重组边界。
5. 误停代价真实：错误候选放行后流水线已 flush，追不回来。
6. 三译码器判据形态不同、折中结构相同。
