# SIMD 与内存布局

单指令多数据（Single Instruction, Multiple Data, SIMD）与内存布局（Memory Layout）是译码器 C/C++ 实现层的吞吐工程：一条向量指令同时对多个数据 lane 运算，数据在内存中的排布决定这些 lane 能否由连续的缓存行供给。二者都不改变译码算法，只改变同一算法在定点模型上的执行代价，因此属于实现域而不是协议域。一句话本质：**SIMD 把一条指令的运算宽度分摊到多个 lane 上，内存布局决定这些 lane 能否被连续搬运；两者共同决定定点译码模型的实际吞吐。**

## 符号与记号约定

本笔记讨论的是存储与指令层面的量，全部单位都落在 bit、byte 与「个」上，不使用协议层的比特编号。下表逐个给出后文用到的符号，符号一律在首次出现之前定义。第四列按两类口径填写：由协议定义的码块长度给出规范号与条款，指令宽度、缓存行、步长与补齐长度这类实现参数写「实现域」并注明来源，它们不是 3GPP 的规定。

| 符号 | 读法 | 含义与取值 | 协议锚点 |
|:---|:---|:---|:---|
| $V$ | 大写 V | 向量寄存器的位宽，即一条 SIMD 指令一次能处理的比特数，取 128、256 或 512，单位为 bit，对应 SSE、AVX2 与 AVX-512 三档指令集 | 实现域：x86-64 指令集规格，非 3GPP 标准 |
| $w$ | 小写 w | 单个 lane 的位宽，即一个元素占用的比特数，取 16 时元素类型为 int16，取 8 时为 int8，单位为 bit | 实现域：定点模型的数据类型选择，非 3GPP 标准 |
| $L_{lane}$ | L 下标 lane | 一个向量寄存器能容纳的 lane 数，取 $V/w$ 的整数部分，单位为个，$V=256$、$w=16$ 时为 16 | 实现域：由 $V$ 与 $w$ 导出，非 3GPP 标准 |
| $K$ | 大写 K | 一个码块的有效元素个数，即译码 hot loop 需要处理的 LLR 或消息个数，单位为个，LDPC 基图 1 的码块最大 8448 | TS 38.212 §5.2.2 |
| $K_{pad}$ | K 下标 pad | 按 lane 数向上补齐之后的数组长度，取 lane 数的整数倍，单位为个，多出的部分只用于向量对齐 | 实现域：由 $K$ 与 $L_{lane}$ 导出，非 3GPP 标准 |
| $W$ | 大写 W | 一条缓存行的字节数，即缓存与内存之间一次搬运的最小块，常见取 64，单位为 byte | 实现域：x86-64 缓存层次规格，非 3GPP 标准 |
| $S$ | 大写 S | 步长，即相邻两个逻辑元素在内存中的地址间隔，单位为 byte，连续排列时等于元素位宽除以 8 | 实现域：数组下标换算得到，非 3GPP 标准 |

运算符与记号惯例有三点。其一，$\lceil\cdot\rceil$ 表示向上取整，$K/L_{lane}$ 的结果只要有小数就进一位，这是补齐长度的来源。其二，$L_{lane}$ 的下标 lane 是限定词而不是变量，读作「lane 数」，不表示 $L$ 与 lane 相乘。其三，byte 与 bit 的换算是 1 byte 等于 8 bit，本笔记的数值例一律按 int16、2 byte 计算，换用 int8 时同一 cache line 能容纳的元素数翻倍。

## 独立解释任务

任务目标：解释译码器 C/C++ 实现中 SIMD 与内存布局如何共同决定吞吐，给出向量宽度与 lane 数的换算、缓存行与步长对有效带宽的影响、结构数组与数组结构在 hot loop 上的差别，以及对齐与补齐对 bit-exact 回放稳定性的约束。

## 前置概念

译码器在实现层处理的对象是软值而不是比特。对数似然比（Log-Likelihood Ratio, LLR）用一个带符号的数表示某比特取 0 与取 1 的可能性之比的对数，其正负号表示倾向、绝对值表示置信度；工程上通常把它量化成定点整数，用 int16 或 int8 保存，量化步长与饱和边界由定点模型给定，见 [[LLR_对数似然比]] 与 [[LLR_Quantization_LLR量化]]。定点数的表示范围、舍入方式与溢出处理见 [[Fixed_Point_Numbers_定点数]]，本笔记只关心这些数在内存里如何排布，不改变它们的数值语义。

实现层的正确性判据是比特精确（bit-exact）。黄金模型（Golden Model）是用浮点或高精度定点写成的参考实现，它给出每一步的期望输出；比特精确回归要求 C/C++ 实现在相同输入下逐比特复现黄金模型的输出，任何差异都要定位到具体步骤，见 [[Golden_Model_黄金模型]] 与 [[Bit_Exact_Regression_比特精确回归]]。SIMD 与内存布局的改动必须保持这一判据：向量化只允许改变运算的打包方式，不允许改变每个元素的数值、顺序或有效范围，补齐产生的 lane 也不能被当作真实比特参与判决。

再往下是微架构层。处理器按寄存器堆、多级缓存与内存的层次组织数据，SIMD 单元从寄存器取数、以缓存行为单位从内存搬运；寄存器与缓存的容量、带宽和延迟由具体平台决定，见 [[RTL_Microarchitecture_RTL微架构]]。本笔记讨论的宽度、行大小与对齐都落在这一层，向上受定点模型约束，向下决定编译出的指令序列能否被流水线持续供给。

## 起源与演进

(1) **起点：标量循环的吞吐上限。** 译码器的 hot loop 对 LLR、外信息与路径度量逐元素做同一种运算，标量实现一次处理一个元素，指令吞吐与访存次数都随码块长度线性增长。SIMD 把同一种运算打包到一条指令上：SSE 的寄存器宽 128 bit，AVX2 为 256 bit，AVX-512 为 512 bit，在 int16 下分别能装 8、16、32 个元素。打包之后同一条加法或比较指令覆盖多个元素，指令条数按 lane 数成比例下降，这是向量化的直接收益来源。

(2) **缓存行成为搬运单位。** 处理器不是按元素从内存取数，而是按缓存行成块搬运，常见行大小为 64 byte。以 int16 的 LLR 为例，一条缓存行装 32 个元素：若程序顺序访问相邻元素，一条行可以服务 32 次访问；若相邻访问间隔 128 byte，每次访问都落在新的一行上，只用到该行的 2 byte。由此得到一个与协议无关的结论：有效带宽由访问模式决定，而不是由元素个数决定。

(3) **数据组织从 AoS 转向 SoA。** 结构数组（Array of Structures, AoS）把一个位置的全部字段放在一起，例如 LLR、外信息与硬判决相邻存放，调试时便于查看同一位置的全貌；数组结构（Structure of Arrays, SoA）把同类字段拆成各自的连续数组，hot loop 只搬运当前需要的那一个字段。译码迭代中绝大多数步骤只读写单一字段，AoS 会让每条缓存行携带大量暂时不用的字段，SoA 则让一条行几乎全部由有用元素组成，因此实现层通常把热数组改为 SoA。

(4) **对齐与伪共享进入正确性边界。** 对齐指数组首地址落在缓存行边界上，C++ 用 `alignas(64)` 声明；不对齐时一次向量读写可能横跨两条缓存行，既增加访问次数，也使同一段数据的读写次序依赖分配器行为。多线程场景下还有伪共享（false sharing）：两个线程写同一缓存行内的不同变量，缓存一致性协议把整行在核间来回传递，吞吐随核数下降。这两类问题的共同点是它们不改变算法结果却改变执行路径，因此必须进入回归范围。

(5) **边界：协议字段与实现字段分列。** 3GPP 只规定接收端要恢复的逻辑序列：码块长度、速率匹配输出长度、软缓存容量、交织与比特选择规则等，见 TS 38.212 §5.2.2 与 §5.4.2.1。SIMD 宽度、lane 数、缓存行、步长、补齐长度与对齐字节都是实现选择，协议不规定也不禁止。实现中必须把两类字段分开保存：`K`、`E`、`Ncb`、`Zc`、`layer`、`rv` 这类协议字段与 `alignment_bytes`、`simd_width_bits`、`lane_count`、`stride`、`padding` 这类布局字段不得混写，否则调试工具会把布局参数误读成协议参数。

## 科学定义

前几节把 SIMD 与内存布局拆成指令宽度、搬运单位与数据组织三条线索，本节把它们写成可计算的量：先由向量宽度算出 lane 数并给出补齐长度，再由缓存行与步长算出有效带宽，最后说明 AoS、SoA 与对齐在 hot loop 上的差别。

### 向量宽度与 lane 计数

一个向量寄存器能容纳的元素数由寄存器位宽除以元素位宽得到：

$$L_{lane}=\frac{V}{w}$$

$V=256$、$w=16$ 时 $L_{lane}=16$，即一条 AVX2 指令同时处理 16 个 int16 元素；换成 $V=128$ 时为 8，$V=512$ 时为 32。码块长度一般不是 lane 数的整数倍，最后一个向量只能部分有效，工程上有两种处理：一种是补零到 lane 的整数倍，用长度字段记住有效范围；另一种是保留尾向量，用掩码只更新有效 lane。补齐后的长度写成

$$K_{pad}=\left\lceil\frac{K}{L_{lane}}\right\rceil L_{lane}$$

以 $K=34$、$L_{lane}=16$ 为例，$\lceil 34/16\rceil=3$，故 $K_{pad}=48$，其中前 34 个是有效元素、后 14 个是补齐位。补齐位只扩展地址空间，不携带信息，CRC 复核、硬判决输出、迭代停止判据与路径度量选择都不能把它们当作真实比特。

### 缓存行与步长

缓存行决定一次搬运的字节数，元素在行内的位置决定这次搬运有多少被真正使用。设一条缓存行的字节数为 $W$、元素位宽为 $w$，则一条行能容纳的元素数为 $W/(w/8)$；$W=64$、$w=16$ 时为 32 个元素。若相邻元素的地址间隔为 $S$，则一条行被使用的比例约为 $(w/8)/\min(S,W)$：$S=2$ 时一条行服务 32 次连续访问，利用率接近满值；$S=128$ 时每次访问都落在不同行上，64 byte 中只用到 2 byte，占比约 3.1%。

这个换算解释了译码器里两类常见访问的差别。按码块顺序遍历 LLR 数组时 $S$ 等于元素字节数，访问是连续的，硬件预取器能提前把后续行搬入；按 layer 或 edge 索引跨步读取时 $S$ 等于索引间隔乘以元素字节数，跨步越大，每条行被浪费的比例越高。把步长写进数据结构而不是散落在下标表达式里，是为了让这一代价可测量：性能实验只需要改 `stride` 字段，就能复现同一段代码在不同布局下的差异。

### 结构数组、数组结构与对齐

AoS 把同一位置的多个字段连续存放，一个元素的全部字段落在同一段地址上；SoA 把每个字段单独成数组，同一字段的元素彼此相邻。设 hot loop 只读 LLR 一个字段、元素含 4 个 int16 字段，则 AoS 下一条 64 byte 缓存行装 8 个元素、其中只有 16 个字节属于当前字段，其余 48 个字节是暂时不用的字段；SoA 下同样的行装 32 个 LLR、64 个字节全部可用。这就是热数组采用 SoA 的定量理由；代价是调试时需要从多个数组拼回同一位置的全貌，因此实现中同时保存布局版本与 trace 哈希，避免调试工具按旧布局解读。

对齐的作用是让一次向量读写不跨越缓存行边界。`alignas(64)` 使数组首地址是 64 的整数倍，元素按 lane 宽度连续排列时，每个向量的地址也随之落在行边界上；若分配器不能保证对齐，应改用 `std::aligned_alloc` 或 `posix_memalign`，并把失败路径写进初始化检查。多线程写回时，对齐还把「同一行内的不同变量被不同线程写」这一伪共享条件显式化，便于按线程分块或按行填充隔开。对齐与补齐都不改变逻辑长度 $K$，只改变物理地址的分布，因此它们属于实现域，不能写进协议字段。

## 直观模型

把 LLR 数组看成一维地址空间：基地址由分配器给出，某个元素的地址是基地址加上它的序号乘以元素字节数，数组的逻辑长度是 $K$，物理长度是 $K_{pad}$。缓存行在这条地址空间上按 $W$ 字节切段，段边界与数组下标没有固定关系，只有在对齐成立时二者才重合。向量指令从地址空间中取一段连续字节装进寄存器，lane 数与段内元素数一致；尾部的补齐位仍然占据地址，但不进入任何判决。

这个结构给出四条约束。其一，数组上界由 $K_{pad}$ 而不是 $K$ 决定，越界检查必须用物理长度，遍历逻辑必须用有效长度。其二，一条缓存行覆盖的元素数由 $W$ 与 $w$ 决定，与 $K$ 无关；改变元素类型会同时改变行内元素数与 lane 数，两个量必须一起重算。其三，步长是地址空间的间隔，不是逻辑下标之差，跨步访问的代价按字节计算。其四，补齐位与 padding lane 只是地址空间中的占位，既不参与 CRC 复核，也不进入 bit-exact 比对的期望输出。

把结构落到一组具体数值上：取 $V=256$、$w=16$、$W=64$、$K=34$，则一条向量装 16 个元素、一条缓存行装 32 个元素、补齐后长度 48，最后一个向量只有 2 个有效 lane。若把该数组改成步长 128 byte 的跨步访问，每次读取都换一条缓存行，64 byte 中只有 2 byte 有用；若改为 SoA 并保持连续访问，同一条行服务 32 次读取。两组数值的差别全部来自地址分布，与译码算法无关。

## 常见误解

实现层的判断容易被简化成口号，下面列出六条常见误用及其准确表述。

| 误解 | 正确理解 |
|:---|:---|
| SIMD lane 多就一定快 | lane 数据无效、访问不连续或分支不一致时，向量宽度反而暴露访存带宽的不足；收益的前提是 lane 全部有效且由连续缓存行供给。 |
| AoS 总比 SoA 好 | 调试时 AoS 便于查看同一位置的全貌；译码 hot loop 通常只取单一字段，此时 SoA 的缓存行利用率显著更高。 |
| SIMD 与内存布局是 3GPP 规定 | 协议固定逻辑比特顺序、码块长度与译码结果，指令宽度、缓存行、对齐与步长都是接收机实现选择。 |
| int8 总优于 int16 | int8 使 lane 数与行内元素数翻倍，但量化精度下降、饱和更频繁；位宽选择由定点模型的精度与吞吐折中决定。 |
| 对齐只是性能细节 | 不对齐会跨缓存行读写、在多线程下引发伪共享，并使 bit-exact 回放的执行路径依赖分配器，属于回归范围。 |
| 补齐位可以当真实比特处理 | 补齐位只为向量对齐而存在，不携带信息；把它们送入 CRC、硬判决或度量比较会改变译码结果。 |

## 协议锚点

本篇的锚点绝大多数落在实现域，只有码块长度与软缓存接口能追到协议条款，下面把两类出处分开列出。

- **协议侧的码块长度**：LDPC 码块的最大长度由 TS 38.212 Rel-19 §5.2.2 规定，基图 1 为 8448、基图 2 为 3840，分段与填充在该节给出；速率匹配输出长度与软缓存容量见 §5.4.2.1。这些量决定 $K$ 的取值范围，但不规定数组如何布局。
- **协议侧的软缓存接口**：软缓存长度 `Ncb`、速率匹配输出长度 `E` 与冗余版本等字段由 TS 38.212 §5.4.2.1 定义，它们是实现必须保留的协议字段；布局字段与它们分列保存，不得混写。
- **非 3GPP 标准项**：SIMD 指令集、向量宽度、lane 数、缓存行大小、AoS 与 SoA、步长、补齐、对齐与伪共享均为工程实现方法论，任何 TS/TR 条款都不作规定；本笔记的数值例按 x86-64 的 64 byte 缓存行与 int16 元素计算，换平台时行大小与指令宽度需要重取。
- **讲义与实现位置**：完整工程讲解见 `docs/L3_工程实现/T18.5_SIMD_memory_layout_decoders.md`，面积与存储代价的核算见 [[T21.5_storage_and_area_estimation]]。

## 关键要点

把全文的结论收束为七条，逐条对应宽度、布局与边界三组内容。

1. SIMD 用一条指令处理 $L_{lane}=V/w$ 个元素，$V=128$、256、512 在 int16 下分别对应 8、16、32 个 lane。
2. 缓存行是搬运单位，64 byte 装 32 个 int16；连续访问时一条行服务 32 次读取，步长 128 byte 时 64 byte 中只用到 2 byte。
3. 码块长度不是 lane 整数倍时需要补齐，$K_{pad}=\lceil K/L_{lane}\rceil L_{lane}$，$K=34$、$L_{lane}=16$ 时补齐到 48。
4. hot loop 只取单一字段时 SoA 的缓存行利用率高于 AoS，AoS 的优势在调试可读性。
5. `alignas(64)` 使数组落在缓存行边界，避免跨行读写与伪共享，并使 bit-exact 回放的执行路径稳定。
6. 协议字段与实现布局字段必须分列，补齐位与 padding lane 不得当作真实比特参与判决。
7. SIMD 与内存布局是非 3GPP 标准的实现域内容，协议只规定接收端要恢复的逻辑序列。
